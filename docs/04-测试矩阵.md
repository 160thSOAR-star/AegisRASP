# 04 测试矩阵

> 对应《生成要求》⑦「测试矩阵输出」。
> 适用版本：aegis-rasp/2.0.0-beta（versionCode 6；native，API 36 / Android 16）· 51 个检测项（8 大类 + 沙箱独立性 + 文件系统视图一致性）· 打分模型见 [rasp_score.c](../rasp-detect-native/src/main/cpp/rasp_score.c)。
>
> 说明：本文档中的分数是**按修复后源码静态推算**的模型结果（未在真机实测），用于设计测试用例与对账；每一格都给出了可复算的依据。本轮已按「白名单收紧、ART 映射排除、快速模式真实裁剪」重新校准，**干净设备不再因 ART JIT / 白名单泛匹配落到可疑区间**，KSU 默认安装可进入 80–100。1.0.1-rc 的口径是 **51 项**：完整模式且沙箱开启 51、沙箱关闭 49、快速模式再减去跳过的 4 项（详见 §2.1）；新增的 10 项只增加证据面，权重（30/10/3）、同类 `0.7^n` 衰减、单强 25 下限、反 Hook 85 下限与 20/50 阈值均未变化。

## 1. 打分模型速查

### 1.1 公式（与实现逐行对应）

```
对每条 hit 且未被白名单豁免的证据 i：
    w_i   = weight(grade_i) × confidence_i          # 强 30 / 间接 10 / 弱 3
    n_i   = 该 (category, grade) 组此前命中数，上限 3
    score += w_i × 0.7^(n_i)

修正（按顺序）：
    if strong_hits > 0 and score < 25 : score = 25      # 单强证据下限
    if anti_hook_hit and score < 85   : score = 85      # 反 Hook 直接高风险
    if total_hits == 1 and weak_hits == 1 : score *= 0.5  # 单一弱线索减半
    score = clamp(score, 0, 100)

等级（用未四舍五入的 score 判）：
    score > 50 → high ； score > 20 → suspicious ； 否则 safe
报告 score = (int)(score + 0.5)
```

### 1.2 参数表

| 参数 | 值 | 出处 |
| --- | --- | --- |
| 强证据权重 | 30 | `grade_weight()` |
| 间接证据权重 | 10 | 同上 |
| 弱线索权重 | 3 | 同上 |
| 同类衰减 | `0.7^n`，n 上限 3（第 4 条起固定 0.343） | `dup[ci][gi]` |
| 单强证据下限 | 25 | `if (strong_hits > 0 && score < 25)` |
| 反 Hook 下限 | 85 | `if (c->anti_hook_hit && score < 85)` |
| 单一弱线索 | ×0.5 | `if (total_hits == 1 && weak_hits == 1)` |
| 等级阈值 | >20 可疑，>50 高风险（严格大于） | `rasp_score_compute()` |
| 证据置信度 | `Σ(weight·conf²) / Σ(weight·conf)`，截断 0.05–0.98 | 同上 |
| 无命中时置信度 | `available / total × 0.9` | 同上（`total` 为本次实际登记的项数，关闭检测项或快速模式跳过项后会变小） |
| 自定义权重 | `"ID=权重;..."`，0 < 权重 ≤ 100，覆盖等级权重 | `weight_spec` |
| 分类桶 | `mount / ksu / kernel / bpf / zygisk / inject / selinux / antihook / sandbox / fops / other`（1.0.1-rc 新增 `fops`，见 [rasp_score.c:19-24](../rasp-detect-native/src/main/cpp/rasp_score.c#L19-L24)） | `kCategories` |
| 白名单豁免 | ID 精确相等即豁免；非 ID 片段 ≥ 10 字节、不以 `/` 开头、非通用进程名；强证据还须 ≥ 14 字节且含 `=`/`.`/` on ` | `evidence_whitelisted()` |
| 证据顺序 | ZYS-005 / ZYS-006 / ZYS-008 由 Java 层在 native 检测前提交（`rasp_ingest_external`），先进入 `zygisk/indirect` 桶 | 影响同类衰减的 n 起点，见 §5.2 |

### 1.3 等级区间

| 分数 | 等级 | UI 呈现 | 处置 |
| --- | --- | --- | --- |
| 0–20 | safe | 绿 | 通过 |
| 21–50 | suspicious | 黄 | 人工确认；结合命中 ID 判断是「低置信度线索」还是「已知误报」 |
| 51–100 | high | 红 | 视为高风险环境；结合 §6 的偏差说明排除误报 |

> 注意：报告的 `counts.hits` 含被白名单豁免的条目，`score` 不含；快速模式下被跳过的项不出现在 items 里（见 §4.4）。

### 2.1 项数与可执行项数的口径（51 / 49 / 47 / 45）

`counts.total` 是本次**实际登记**的检测项数：快速模式跳过的项根本不出现，`disabled` 关闭的项也不出现。依据是 [rasp_jni.c:206-215](../rasp-detect-native/src/main/cpp/rasp_jni.c#L206-L215) 的调度顺序与各模块的 `fast_mode` 分支：

| 配置 | `counts.total` | 少掉的项 | 依据 |
| --- | --- | --- | --- |
| 完整模式 + 沙箱开启（默认） | **51** | — | [CheckCatalog.kt:12-85](../rasp-detect-native/src/main/java/com/rasp/detect/CheckCatalog.kt#L12-L85) 共 51 条；`jni_run_detect()` 共 10 个模块入口（mount / ksu / kernel / bpf / zygisk / inject / security / extra / sandbox / antihook） |
| 完整模式 + 沙箱关闭 | **49** | MNT-007、SBX-001 | `if (!rasp_cancelled() && ctx.sandbox_enabled) rasp_check_sandbox(&ctx);`——两项都由 `rasp_check_sandbox()` 产出 |
| 快速模式 + 沙箱开启 | **47** | 再减 MNT-002、MNT-003、MNT-006、BPF-003 | mount 模块三处 `if (!c->fast_mode …)`（[rasp_checks_mount.c:468-472](../rasp-detect-native/src/main/cpp/rasp_checks_mount.c#L468-L472)）+ kernel 模块 `if (!c->fast_mode …) check_net_latency(c)` |
| 快速模式 + 沙箱关闭 | **45** | 上两组叠加 | 同上 |

要点：

- **新增的 10 项在快速模式下仍全部执行**：`rasp_check_extra()` 没有 `fast_mode` 分支（[rasp_checks_extra.c:658-670](../rasp-detect-native/src/main/cpp/rasp_checks_extra.c#L658-L670)）；9 个 native 新项共享 2500 ms 预算，其中 `check_errno_semantics()` 前没有 `rasp_deadline_hit()` 检查，属「必跑」项。
- 关闭单项（`disabled`）会进一步减少 `total`；对账时以报告里的实际值为准，不要用 51 硬套。
- 「无命中时置信度」= `available / total × 0.9`，`total` 变化会直接改变置信度读数（见 §5.1）。

### 2.2 新增 10 项的分场景预期

## 3. 场景构造步骤与通过判据

### 3.1 通用前置

1. 构建：`./gradlew :app-ui:assembleDebug`（或 release），确认 `librasp-detect.so` 已打入 APK 的 `lib/arm64-v8a/`（或对应 ABI）。
2. 安装：`adb install -r app-ui/build/outputs/apk/debug/app-ui-debug.apk`。
3. 基线记录：`adb shell getprop ro.build.fingerprint`、`ro.build.tags`、`ro.boot.verifiedbootstate`、`uname -a`，填入 §7 的记录表。
4. 每次测试前清空应用数据（`adb shell pm clear <pkg>`）；白名单/模式切换后再跑一次。
5. 每次跑完后导出报告（JSON），保留 `items` 原文作为对账依据。

### 3.2 场景 ①：干净 AOSP15 user

- **构造**：Pixel / 官方 GSI 的 Android 15 user 版，bootloader 锁定，未刷任何 root；安装检测 App，完整模式运行。
- **核对**：`adb shell ps -A | grep -E "ksud|magisk|zygisk"` 应为空；`/data/adb` 不存在。
- **通过判据**：
  - 无 MNT-001/002/003/004/005/006/007/008/009 命中；
  - 无 KSU-001～005 命中；
  - 无 AHK-001～006 命中（含新增的 AHK-005 / AHK-006）；
  - 新增的 KRN-006/007、INJ-005、FOPS-001、ZYS-007/008 也不应命中（逐项基线见 §2.2）；
  - ZYS-001/002/004、INJ-001 原则上不命中；若命中，raw 必须指向非 JIT 的 memfd、≥2 段 rwx 或 >64MB 的匿名 rw，否则判为实现缺陷；
  - score ≤20、level=safe；若因 ≥2 段非 JIT rwx 落到 21–24，记录 raw 并按残留误报归档。

### 3.3 场景 ②：干净 CloreOS15 正式版

- **构造**：CloreOS 官方正式版固件（未解锁），安装检测 App，完整模式。
- **核对**：`getprop | grep -i clore` 应有原厂属性；`/system/build.prop` 可读。
- **通过判据**：
  - 同 ①；
  - SEL-005 的 `mismatches=0`（原厂属性与磁盘一致）；
  - SEL-003 若命中（orange），只允许作为弱线索（≤2 分），不得单独把分数推过 50。

### 3.4 场景 ③：KernelSU 默认安装（无隐藏）

- **构造**：
  1. 解锁 bootloader，用 KernelSU 的 `boot.img` 补丁流程刷入（`fastboot flash boot kernelsu_patched.img`）；
  2. 安装 KernelSU 管理器，确认 `su` 可用（`adb shell su -c id`）；
  3. 在管理器中启用 ZygiskNext 并安装至少一个 Zygisk 模块（模拟「默认可用环境」），**不安装** Shamiko / HMA / LSPosed / DenyList；
  4. 重启后确认 `ps -A | grep ksud` 可见；
  5. 安装检测 App，完整模式运行。
- **通过判据**：
  - KSU-001 命中且 confidence≈0.92（raw 中 `matched>0`，`processes` 含 `ksud(pid=...)`）；
  - **MNT-004 与 ZYS-003 必须计分**（修复前它们被整类豁免，报告里会看到 `hit=true` 且 `score` 不涨——现在应正常涨分）；
  - SEL-004 命中（overlay/rw 系统分区）；KRN-002 不再被 Linux version 系列豁免，内核串含 KSU 标记时应命中（1.8–2.1）；
  - 新增 10 项在该场景多为 miss；若 AHK-005 / AHK-006 命中，说明环境除 root 外还有用户态 hook，`score` 会直接进 85+，应单独记录；
  - score 84–100、level=high；若只命中 KSU-001（无模块/无 overlay），落在 28 附近属模型取向（§6.3），应先确认证据画像。

### 3.5 场景 ④：KSU + Shamiko 全套隐藏

- **构造**：
  1. 在 ③ 的基础上安装 Shamiko（Zygisk 模块），在 KernelSU 管理器中对检测 App 启用隐藏（Shamiko 白名单/黑名单按模块文档配置，目标是让 App 看不到 root 与模块）；
  2. 重启，确认 `adb shell su` 仍可用（root 未移除），但 App 内 `/proc/self/mountinfo` 看不到 `/data/adb`；
  3. 运行检测。
- **通过判据**：
  - KSU-001 仍应命中（进程名特征通常不被 Shamiko 隐藏）——若未命中，记录为「ksud 亦被隐藏」；
  - **MNT-003 命中**（应用侧 unmount 后与 system_server 视图不同）是核心判据；
  - MNT-004 / ZYS-003 因应用侧不可见而 miss，属预期；若 system_server 的 mountinfo 可读，MNT-002 会正常计分（+25.5，MNT-003 衰减后 +17.85）；
  - score 30–75；MNT-003 + KSU-001 同时出现时通常 ≥52，MNT-002 可读时再上移。

### 3.6 场景 ⑤：KSU + Shamiko + HMA Next + LSPosed 全隐藏

- **构造**：
  1. 在 ④ 的基础上安装 LSPosed（Zygisk 版），确认模块作用域包含检测 App；
  2. 安装 HideMyApplist Next，配置「对检测 App 隐藏指定测试包」（至少隐藏 2 个已安装包）；
  3. 重启，确认 HMA 生效（用另一个包列表查看工具验证被隐藏包不可见）；
  4. 运行检测。
- **通过判据**：
  - ZYS-005 命中（`hiddenFromInstalled` 或 `appsMissing/appsExtra` 非空）**或** ZYS-006 命中（binder 与门面结果不一致）；若属性区在运行期被 `resetprop` 改过，ZYS-008 也会命中（+6.0，衰减后约 +2.9）；
  - MNT-003 命中；ZYS-004 若 LSPosed 模块以具名 so 映射则命中（conf 0.85），以匿名 memfd 注入则退化为 ZYS-001；MNT-002 若可读同样计分；
  - KSU-001 视隐藏程度，可能命中也可能 miss；
  - score 43–100；典型 69（MNT-003 25.5 + ZYS-004 25.5 + ZYS-005 6.5 + ZYS-006 4.9 + ZYS-001 3.4 + ZYS-002 3.1；ZYS-005/006 先注入，ZYS-001/002 落在 n=2/3 的衰减位上；若 ZYS-008 也命中，它占 n=2 位，典型值约 71）。

### 3.7 场景 ⑥：Zygisk DenyList 全开

- **构造**：
  1. Magisk（或带 DenyList 的 Zygisk 实现）+ Zygisk 启用；
  2. 在 DenyList 中勾选**全部应用**（至少包含检测 App 与常用应用），开启「Enforce DenyList」；
  3. 重启，确认检测 App 的 maps 中没有 Zygisk 模块映射；
  4. 运行检测。
- **通过判据**：
  - KSU-001 命中（`magiskd`/`zygiskd` 特征，conf 0.92）；
  - MNT-003 命中（DenyList 的应用侧隔离与 system_server 视图不同）；MNT-002 若可读也算强证据；
  - ZYS-001 通常 miss（应用被排除注入），不得把「ZYS-001 miss」当成安全；
  - score 32–75（MNT-003 命中时约 57；MNT-002 可读时约 75）。

### 3.8 场景 ⑦：Android Studio 模拟器 userdebug

- **构造**：
  1. Android Studio → AVD Manager → 创建 API 35、x86_64、`google_apis`（非 Play）镜像；
  2. 启动 AVD，`adb install` 检测 App，完整模式运行；
  3. 记录 `getprop ro.build.type`（应为 userdebug）、`ro.boot.verifiedbootstate`。
- **通过判据**：
  - 无 KSU-001～005 命中；
  - SEL-003 允许命中（orange），只作弱线索；
  - SBX-001 应为 `available=true`（clone3 在模拟器上通常可用）；若 `error` 显示 seccomp，记录为环境限制；
  - score ≤24（ART 映射已排除，通常 0–1；若 ≥2 段 rwx 命中 ZYS-004 会到 24，需看 raw）。

### 3.9 场景 ⑧：检测函数被 Hook 的对抗环境

- **构造（原生层 Hook，触发 AHK）**：
  1. 在已 root 设备上安装 frida-server（或等价注入框架），确认可注入检测 App；
  2. 编写 Hook 脚本，对 `libc.so` 的 `open`/`read` 做 inline hook（返回伪造的 mountinfo 内容），或用同等方式 patch 本库 `rasp_emit`/`rasp_score_compute` 的代码页；
  3. `frida -U -f <pkg> -l hook.js` 启动后运行检测。
- **构造（Java 层 Hook，用于验证「检测不到但要能被元信号发现」）**：
  1. 用 LSPosed 模块 Hook `com.rasp.detect.RaspNative.runDetect`，直接返回 `{"schema":1,"score":0,"level":"safe","items":[]}`；
  2. 运行检测，检查 `durationMs`、`counts.total`、`items` 条数是否符合伪造特征（§6.7）。
- **通过判据**：
  - 原生层 Hook：`antiHook.hit=true`，AHK-001/AHK-002/AHK-003 至少一项命中，`score≥85`；1.0.1-rc 起 AHK-005 / AHK-006 也会置位，补测时应至少命中其中一项；
  - Java 层 Hook（绕过原生自校验）：`score` 可能为 0，但必须能用「`items` 为空 / `counts.total=0` / `durationMs` 异常」识别为不可信报告；
  - 两种情况都不得把「报告不可信」当作「设备安全」。

## 4. 性能判据

### 4.1 硬指标

| 指标 | 判据 | 测量方法 |
| --- | --- | --- |
| 完整模式总耗时 | < 6 s（目标 < 1.5 s） | 端到端：`SystemClock.elapsedRealtime()` 包住 `engine.detect()`；原生段看报告 `durationMs` |
| 快速模式总耗时 | < 2 s | 同上（`RaspConfig.fastMode = true`） |
| 主线程不阻塞 | 检测期间 UI 可交互、无 ANR、无 >16 ms 的主线程同步等待 | 见 §4.3 |
| 单检测项熔断 | 各模块预算内（下表），超时跳过不影响整体 | 报告 `error` 字段与 `available` |

### 4.2 模块预算与预期实测

预算来自各 `rasp_check_*()` 开头的 `rasp_ctx_set_budget()`，是**熔断上限**，不是固定等待时间：

| 模块 | 预算 (ms) | 典型耗时 (ms) | 备注 |
| --- | --- | --- | --- |
| mount | 2500 | 20–120 | 读 `mountinfo`（~100KB）；快速模式跳过跨进程读与多路径校验 |
| ksu | 2000 | 10–80 | 完整模式扫描最多 700 个进程；快速模式 220 |
| kernel | 2000 | 5–30 | 240 次 `getpid`（快速模式 80 次）+ 若干 proc 读取 |
| bpf | 1500 | 5–40 | fd/fdinfo 遍历 + 120 次 socket RTT（快速模式跳过 RTT） |
| zygisk | 2500 | 5–60 | 多次 maps 解析 + mountinfo 解析 |
| inject | 2000 | 5–40 | maps + status + libc 入口检查 |
| security | 1800 | 5–30 | proc/sys 读取 + build.prop 比对 |
| extra | 2500 | 10–80（静态估算） | 1.0.1-rc 新增 10 项：mountinfo/statx/statfs 交叉、时钟与 errno 探针、maps 来源扫描、openat2 双读；**无 `fast_mode` 分支，快速模式不裁剪** |
| sandbox | 2500 | 5–1500 | fork/`clone3` + 子进程读 64KB；失败时最多等 1500 ms 后 SIGKILL |
| antihook | 1500 | 1–20 | 代码段哈希 + JNI 表校验 |

> 合计的「最坏情况」是各预算之和（2.5+2.0+2.0+1.5+2.5+2.0+1.8+2.5+2.5+1.5 = 20.8 s），但只有在对端持续阻塞时才会接近；实测典型值远低于 1 s。沙箱超时是唯一可能接近 1.5 s 的单点。
>
> **注意（1.0.3 起）**：上表**不含兼容探测阶段 `probe`**。`rasp_probe_compat` 会 fork 一个一次性子进程，并在 400 × 2 ms 的窗口内等待，自身最长约 **800 ms**，且不计入任何模块预算。因此真正的最坏总耗时是 **20.8 s + 0.8 s ≈ 21.6 s**（1.0.1 及更早为 20.8 s）。探测子进程通常几毫秒完成，典型值不受影响；上面「实测典型值远低于 1 s」这句话本身仍然**未经真机实测**。

### 4.3 主线程不阻塞的验证方法

1. **代码路径**：`RaspViewModel.startDetection()` → `viewModelScope.launch` → `RaspEngine.detect()` → `withContext(Dispatchers.Default)` + JNI 调用。主线程只负责状态更新，原生检测与证据回调都在后台线程。
2. **StrictMode**：在 debug 构建的 `Application` 中开启 `detectDiskReads()`/`detectDiskWrites()` → `penaltyLog()`，检测期间观察 logcat，不应出现主线程磁盘读写告警。
3. **UI 交互**：检测期间滑动列表、展开卡片、切换设置页，应无掉帧/ANR；`elapsedMs` 由 120 ms 定时器驱动，与检测线程无关。
4. **帧率**：可用 `adb shell dumpsys gfxinfo <pkg>` 观察检测期间的 jank 帧数（背景雪花动画本身会占用一定帧时间，需与基线对比）。
5. **取消路径**：点击取消 → `cancelDetect()` 置位 `g_cancel`，各模块在下一次 `rasp_cancelled()` 检查点提前返回（不打断当前模块内部的阻塞读）；通常 <1 s 回到空闲态，若取消瞬间正在等沙箱子进程，最坏约 2.5 s（1500 ms 等待 + 当前模块收尾）。

### 4.4 快速模式的真实行为（修复后）

快速模式现在**确实裁剪检测项**（[rasp_checks_mount.c:465-472](../rasp-detect-native/src/main/cpp/rasp_checks_mount.c#L465-L472)、[rasp_checks_kernel.c:562](../rasp-detect-native/src/main/cpp/rasp_checks_kernel.c#L562)、[rasp_checks_ksu.c:82](../rasp-detect-native/src/main/cpp/rasp_checks_ksu.c#L82)）：

| 差异 | 完整模式 | 快速模式 |
| --- | --- | --- |
| 跨进程 mountinfo 比对（MNT-002） | 执行 | **跳过（不出现该 item）** |
| 跨进程 stat 比对（MNT-003） | 执行 | **跳过** |
| 多路径读取一致性（MNT-006） | 执行 | **跳过** |
| 网络包处理时延（BPF-003） | 执行 | **跳过** |
| 新增 10 项（`rasp_check_extra`） | 执行 | 执行（模块无 `fast_mode` 分支，不裁剪） |
| 进程扫描上限（KSU-001） | 700 | 220 |
| KRN-001 采样轮次 | 240 | 80 |

后果与使用建议：

- 快速模式的 `counts.total` 是 **47**（51 − 4，沙箱开启时）、沙箱关闭时 **45**，不是 51；「无命中时置信度」按实际 `total` 计算，别拿 51 去对账（四档口径见 §2.1）。
- 省下的主要是跨进程读取与 socket RTT，典型可省 30–120 ms；在 SELinux 拒绝读跨进程视图的设备上省得更多。
- **快速模式会丢失 MNT-002/003/006**，root/隐藏场景可能因此少 25 分左右（MNT-003 是强证据），所以**验收 root 环境必须用完整模式**；快速模式只用于日常自检。
- 设置页文案「快速模式（跳过高开销项）」现在与实现一致；若要进一步裁剪单项，用设置页的检测项开关（`disabled` 列表，`rasp_emit()` 直接早退）。

## 6. 区间校准与已知偏差

### 6.1 需求目标 vs 静态推算

| 场景 | 需求目标 | 静态推算 | 偏差 | 根因 |
| --- | --- | --- | --- | --- |
| ① 干净 AOSP15 | 0–10 | 0–24（典型 0–3） | 接近 | 残留映射只在小概率下命中（02 文档 §2.10） |
| ② 干净 CloreOS15 | 0–15 | 0–24（典型 0–2） | 接近 | 同上 |
| ③ KSU 默认 | 80–100 | 84–100（典型 100） | 一致 | 修复后 Mount/Zygisk 强证据恢复计分 |
| ④ KSU+Shamiko | 50–80 | 30–75（典型 57） | 低端偏低 | ksud 被隐藏或视图一致时不足 50；MNT-002 可读时上移 |
| ⑤ 全隐藏 | 35–65 | 43–100（典型 69） | 偏高 | 修复后 ZYS-004/MNT-003/MNT-002 恢复计分（§6.4） |
| ⑥ DenyList | 40–70 | 32–75（典型 57） | 接近 | MNT-003 miss 时偏低；MNT-002 可读时上移 |
| ⑦ 模拟器 | 0–20 | 0–24（1.0.2 起典型 0–1；INJ-005 改为不可用，不再有典型 7 的噪声） | 接近 | ART 映射与短片段豁免已修复（02 文档 §2.10）；INJ-005 的 `/data/local/tmp` 误报见 §2.2 |
| ⑧ Hook 对抗 | 60–90 | 85–100 | 偏高 | 反 Hook 下限固定 85 |

### 6.2 根因一：条件豁免与「锚点可达性」

第三版模板已无「无条件豁免任何检测项」的条目，上一版的 3 处自命中（MNT-002 的 `system_server`、KSU-003 的 `zygote64`、KRN-002 的 `Linux version …`）随「通用进程名黑名单 + 删除版本串 + 分号分隔」一并消失。仍然存在的只有两类**条件豁免**：

- **MNT-004**：仅当 `example` 恰为 `overlay on /system_ext` 时豁免。其余 4 条锚点（`tmpfs on /apex`、`tmpfs on /dev/__properties__`、`proc on /proc`、`sysfs on /sys`）目前不会出现在 MNT-004 的示例里——它只检查 `/system`、`/vendor`、`/product`、`/system_ext`、`/odm`，这些锚点属于「保留以备扩展」。
- **ZYS-005 / ZYS-006**：差异列表出现 `com.android.*` 系统包名时整条豁免。若 HMA 隐藏的是系统应用（少见），⑤ 会少 6.5 / 4.9 分。
- **ID 豁免分支已可用**（7 字符 ID 也生效），但默认模板没有放任何 ID；用 `extraJson` 做业务豁免时要留痕。

对分数的影响：MNT-002 不再被 `system_server` 豁免，Shamiko / DenyList 场景若 system_server 视图可读会多出 25.5（MNT-003 衰减后 17.85）；KRN-002 在内核串含 KSU/Magisk 标记时正常计分 1.8–2.1。

### 6.3 根因二：模型取向（不是缺陷）

- 单条强证据只到 25（下限），不直接判高风险——这是需求 ⑥-3 的明确要求；
- 因此「只有 ksud 可见、没有任何其它痕迹」的裸 KSU 环境只能到 28 分；需求书 ③「KSU 默认安装 80–100」隐含了「Zygisk 注入 + 模块 overlay + 视图隔离」的证据画像（§5.2 的 7 条证据）；
- 验收时应按「证据画像是否齐全」判定，而不是只装满 KSU 就期待 80+。

### 6.4 根因三：隐藏场景的分数上移

- 修复前 MNT-004 / ZYS-003 / SEL-004 / ZYS-004 被白名单整类豁免，隐藏套件反而容易「看起来干净」；
- 修复后这些强证据恢复计分，④⑤⑥ 的典型值从原来的 50 前后上移到 57–69；若 MNT-002 可读，④ 可到 75、⑥ 可到 75、⑤ 可到 87 以上；⑤ 可能超过需求带的 65；
- 这是**检测能力恢复**的结果，不是误报：Shamiko 只能 unmount 应用侧，MNT-003 仍能看到与 system_server 的视图差异；LSPosed 的模块映射仍会留下 ZYS-004。
- 若要把 ⑤ 拉回 35–65，应先确认是否存在真实误报（看 raw），而不是调低权重。

### 6.5 根因四：快速模式改变报告形状

- 快速模式跳过 MNT-002/003/006 与 BPF-003，`counts.total` 变为 **47**（沙箱开启）或 **45**（沙箱关闭），报告里这 4 项**不存在**（不是 `available=false`）；
- 在 root 场景会因此少 25 分左右（MNT-003 缺失），所以性能测试与功能验收要分开：性能可以用快速模式，功能验收必须用完整模式；
- 记录表（§7）必须写明本次用的是哪种模式，否则分数不可比。

### 6.6 收敛前的验收替代方案

允许用「命中集合 + 元信号」而不是纯分数验收（尤其在真机基线尚未建立时）：

| 判据 | 干净设备 | Root / 隐藏环境 |
| --- | --- | --- |
| 必须**不**出现 | MNT-001～009、KSU-001～005、KRN-006/007、INJ-005、AHK-001～006、FOPS-001、ZYS-008、SEL-004/005（其中 INJ-005 在模拟器上属已知误报，见 §2.2） | — |
| 必须出现 | — | KSU-001（root 本体可见时）或 MNT-003（视图隔离）或 AHK 任一 |
| 允许出现（按残留误报归档） | ZYS-001/004、INJ-001、SEL-003，且 raw 指向非 JIT memfd / ≥2 段 rwx / 大块匿名 rw | ZYS-001/004（注入痕迹）、ZYS-005/006（包列表过滤）、SEL-004 |
| 报告可信度 | `available ≥ 0.8×total`、`items` 条数正常、`durationMs` 在 0.2–2 s | 同左；若不符按 §6.7 元信号判「无法判定」 |

元信号（可用率、结果矛盾、耗时异常）的完整清单见 03 文档 §4.3。

### 6.7 元信号速查（验收时配合 §3 使用）

| 信号 | 正常 | 异常 → 处置 |
| --- | --- | --- |
| 可用率 | `available/total` 接近 1（完整模式 51/51） | 显著偏低 → 判「无法判定」，不是「安全」 |
| 反 Hook 与自校验矛盾 | `antiHook.hit=false` 且 AHK 全部可用 | AHK 某项不可用 → 自校验被短路 |
| 分数与命中数矛盾 | `hits=0 ↔ score=0`；`hits≥3 ↔ score>0` | 高 hits 低分（异常豁免）、低 hits 高分（权重被覆盖） |
| 耗时 | 完整模式数百毫秒、有梯度 | <50 ms 且 items 少 → 被短路；>5 s → 熔断/干扰 |
| items 条数 | 完整 51（未开 disabled）；快速 47（沙箱开）/ 45（关） | 明显更少 → 被截断或伪造 |
| 时间戳 | 单调递增、有梯度 | 全相同或倒序 → 报告被合成/重放 |

### 6.8 1.0.1-rc 的区间变化说明

新增 10 项后区间**基本保持**，逐场景的理由如下：

| 场景 | 区间 | 是否调整 | 原因 |
| --- | --- | --- | --- |
| ①② 干净 | 0–24（典型 0–3） | 不变 | 10 项在干净设备上全部 miss，不产生任何分值（逐项依据见 §2.2） |
| ⑦ 模拟器 | 0–24（典型 0–1） | 1.0.2 起**回到典型 0–1** | INJ-005 在模拟器上改为 `available=false`（不再计 7.0）；可用项数 51 → 50 |
| ③ KSU 默认 | 84–100 | 不变 | KRN-006/007 是否命中取决于内核有没有插桩；AHK-005/006 命中时本来就在 ≥85 区间内 |
| ④⑥ Shamiko / DenyList | 30–75 | 维持 75 上界 | 口径是「不含 fops 命中」；若 FOPS-001 命中（+25.5）会整体上移（典型 57 → 约 83），此时按高危处理，不按误报撤销 |
| ⑤ 全隐藏 | 43–100 | 不变 | ZYS-007 最多 +1.2，可忽略；FOPS-001 命中时仍落在上界内 |
| ⑧ Hook 对抗 | 85–100 | 不变 | AHK-005/006 与既有 AHK 共用 `antihook/strong` 桶（n 封顶 3），只把 72.19 抬到约 90.9，仍被 85 下限覆盖 |

一句话口径：**新项抬的是「隐藏得不够彻底」那部分证据，不会抬高干净设备的基线**。凡是新项在干净设备上命中，都应先按误报排查（02 文档 §2.1、§2.3、§2.5、§2.6、§2.8、§2.9 已逐项列了误报源）。

耗时区间也未调整：`rasp_check_extra()` 的静态估算为 10–80 ms（该模块自带 2500 ms 预算），落在既有 300–800 ms 区间内；若某机型明显上移，先看报告 `durationMs` 是否接近该模块预算（触发熔断）。

### 6.9 1.0.2 判据变更对预期分数的影响（2.0.0-beta 重算口径）

1.0.2 改了 **6 处判据 / 可用性判定**（逐项清单见 `docs/01` §0.3）。对本文 8 个场景的影响是
**「区间不变、噪声与可用项数变化」**，逐条如下：

| 变更 | 对分数的影响 | 对区间 / 口径的影响 |
| --- | --- | --- |
| `INJ-005` 模拟器改 `available=false` | ⑦ 去掉最多 7.0 分噪声 | ⑦ 典型值回到 0–1；**可用项 51 → 50** |
| `AHK-006` 改连续两轮复测 | ①② 偶发假阳性（曾 +27.6 并触发 85 下限）几乎消除 | ①② 上界更稳；⑧ 不变（仍 ≥85） |
| `KRN-007` 放行 `EACCES/EPERM` | 加固 ROM 上少 5.5 分噪声 | ①② 典型值下移，区间不变 |
| `ZYS-007` 词表收紧 | 少 1.2 分噪声（弱线索） | 不变 |
| `BPF-004` 修正 `available` | 分数不变（该项本就 `hit=false`） | **可用项数统计变准**（不再虚高） |
| `MNT-001` 补发占位 | 分数不变 | 覆盖率由「5 项静默缺席」变为「5 项显式不可用」 |

> **怎么用这张表**：手上若有 1.0.1 时代的真机报告，**不要把它的分数直接和 2.0.0-beta 对比**。
> 先比 `counts.available`（模拟器上少 1），再比 `hit` 集合（`INJ-005` 会从 `hit` 变成 `unavailable`）。
>
> **并且必须重申**：本文所有区间仍是**静态推算，不是实测**。1.0.2 / 1.0.3 的判据改动只调整了
> 「噪声口径」，目前**没有任何一台设备上的实测分布**来验证这些区间。见 §6.1 与 `docs/05` §5。
