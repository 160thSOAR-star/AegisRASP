# 01 检测项清单（RASP 本地检测 · Android 15 / API 35 · 1.0.1）

## 0. 平台定位

- **运行形态**：普通应用进程（`untrusted_app`，uid 10xxx），无 root、无 su、无内核模块、无远程服务端。全部逻辑运行在 `rasp-detect-native` 的 native 库与 App 进程内。
- **目标环境**：Android 15（API 35）/ CloreOS15 ROM / KernelSU 内核，以及其上常见的隐藏套件组合（Shamiko、Zygisk DenyList、HideMyApplist Next、LSPosed 全隐藏、susfs 类内核态隐藏）。
- **检测项规模**：**51 项**，分 10 个类别 —— mount 8 + ksu 5 + kernel 7 + bpf 4 + zygisk 8 + inject 5 + selinux 5 + antihook 6 + sandbox 2 + **fops 1**（1.0.1 新增「文件系统视图一致性 fops」类别，目前仅 FOPS-001）。等级分布为强证据 20 / 间接证据 25 / 弱线索 6。1.0.1-rc 相对 1.0.0 新增 10 项：MNT-008/009、KRN-006/007、INJ-005、AHK-005/006、FOPS-001、ZYS-007、ZYS-008。
- **检测性质**：**只做痕迹采集与交叉校验**。不修改任何文件、属性、挂载、进程状态，不 ptrace 任何进程，不加载/卸载内核模块，不做 SafetyNet / Play Integrity 等远程校验。
- **数据通路**：Compose UI → `RaspEngine.kt` → `RaspNative.runDetect`（`rasp_jni.c`）→ 9 类 native 模块（mount / ksu / kernel / bpf / zygisk / inject / security / extra / antihook）+ clone3 沙箱 → 流式证据（每项一行 JSON）→ `rasp_score.c` 加权聚合 → 报告。ZYS-005 / ZYS-006 / ZYS-008 由 `JavaProbes.kt` 执行后经 `submitEvidence` 回注同一套聚合模型（ZYS-008 另经 `RaspNative.readProperty` 读 native 属性值）。
- **核心手段**：直调 syscall（aarch64 `svc #0` / x86_64 `syscall`，见 `rasp_syscall.h`）、`pidfd_open` + `openat`、`statx(STATX_MNT_ID)`、`statfs`（自定义 `struct rasp_statfs`，`SYS_STATFS` = aarch64 43 / x86_64 137）、`openat2`（`struct rasp_open_how`，`SYS_OPENAT2`=437）、`getdents64`（目录枚举 + `readlinkat` 按名回访）、`/proc/self/maps`、`dladdr` 地址反查 + maps 段权限校验、函数序言字节校验、`clone3` 沙箱、多路径读取比对。
- **调度模型**：`rasp_jni.c::jni_run_detect` 顺序执行 mount → ksu → kernel → bpf → zygisk → inject → security → extra → sandbox → antihook；每模块设置时间预算（mount 2500ms、ksu 2000ms、kernel 2000ms、bpf 1500ms、zygisk 2500ms、inject 2000ms、security 1800ms、extra 2500ms、sandbox 2500ms、antihook 1500ms），模块内以 `rasp_deadline_hit()` 逐项熔断；`cancelDetect()` 通过 `rasp_cancelled()` 参与熔断。其中 `extra`（`rasp_checks_extra.c`，1.0.1 新增，自带 2500ms 预算）承载 1.0.1 的 9 个 native 新项（MNT-008/009、KRN-006/007、INJ-005、AHK-005/006、FOPS-001、ZYS-007）：它们的 `category` 沿用所属类别（mount / kernel / inject / antihook / fops / zygisk），但执行阶段与预算独立于同名类模块，`CheckCatalog.kt` 里仍按类别归并展示。
- **fastMode 的真实语义**：`ctx.fast_mode` 为真时，MNT-002/003/006（跨进程 mountinfo、跨视图 stat、多路径比对）与 BPF-003（网络时延）整体跳过，KSU-001 的进程扫描上限 700 → 220，KRN-001 采样轮数 240 → 80；其余检测项照常执行，并统一受模块时间预算截断。本文各条的「调度策略」按此实现描述。1.0.1 新增的 10 项均无 `fast_mode` 分支（`rasp_checks_extra.c` 与 `JavaProbes.propertyCrossCheck` 里没有任何 fast 判定），因此全量模式下与快速模式下都执行。
- **白名单与开关**：`disabled` 中的 ID 在 `rasp_emit()` 内直接丢弃（不采集、不打分）；白名单（mount/processes/properties/kernel/oem）**不参与采集**，只在 `rasp_score.c::evidence_whitelisted()` 打分阶段生效，规则为：片段与检测项 ID 完全相等 → 显式豁免；否则片段需长度 ≥ 10、不以 `/` 开头、且不在通用进程名黑名单（system_server / zygote64 / zygote / init / surfaceflinger / servicemanager）；**强证据**另需片段长度 ≥ 14 且含 `=`、`.` 或 ` on ` 之一才允许豁免；片段之间用 `;` 分隔，因此 `overlay on /system_ext` 这类多词锚点不会被拆散。`rasp_whitelisted()` 工具函数目前无模块调用。

### 0.1 证据分级定义

| 等级 | 枚举 | 单条权重 | 判据 |
| --- | --- | --- | --- |
| 强证据 | `GRADE_STRONG`（strong） | **30** | 单一观测点即可直接证明「内核返回状态与用户态视图不一致」或「存在非系统来源的可执行代码/挂载」 |
| 间接证据 | `GRADE_INDIRECT`（indirect） | **10** | 单独看有合理解释，必须与其它观测点组合才有判别力 |
| 弱线索 | `GRADE_WEAK`（weak） | **3** | 仅作参考；`rasp_score.c` 中「仅一条弱线索命中」会把总分 ×0.5，不单独升级风险 |

打分：`score += 权重 × confidence × 0.7^n`（n 为同类别同等级已命中条数，抑制同类重复证据）；单条强证据把下限抬到 25；`anti_hook_hit` 命中直接抬到 85；>50 判 high，>20 判 suspicious。`rasp_score.c::kCategories` 共 11 个槽位：`mount / ksu / kernel / bpf / zygisk / inject / selinux / antihook / sandbox / fops / other`，1.0.1 新增的 `fops` 占据第 10 槽（`other` 仍为兜底），未登记的类别名一律落入 `other`，因此 `fops` 的同类衰减与其它类别互相独立。

### 0.2 `available=false` 的语义

跨进程读 `/proc/<pid>/...` 常被 **SELinux**（`untrusted_app` 读不到 init / system_server 的 mountinfo、cgroup、status 等）与 **ptrace scope / Yama**（`/proc/<pid>/exe`、`fd`、`stat` 被拒）限制。此时对应检测项会：

- 置 `available=false`（`hit=false`、`confidence=0`），
- 在 `error` 字段写明具体原因（如 `cross-process mountinfo unreadable (SELinux/ptrace scope)`），
- **不**输出「安全」结论，也**不**伪造证据。

`available=false` 的含义是「本次检测未取得该维度的证据」，绝不等于「该维度正常」。报告 `counts.available / counts.total` 可直接衡量覆盖面；无命中时 `confidence = available/total × 0.9`，覆盖度低即置信度低，需要更换环境（如可读的 Context 或更高权限的取证工具）复测。

## 1. 第 1 类：Mount Namespace 与文件视图隔离（MNT-001 ~ MNT-006、MNT-008 ~ MNT-009、FOPS-001，模块预算 2500ms）

> 本章共 9 项：MNT-001 ~ MNT-006 由 `rasp_checks_mount.c` 实现（2500ms 预算，章节标题中的「模块预算」指它）；MNT-008 / MNT-009 是 1.0.1 新增项，由 `rasp_checks_extra.c` 实现、`category` 仍为 `mount`，执行阶段在 `extra`（自带 2500ms 预算）。FOPS-001 同样在 `rasp_checks_extra.c`，`CheckCatalog.kt` 中类别为 1.0.1 新增的 `fops`（文件系统视图一致性），因其观测对象正是「同一目录的枚举视图与按名访问视图」，故在本章一并说明。本章强证据 5 项（MNT-001/002/003/004、FOPS-001）、间接证据 4 项（MNT-005/006/008/009）。

### MNT-001 挂载视图自洽性校验（statx mnt_id vs mountinfo）
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：每个挂载实例在内核里都有唯一 `mnt_id`。`statx` 由内核直接返回目标的 `stx_mnt_id`，而 `/proc/self/mountinfo` 的第 1 字段同样是 `mnt_id`。两者本应一一对应，任何仅在用户态伪造 mountinfo 文本（删行、改名、改挂载点）的隐藏手段都会让「内核真实 mnt_id」在文本里找不到。
- **实现思路**：`rasp_checks_mount.c::check_self_consistency`。对 `/system`、`/system/bin`、`/system/etc`、`/vendor`、`/product`、`/data`、`/data/app`、`/proc`、`/dev` 逐一执行 `rasp_raw_statx(AT_FDCWD, path, 0, RASP_STATX_BASIC_STATS | 0x1000 /* STATX_MNT_ID */, &stx)`，再用 `id_present()` 在由 `parse_mountinfo()` 解析出的 id 集合（上限 768 个）中查找；`checked` 与 `missing` 写入 raw，`missing>0` 时命中。
- **隐藏套件留下的痕迹特征**：**mount-namespace 隔离**（每进程不同挂载视图）与 **Shamiko / Zygisk DenyList** 的「按包摘挂载」若发生在 mountinfo 生成之后（例如只过滤文本视图），必然出现 mnt_id 缺失；**procfs 视图隐藏**（对 mountinfo 做行级替换）同样触发。
- **为什么 Momo 类工具检测不到**：Momo 类工具以固定路径/来源字符串黑名单（`/data/adb`、magisk 等）匹配文本，不做「内核返回值 ↔ 文本视图」的事后交叉校验；本项的比较基准来自内核 `statx`，文本被改写即暴露。
- **性能开销 / 调度策略**：低 · 全量执行（9 次 statx，无进程枚举）。
- **环境限制**：内核 < 5.8 时 `stx_mnt_id` 恒为 0，代码跳过该路径；若全部路径都被跳过则 `checked=0` → `available=false`。另外 `/proc/self/mountinfo` 读取失败时本模块会直接输出 MNT-001 不可用并 `return`，本轮 MNT-002~006 不再产出证据。

### MNT-002 跨进程 mountinfo 结构比对（pidfd → init/system_server）
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：同一 mount namespace 下，应用进程与 init / system_server 看到的挂载条目集合在「系统分区是否 overlay/tmpfs、条目数量」上应保持稳定比例。仅对目标应用做的挂载隐藏会让本进程视图显著偏离这两个基准进程。
- **实现思路**：`rasp_checks_mount.c::check_cross_process_mount`。目标为 pid 1 与 `rasp_find_proc_pid("system_server", 512)`（找不到时回退固定 pid 1000）；读取统一走 `rasp_util.c::rasp_read_proc` → 优先 `rasp_pidfd_open_compat()` + `openat(pidfd, "mountinfo")`，失败回退 `/proc/<pid>/mountinfo`，`via_pidfd` 记入 raw。比对 `overlay_on_system`、`tmpfs_on_system` 两个布尔量与条目数比值（90%~115% 之外视为异常）。
- **隐藏套件留下的痕迹特征**：**Shamiko** 与 **Zygisk DenyList** 的按包隔离、**mount namespace 隔离**、**procfs 视图隐藏** 都会造成「本进程多/少若干条」。跨进程读取被拒绝本身就是线索，会写入 `unavailable` 字段。
- **为什么 Momo 类工具检测不到**：Momo 只在自身进程内看固定路径，没有「另一个进程的同一文件」这个基线，因此无法发现只针对本包生效的视图过滤；本项把 init / system_server 当作天然对照组。
- **性能开销 / 调度策略**：中（两次跨进程大文件读取，单缓冲区 96KB）· 全量执行，受 2500ms 预算与 `rasp_deadline_hit()` 约束。
- **环境限制**：Android 15 上 `untrusted_app` 读 init/system_server 的 mountinfo 通常 EACCES（SELinux）。两个目标都读不到时 `compared=0` → `available=false`，error 为 `cross-process mountinfo unreadable (SELinux/ptrace scope)`。

### MNT-003 同路径文件 stat 元信息跨视图比对
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：同一个系统文件经「普通路径」和「经 `/proc/self/root` 或其它进程 root 的路径」访问时必须落到同一 inode；若某条访问路径被 bind mount / overlay 重定向，`ino / dev / size` 必然分叉。
- **实现思路**：`rasp_checks_mount.c::check_cross_process_stat`。比较 `/system/bin/app_process64` 与 `/proc/self/root/system/bin/app_process64` 的 `statx` 结果（`stx_ino`、`stx_dev_major/minor`、`stx_size`）；再用 `rasp_pidfd_open_compat(system_server)` 拿到 pidfd，执行 `statx(pidfd, "root/system/bin/app_process64", ...)` 与自身结果比对，`xproc_checked` / `xproc_diff` 入 raw。
- **隐藏套件留下的痕迹特征**：**Shamiko** 的 tmpfs/overlay 覆盖 `/system`、**mount namespace 隔离**、以及任何把目标文件替换为「同路径不同 inode」的注入式伪装都会触发；**HMA Next** 本身不改文件元信息，本项对其不敏感。
- **为什么 Momo 类工具检测不到**：固定路径黑名单只比对字符串，不比 inode；本项把 `stx_dev` 与 `stx_ino` 作为身份指纹，伪装必须同时伪造内核元信息才能逃逸。
- **性能开销 / 调度策略**：低（3 次 statx + 1 次 pidfd 打开）· 全量执行。
- **环境限制**：`compared + xproc_checked == 0` 时 `available=false`（error：`no readable view for stat comparison`）。system_server 的 pidfd 路径在多数 Android 15 环境返回 EACCES，此时只剩自身两视图比对，但**不会**因此判为不可用。

### MNT-004 匿名 overlay / tmpfs 覆盖系统分区痕迹
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：正常 Android 15 的 `/system`、`/vendor`、`/product`、`/system_ext`、`/odm` 是只读 dm-verity 挂载，不会以 `overlay`/`tmpfs` 形式出现，也不会 `rw` 挂载。隐藏套件为了让模块文件「看起来不存在」，典型手法是在系统分区上叠 tmpfs 空目录或 overlay。
- **实现思路**：`rasp_checks_mount.c::check_overlay` + `parse_mountinfo` + `count_duplicate_mountpoints`。统计：系统路径上的 `overlay`、`tmpfs`；系统路径 `rw` 选项；挂载点或来源含 `/data/adb`；来源含 `KSU`/`ksu`/`magisk`/`worker`；同一挂载点重复出现（stacked mount，上限统计 192 个挂载点）。各因子置信度累加（0.5 / 0.3 / 0.4 / 0.5 / 0.3，封顶 0.95）。
- **隐藏套件留下的痕迹特征**：**Shamiko**（tmpfs over `/system`）、**KernelSU 本体**（overlay + `/data/adb` 来源）、**mount namespace 隔离**（同路径重复挂载）都会命中；**procfs 视图隐藏** 若把可疑行删干净反而使本项漏报（需靠 MNT-001 兜底）。
- **为什么 Momo 类工具检测不到**：Momo 类工具只按「来源字符串是否为 magisk」这类单条件匹配；本项同时看文件系统类型、挂载选项、重复挂载点与来源四类信号并按权重合成，且与 MNT-001 的 mnt_id 校验互为兜底。
- **性能开销 / 调度策略**：低 · 全量执行（本项不设 available 分支，只要 mountinfo 解析成功就输出）。
- **环境限制**：只要 `parse_mountinfo` 拿到内容就 `available=1`；极端情况下 mountinfo 被替换为空文件会得到 `mount_entries=0` 且全部因子为 0（不命中），此情形由 MNT-001/MNT-006 负责暴露。

### MNT-005 挂载点 propagation 属性异常
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：Android 常规挂载的 `shared:` propagation 标记很少，且几乎不出现在系统分区上。若系统分区或 `/data` 出现 `shared:N`，并伴随系统分区 `rw`/`tmpfs`/`overlay`，说明有进程在做跨 namespace 的挂载传播（shadow mount 的常见前置条件）。
- **实现思路**：`rasp_checks_mount.c::check_propagation`。在 `parse_mountinfo` 阶段统计挂载选项含 `shared:` 的条目数（`shared_prop`）并记录示例；命中条件为 `shared_prop > 0 && (rw_system || tmpfs_on_system || overlay_on_system)`，置信度固定 0.5。
- **隐藏套件留下的痕迹特征**：**mount namespace 隔离**、**Shamiko** 的挂载重组会留下 propagation 标记；**syscall 劫持 / kprobe hook / bpf 视图篡改** 与本项无关（它们不改挂载属性）。
- **为什么 Momo 类工具检测不到**：propagation 需要解析 mountinfo 第 7 字段之后的可选字段；Momo 类工具通常只比对第 5/6 字段（挂载点、选项）里的关键字，不解析 propagation 语义。
- **性能开销 / 调度策略**：低 · 全量执行（与 MNT-004 共用一次解析）。
- **环境限制**：无可用性分支（`available` 恒为 1），但如果 mountinfo 被整体伪造，本项与 MNT-004 会同时静默。

### MNT-006 多路径读取一致性（mountinfo / mounts / raw + libc）
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：同一份 `/proc/self/mounts` 用「直调 syscall」与「libc 的 `open/read`」读取应当字节一致；`mounts` 与 `mountinfo` 的行数也应保持稳定比例（80%~125%）。前者暴露 **libc 层 inline hook**，后者暴露两套 procfs 输出被差异化篡改。
- **实现思路**：`rasp_checks_mount.c::check_multi_path`。`rasp_read_file_raw("/proc/self/mounts")`（`rasp_raw_open/read`）与 `rasp_read_file_libc`（libc `open/read`）双读，长度或内容不等即 `divergence`；`mounts_lines` 与 `mountinfo_lines` 比值越界即 `count_gap`。
- **隐藏套件留下的痕迹特征**：**syscall 劫持**（hook libc 的 open/read 或 `syscall()` 包装）直接造成两路读取分叉；**procfs 视图隐藏** 会导致 mounts 与 mountinfo 行数比例失衡；**Shamiko** 若只过滤其中一种视图也会触发。
- **为什么 Momo 类工具检测不到**：Momo 用 libc 单路径读取，天然看不到「同一文件两种读法不一致」；本项把「实现路径差异」本身当作观测对象。
- **性能开销 / 调度策略**：低（两次 48KB 读取 + 行数统计）· 全量执行。
- **环境限制**：`available` 恒为 1；若两路读取都失败则 `mounts_lines=0` 且不命中（无 error 标记），结论由 MNT-002 的不可用状态共同表达。

### MNT-008 挂载只读标志与 statfs 一致性
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：mountinfo 第 6 字段的挂载选项（`ro` / `rw`）与内核对同一挂载点返回的 `statfs.f_flags & ST_RDONLY` 描述的是同一事实：这个挂载实例当前是不是只读。只改写 mountinfo 文本（把 `rw` 美化成 `ro`，让被 overlay/tmpfs 覆写的系统分区「看起来」仍然只读）不会改变内核 `statfs` 的返回值，两个来源必然分叉。
- **实现思路**：`rasp_checks_extra.c::check_statfs_flags`。`rasp_read_file_raw("/proc/self/mountinfo")` 一次读入 96KB 静态缓冲，`mountinfo_lookup()` 按第 5 字段（挂载点）精确匹配目标路径并解析第 6 字段，`opts_is_readonly()` 只看首个 token（`ro`/`rw` 后必须紧跟 `,` 或行尾，避免把 `relatime` 之类误判）；再对 `/system`、`/vendor`、`/product`、`/system_ext` 逐个 `rasp_raw_statfs()`（直调 `SYS_STATFS`，aarch64 43 / x86_64 137，结构体为自定义 `struct rasp_statfs`，避开 bionic 布局差异），取 `f_flags & RASP_ST_RDONLY` 作为实际值。期望值与实际值不等即 `mismatched++`，`checked` / `mismatched` / `detail`（形如 `/system(mount=ro,statfs=rw);`）写入 raw，置信度 0.6。
- **隐藏套件留下的痕迹特征**：**procfs 视图隐藏**（把系统分区选项统一改写成 `ro` 以掩盖 overlay/rw 覆盖）最典型；**Shamiko** 的 tmpfs 覆盖若只改文本选项、不动真实挂载标志同样命中；**syscall 劫持** 若只包装 `open`/`read` 伪造 mountinfo 文本（而 `statfs` 走另一条 syscall）也会分叉。**mount namespace 隔离** 只改挂载集合、不改单点只读标志时不命中（由 MNT-001 / MNT-004 负责）。
- **为什么 Momo 类工具检测不到**：Momo 类工具只在 mountinfo 文本里 grep 关键字，从不把「文本里写的 ro/rw」与「内核 `statfs` 返回的标志位」对照；本项的比较基准来自内核当次系统调用，文本被美化即暴露。
- **性能开销 / 调度策略**：低（1 次 mountinfo 读取 + 最多 4 次 statfs）· 全量执行，无 `fast_mode` 分支，受 `extra` 模块 2500ms 预算与 `rasp_deadline_hit()` 约束（本项是 `extra` 的第一项，`check_statfs_flags` 在入口处无条件执行）。
- **环境限制**：mountinfo 读不到 → `available=false`（`cannot read mountinfo`）；某路径在 mountinfo 中无对应条目、选项首 token 既非 `ro` 也非 `rw`、或 `statfs` 失败 → 该路径跳过；全部路径都被跳过时 `checked==0` → `available=false`（`no mount point available for statfs`）。`/product` 合入 `/system` 的 ROM 只是样本变少，不误报。

### MNT-009 挂载设备号与 statx 设备号一致性
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：文件的 `stx_dev_major/minor` 由内核按「该文件实际所在的挂载实例」给出，而 mountinfo 第 3 字段（`major:minor`）登记的是该挂载点绑定的设备号。正常设备上二者相等；一旦发生覆盖式挂载（叠加新文件系统但挂载表仍保留旧条目）或命名空间切换，就会出现「文件所在设备」与「挂载表登记设备」脱节。
- **实现思路**：`rasp_checks_extra.c::check_mount_dev`。三个探针：`/system/bin/app_process64`（挂载点 `/system`）、`/system/build.prop`（`/system`）、`/product/build.prop`（`/product`）。先 `rasp_raw_statx(AT_FDCWD, path, 0, RASP_STATX_BASIC_STATS, &stx)` 取 `stx_dev_major/minor`，再 `mountinfo_lookup()` 取该挂载点条目的第 3 字段，按 `:` 切分后 `strtoull` 得 `dev_major/dev_minor`。两者任一不等即 `mismatched++`，`detail` 记 `path(statx=M:m,mount=M:M);`，置信度 0.65。
- **隐藏套件留下的痕迹特征**：**overlay / bind 覆盖式挂载**（同一挂载点叠了新 fs，文本仍描述旧设备）最典型；**mount namespace 隔离** 在 `setns` 之后自身视图与挂载表登记不同步时命中；**procfs 视图隐藏** 若改写了 `major:minor` 列同样分叉。**Shamiko** 的 tmpfs 空目录覆盖会引入新的匿名设备号，通常也会命中。
- **为什么 Momo 类工具检测不到**：黑名单工具只比对路径与来源字符串，不看设备号；本项要求「文件实际所在设备」与「挂载表登记设备」对齐，改写任一列都会暴露。
- **性能开销 / 调度策略**：低（3 次 statx + 复用 1 次 mountinfo 读取）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：mountinfo 读不到 → `available=false`（`cannot read mountinfo`）；探针 statx 失败或该挂载点在 mountinfo 中无条目 → 跳过；`checked==0` → `available=false`（`no comparable device number`）。btrfs / erofs 等按 subvolume 分配不同 device 的布局、以及 `/product` 合入 `/system` 的 ROM 可能造成样本错配，故只给间接等级。

### FOPS-001 目录枚举与直接访问不一致（procfs 目录过滤）
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：`getdents64`（目录项枚举）与「按名字直接 `readlinkat`」是两条独立的 VFS 路径。若隐藏套件只 hook `readdir` / `getdents64`，把某些目录项从枚举结果里滤掉，那么「目录里看不到、但按名字仍能访问」的条目就会残留——这是目录级过滤的固有破绽。`/proc/self/fd` 里的数字 fd 是最容易验证的载体：编号空间固定（0..511），且每个条目都能用 `readlinkat` 单独回访。
- **实现思路**：`rasp_checks_extra.c::check_dir_filter`。`rasp_raw_open("/proc/self/fd", O_RDONLY|O_DIRECTORY|O_CLOEXEC)` 拿 dirfd，循环 `rasp_raw_getdents64()`，把纯数字名字 `atoi` 后置位 `listed[512]` 并累计 `listed_count`；随后对 `0..511` 中**每一个未列出**的编号，用 `rasp_raw_readlinkat(dirfd, "<n>", ...)` 直接访问，返回长度 >0 即 `hidden++`，首个例子写成 `fd N hidden from readdir -> <target>` 存入 `detail`。`hidden > 0` → 置信度 0.85，`listed_entries` / `hidden_entries` / `detail` 入 raw。
- **隐藏套件留下的痕迹特征**：**procfs 视图隐藏 / 目录级过滤**（只 hook `readdir` 以藏掉 fd、pid、task 目录项）最典型；**LSPosed 全隐藏** 若用目录过滤隐藏模块自身 fd 会命中；**内核态目录项过滤补丁**（只在 `iterate_shared` 里做过滤、不接管 readlink 路径）同样命中——这是本项相对纯用户态检测的额外覆盖面。
- **为什么 Momo 类工具检测不到**：黑名单工具「列目录看到什么算什么」，不会有「拿未列出的名字反过来访问」这一步；本项把枚举结果与按名访问互为对照，过滤器只要漏掉一条就暴露，且不依赖任何名字黑名单。
- **性能开销 / 调度策略**：低（1 次目录遍历 + 最多 512 次 `readlinkat`，绝大多数编号会以 ENOENT 快速返回）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：`/proc/self/fd` 打不开 → `available=false`（`cannot open /proc/self/fd`）；其余情况 `available` 恒为 1。fd 编号天然稀疏（打开过又关闭的号段），按名访问返回 ENOENT 不计入 `hidden`，因此稀疏不会误报；扫描上限 512 意味着编号 ≥512 的 fd 不在覆盖范围（fd 号按「最小可用」分配，正常 App 同时打开的 fd 通常远低于 512，但长期运行后编号可能累积到更高值，这部分不覆盖）。

> MNT-007 编号上属于挂载类，但实现位于 `rasp_sandbox.c`（与 SBX-001 同一次 clone3 沙箱运行），`CheckCatalog.kt` 中类别标注为 `sandbox`，故在第 9 章与 SBX-001 一并说明。

## 2. 第 2 类：KernelSU 本体与进程痕迹（KSU-001 ~ KSU-005，模块预算 2000ms）

> 本章共 5 项，全部由 `rasp_checks_ksu.c` 实现（2000ms 预算）：强证据 2 项（KSU-001/004）、间接证据 3 项（KSU-002/003/005）。1.0.1 未改动本章，KSU-001 ~ KSU-005 的实现与判据保持不变。

### KSU-001 ksud 守护进程间接特征（cmdline/comm 特征匹配）
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：KernelSU 的用户态守护进程（ksud）与隐藏套件的常驻进程必须存在于某处；即使二进制改名，`comm`（内核 task 名）与 `cmdline`（argv 拼接）通常仍保留族特征。有界枚举 `/proc` 即可采集这两个字段。
- **实现思路**：`rasp_checks_ksu.c::check_ksud_process`。`rasp_util.c::rasp_scan_procs(entries, 600, 700)` 有界枚举（完整模式最多 700 个 pid、快速模式 220 个，保留 600 条），逐条对 `comm` 与 `cmdline` 做 `rasp_contains_ci()` 匹配特征表 `kSuspiciousNames`：`ksud, kernelsu, ksu_, shamiko, zygiskd, zygisk, lspd, lsposed, magiskd, apd, susfs, hide_, tricky, riru, edxp, memfd:`；跳过自身 pid，命中项最多保留 16 个并补读 `/proc/<pid>/stat`。置信度 0.92。
- **隐藏套件留下的痕迹特征**：**KernelSU** 的 ksud、**Shamiko / zygiskd**、**LSPosed（lspd）**、**HMA Next**（常以隐藏/随机名驻留，落到 `hide_`/`memfd:` 特征）均可能命中；**procfs 视图隐藏** 若把该 pid 目录整体摘除，本项会漏，但 KSU-003 的父链与 MNT-002 的跨进程视图仍可能暴露。
- **为什么 Momo 类工具检测不到**：Momo 只匹配少量固定进程名与固定路径，且不区分「进程在不在」与「进程可见不可见」；本项做有界全表扫描并保留原始 `pid/comm` 明细，便于和 KSU-002/003 交叉，不依赖单一名字。
- **性能开销 / 调度策略**：中（完整模式最多 700 个 pid × 3 次 procfs 读取，快速模式 220 个）· 全量执行，受 2000ms 预算熔断；预算耗尽时后续 KSU-002~005 跳过。
- **环境限制**：`rasp_scan_procs` 打开 `/proc` 失败或 `n=0` → `available=false`（error：`cannot enumerate /proc`）。

### KSU-002 进程组与会话 ID 异常
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：正常 zygote 派生的应用进程 `pgrp` 与 `session` 非 0；被注入或经异常路径 fork 出来的进程可能出现 `pgrp=0`/`sid=0`。这是对 KSU-001 命中进程的二次校验。
- **实现思路**：`rasp_checks_ksu.c::check_pgrp_sid`。对 KSU-001 收集到的进程，用 `parse_stat_pgrp_sid()` 解析 `/proc/<pid>/stat` 的 `state ppid pgrp session`（从 `)` 之后 `sscanf`），统计 `pgrp==0 || sid==0` 的数量。
- **隐藏套件留下的痕迹特征**：**Zygisk / zygiskd** 注入链、**LSPosed** 注入后产生的异常线程组可能留下 0 值；**Shamiko / HMA Next** 只做视图层隐藏，不影响本项。
- **为什么 Momo 类工具检测不到**：`pgrp/sid` 需要解析 `stat` 并区分 `comm` 中的空格，黑名单式工具通常不解析该字段，也不把「进程存在」与「进程身份合法」分开判断。
- **性能开销 / 调度策略**：低 · 全量执行；无 KSU-001 命中时本项 `suspicious_processes=0`，不产生证据价值（`available=1`、`hit=0`）。
- **环境限制**：自身进程组/会话 ID 也参与判定（读取 `/proc/self/stat` 的 pgrp/sid，为 0 则计入异常）；只读 `stat` 失败时该进程 `pgrp=sid=-1`，不计异常。

### KSU-003 父进程链异常溯源
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：App 进程的正常父进程必须是 `zygote`/`zygote64`。若父进程被改为 `init` 之外的其它进程，或祖先链上出现隐藏套件进程名，说明启动路径被重定向（典型的注入/包裹启动）。
- **实现思路**：`rasp_checks_ksu.c::check_parent_chain`。从自身 pid 起沿 `/proc/<pid>/status` 的 `Name`/`PPid` 上溯，最多 8 层，`rasp_read_proc()` 读 status；同时单独取直接父进程 `Name`，要求以 `zygote` 开头或等于 `init`；祖先命中 `kSuspiciousNames` 时置信度 0.8，仅父进程异常时 0.45。
- **隐藏套件留下的痕迹特征**：**Zygisk** 注入后父链通常仍是 zygote（本项不命中），但 **ksud 派生的包裹启动**、**LSPosed 的独立进程注入** 会留下非 zygote 父进程；**内核模块内存擦除**若抹掉的是 task 名，会让父链出现空 `Name`，同样判异常。
- **为什么 Momo 类工具检测不到**：Momo 不检查父进程链，只看包名/路径黑名单；本项校验的是「进程从哪来」，属于调用路径维度的证据，与名称伪装正交。
- **性能开销 / 调度策略**：低（≤9 次 status 读取）· 全量执行。
- **环境限制**：`chain` 为空（一次 status 都读不到）→ `available=false`（`cannot read parent chain`）。父进程 `Name` 读取失败时 `parent_anomaly` 保持 0，不误报。

### KSU-004 memfd 无文件进程检测
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：`memfd_create` 出来的可执行体在 `/proc/<pid>/exe` 上表现为 `memfd:xxx (deleted)`，磁盘上没有对应文件。无文件执行的隐藏套件/注入载荷必然留下这个符号链接特征。
- **实现思路**：`rasp_checks_ksu.c::check_memfd_process`。自身用 `rasp_raw_readlinkat(AT_FDCWD, "/proc/self/exe", ...)`；随后有界枚举 `/proc`（`rasp_scan_procs(entries, 300, 400)`），只对 `PPid == self_pid` 的直接子进程读 `/proc/<pid>/exe`，命中 `memfd:` 或 `(deleted)` 计数（上限 8）。置信度 0.85。
- **隐藏套件留下的痕迹特征**：**Zygisk** 的注入载荷、**KernelSU 模块的 memfd 执行**、部分 **HMA Next** 版本的 dex 内存加载会命中；**Shamiko** 本体不做 memfd 执行，不命中。
- **为什么 Momo 类工具检测不到**：`/proc/<pid>/exe` 的 readlink 在 Yama/SELinux 下常被拒，固定路径扫描工具直接放弃；本项明确只查自身与直接子进程（合法可读范围），把「读不到」与「读到 memfd」区分开，不靠黑名单。
- **性能开销 / 调度策略**：中（有界 400 pid 枚举 + 子进程 readlink）· 全量执行。
- **环境限制**：`available` 恒为 1；若 `rasp_raw_readlinkat` 全部失败则 `hits=0`（不判不可用），因无法区分「无 memfd」与「无权限」，结论需结合 INJ-001 的 maps 结果看。

### KSU-005 进程 fd 列表异常匿名文件检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：普通 App 的 `anon_inode:` 数量很少（eventfd、dmabuf、ion 等）。若自身 fd 表里出现 `memfd:`、`bpf` 或匿名 inode 数量异常膨胀，说明进程内被塞入了额外运行时对象。
- **实现思路**：`rasp_checks_ksu.c::check_fd_anon`。`rasp_raw_open("/proc/self/fd", O_RDONLY|O_DIRECTORY|O_CLOEXEC)` + `rasp_raw_getdents64()` 遍历，对每个数字项 `rasp_raw_readlinkat(dirfd, name)` 取目标；统计 `anon_inode`、`memfd`、`bpf`、`dmabuf`。命中：`memfd>0 || bpf>0 || anon>24`；置信度按 0.45/0.5/0.3 累加封顶 0.9。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 的模块 so 经 memfd 加载、**Zygisk** 的 bpf/anon 句柄、**bpf 视图篡改** 工具持有的 map fd 会命中；**Shamiko** 不改本进程 fd，不命中。
- **为什么 Momo 类工具检测不到**：fd 表是「进程内自证」维度，黑名单工具不枚举 `/proc/self/fd`，也不看 `readlink` 目标；本项不依赖任何名字匹配。
- **性能开销 / 调度策略**：低（单次目录遍历 + 每次 readlink）· 全量执行。
- **环境限制**：`/proc/self/fd` 打不开 → `available=false`（`cannot open /proc/self/fd`）。`anon>24` 阈值偏保守，某些厂商 ROM 的高 fd 占用可能造成误报，需要白名单或权重下调。

## 3. 第 3 类：内核态间接痕迹（KRN-001 ~ KRN-007，模块预算 2000ms）

> 本章共 7 项：KRN-001 ~ KRN-005 由 `rasp_checks_kernel.c` 实现（2000ms 预算）；KRN-006 / KRN-007 是 1.0.1 新增项，由 `rasp_checks_extra.c` 实现、`category` 仍为 `kernel`，执行阶段在 `extra`（自带 2500ms 预算）。本章强证据 1 项（KRN-004）、间接证据 4 项（KRN-001/003/006/007）、弱线索 2 项（KRN-002/005）。

### KRN-001 系统调用耗时分布统计
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：`kprobe`/`ftrace` 逐次回调、或对 `sys_getpid` 做内核态劫持，都会给每次调用增加固定或抖动开销。对同一 syscall 做数百次采样，正常分布紧凑，被 hook 的分布会出现离群点（中位数 12 倍以上且 >20µs）。
- **实现思路**：`rasp_checks_kernel.c::check_syscall_timing`。用 `rasp_mono_ns()` 包裹 `rasp_raw_syscall0(SYS_GETPID)`，采样 240 次（fastMode 80 次），`qsort` 后取 `median/p99/max/mean`，统计 `>median*12 && >20000ns` 的离群点；离群点 > 轮数/40 即命中，置信度 0.5（>轮数/12 时 0.75）。
- **隐藏套件留下的痕迹特征**：**kprobe hook** 与 **syscall 劫持** 会显著改变分布；**bpf 视图篡改** 若在 tracepoint 上挂程序也会有抖动；**Shamiko/HMA Next** 属用户态视图层，不触发。
- **为什么 Momo 类工具检测不到**：时间维度需要高频采样与统计，Momo 类工具做的是同步字符串比对，没有任何时序基线；本项不依赖任何可被伪造的文本。
- **性能开销 / 调度策略**：中（240 次 syscall + 排序，约几十 µs 级）· 全量执行；fastMode 下减至 80 轮。
- **环境限制**：`available` 恒为 1；CPU 降频、热节流、调度噪声都可能制造离群点，因此只给间接等级，不与其它项叠加升级。

### KRN-002 内核配置与版本指纹偏离
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：KernelSU/susfs 类内核常在 `version` 字符串里留下 `-ksu`/`sukisu`/`apatch` 等标记；另外 `/proc/version`、`/proc/sys/kernel/osrelease` 与 `uname(2)` 三者应描述同一内核，出现不一致说明有视图层改写。
- **实现思路**：`rasp_checks_kernel.c::check_kernel_fingerprint`。优先 `rasp_read_proc(1, "version")`，失败回退 `rasp_read_file_raw("/proc/version")`；`uname()` 取 `release` 与 `/proc/version` 中 `Linux version ` 之后的内容前缀比对；再读 `/proc/sys/kernel/osrelease` 与 `un.release` 做 `strcmp`。标记命中 0.6，release 不一致 0.7。
- **隐藏套件留下的痕迹特征**：**KernelSU 本体** 的内核标记、**susfs** 的内核字符串清理（清理后往往与 uname 不一致）会命中；**kprobe hook** 不改变字符串，不命中。
- **为什么 Momo 类工具检测不到**：Momo 只 grep `version` 中的固定关键字，不做三源（procfs / sysfs / uname）一致性比对；本项即使关键字被清掉，仍可能因 osrelease 与 uname 分叉而报警。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：三处都读不到 → `available=false`（`cannot read /proc/version`）。`/proc/1/version` 在 SELinux 下常不可读，但有 `/proc/version` 回退，一般不判不可用。

### KRN-003 task_struct 与 /proc 视图不一致
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：`/proc/self/status` 的 `Pid/Tgid/Threads` 来自内核 task_struct；直调 `getpid/gettid` 也由内核返回；`/proc/self/task` 目录项数同样是内核事实。三者互不一致说明 procfs 文本被伪造，或进程身份被替换。
- **实现思路**：`rasp_checks_kernel.c::check_task_view`。`rasp_read_proc(self_pid, "status")` 取 `Pid/Tgid/Threads`，`rasp_raw_getpid()`/`rasp_raw_gettid()` 做比对；再用 `rasp_raw_open("/proc/self/task")` + `rasp_raw_getdents64()` 数线程目录项，与 `Threads` 比较（差值 >2 视为不一致）。身份不一致 0.85，线程数不一致 0.4。
- **隐藏套件留下的痕迹特征**：**procfs 视图隐藏** 或 rootkit 式的 `/proc` 劫持会命中；**内核模块内存擦除** 若只擦 task 名而不改 pid 视图，则不命中（本项不比对 `Name`）。
- **为什么 Momo 类工具检测不到**：本项是「同一事实的三种取法」互证，Momo 只取一种；伪造文本的隐藏方式在 Momo 眼里完全正常。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：自身 status 读不到 → `available=false`（`cannot read /proc/self/status`）。`/proc/self/task` 打不开时 `task_count=-1`，跳过线程数比对。

### KRN-004 cred 结构间接行为特征
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：应用进程的 `Uid/Gid` 四元组（real/effective/saved/fs）应当全等且等于 `getuid/geteuid` 直调结果；`CapEff` 在非特权应用中应为 0。任何 cred 提权（哪怕只提升 capability）都会破坏这个等式。
- **实现思路**：`rasp_checks_kernel.c::check_cred`。从 status 解析 `Uid`、`Gid`、`CapEff`；`sscanf` 四元组后与 `rasp_raw_getuid()`/`rasp_raw_geteuid()` 比对；四元组内部不等或 `CapEff != 0` 即命中，置信度 0.9。
- **隐藏套件留下的痕迹特征**：**KernelSU 的 su 授权** 若把目标进程 cred 改成 root（或半 root），本项直接命中；**内核模块内存擦除** 若只隐藏文件不改 cred，不命中；**Shamiko/HMA Next** 不碰 cred。
- **为什么 Momo 类工具检测不到**：黑名单工具不读 `CapEff`，也不比对 real/effective 四元组；本项检测的是「权限结构本身」，与路径/包名无关，改名无法规避。
- **性能开销 / 调度策略**：低 · 全量执行（`check_cred` 在 `rasp_check_kernel_trace` 中不受 deadline 熔断，保证一定执行）。
- **环境限制**：status 读不到 → `available=false`。部分厂商 ROM 给普通应用授予 ambient capability 时可能出现非 0 `CapEff` 的误报，故该项虽为强证据，建议结合 SEL-001 一起看。

### KRN-005 内核符号表异常间接推断
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：普通应用读 `/proc/kallsyms` 通常被 `kptr_restrict` 处理成全 0 地址。若居然读到大量非 0 内核地址，说明 `kptr_restrict` 被关闭（常见于调试型 root 环境），属于环境弱信号。
- **实现思路**：`rasp_checks_kernel.c::check_kallsyms`。`rasp_read_file_raw("/proc/kallsyms")` 读前 8KB，统计行数与首字段非 0 的地址数量；再读 `/proc/sys/kernel/kptr_restrict` 入 raw。`leaked = nonzero_addr>0`，置信度 0.25。
- **隐藏套件留下的痕迹特征**：**KernelSU 的调试配置**、**kprobe hook 部署脚本** 常顺手关掉 `kptr_restrict`；**bpf 视图篡改** 不相关。
- **为什么 Momo 类工具检测不到**：Momo 不读 kallsyms（读了也多为空），没有「地址可用性」这一维度；本项价值不在精确命中，而在低成本补充环境画像。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：读不到 → `available=false`（`kallsyms not readable`），并**明确不视为异常**（普通应用读不到是正常现象）。

### KRN-006 内核时序自洽性（btime / uptime / BOOTTIME）
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：三个时间源描述同一段时间线：`/proc/stat` 的 `btime`（开机时刻，wall clock 秒）与 `CLOCK_BOOTTIME`（含休眠的开机时长）应满足 `btime ≈ 真实时间 − BOOTTIME`；`/proc/uptime` 首字段与 `CLOCK_BOOTTIME` 同源，二者应几乎相等。真实时间由 `CLOCK_REALTIME` 取得。时序由内核 timekeeping 维护，任何改写 procfs 文本（例如伪造更早的开机时刻以掩盖模块加载时间线）或 hook `clock_gettime` 的行为都会破坏这两条等式。
- **实现思路**：`rasp_checks_extra.c::check_time_sanity`。`rasp_read_file_raw("/proc/stat")` 扫 `btime ` 行 `strtoll`；`rasp_read_file_raw("/proc/uptime")` 后 `strtod` 取首值；`rasp_raw_clock_gettime(RASP_CLOCK_BOOTTIME /* 7 */, &boot)` 直调取开机时长；`rasp_now_ms()/1000`（内部为 `CLOCK_REALTIME`）作为 now。令 `est_btime = now − boottime`：`|btime − est_btime| > 8s` 记 0.45，`|uptime − boottime| > 5s` 记 0.45，累加封顶 0.9；`btime` / `boottime_seconds` / `uptime_seconds` / `btime_delta` / `uptime_delta` 全部写入 raw。
- **隐藏套件留下的痕迹特征**：**susfs 类内核态时间线伪造**（改 btime 以掩盖模块或挂载的建立时刻）最典型；**kprobe hook / syscall 劫持** 若接管 `clock_gettime` 会先破坏 uptime 等式；**procfs 视图隐藏** 只替换 `/proc/stat` 或 `/proc/uptime` 其中之一时两边立刻分叉。**Shamiko / LSPosed** 不碰时间源，不命中。
- **为什么 Momo 类工具检测不到**：黑名单工具不读 `btime`，也没有「两个时间源互相校验」的概念；本项不依赖任何可被伪造的字符串，只比较内核给出的秒级数值。
- **性能开销 / 调度策略**：低（2 次小文件读取 + 1 次 `clock_gettime` + 算术比较）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：`/proc/stat` 读不到 → `available=false`（`cannot read /proc/stat`）；`btime` 与 `uptime` 都取不到 → `available=false`（`time sources unavailable`）。8s / 5s 的容差是经验值：设备长时间休眠、用户态 NTP 校时（`settimeofday`）都会扰动 `btime` 差值，因此只给间接等级且不与其它项叠加升级。

### KRN-007 syscall 返回码语义异常探针
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：内核 syscall 的失败语义是确定的：不存在的路径返回 `ENOENT`，存在的路径打开成功。若隐藏套件把 `ENOENT` 改写成 `EACCES` / `EPERM`（「假装不存在」式过滤最常见的副作用），或让本应失败的路径「成功」，说明返回值在用户态被改写、或 procfs 条目被替换成了别的东西。
- **实现思路**：`rasp_checks_extra.c::check_errno_semantics`。5 个探针及期望：`/proc/self/__aegis_probe_noent__`（期望 `ENOENT`）、`/dev/__aegis_probe_noent__`（期望 `ENOENT`）、`/system/bin/sh`（期望成功）、`/proc/version`（期望成功）、空路径 `""`（期望 `ENOENT`）。逐个 `rasp_raw_open(O_RDONLY|O_CLOEXEC)` 并立即保存 `errno`：该成功的失败、该失败的却成功、或失败 errno 不等于期望值，都计入 `anomalies++`（成功时先 `rasp_raw_close`）；`probes` / `anomalies` / `detail`（含 label 与实测 errno）入 raw，置信度 0.55。
- **隐藏套件留下的痕迹特征**：**syscall 劫持**（包装 `open`/`openat`，把敏感路径统一改成 `EACCES` 以免泄露存在性）最典型；**procfs 视图隐藏** 若把 `/proc/version` 也一起摘掉会造成「该成功的失败」；**沙箱/容器化的精简 rootfs** 也会因路径缺失命中（这是本项的主要误报来源）。
- **为什么 Momo 类工具检测不到**：黑名单工具只判断「路径能不能打开」，不校验「失败的 errno 是不是内核该给的那一个」；本项把 errno 语义本身当作观测对象，`EACCES` 冒充 `ENOENT` 这种反取证手法在它眼里完全正常。
- **性能开销 / 调度策略**：低（5 次 open，失败路径通常立即返回）· 全量执行，且不参与 `rasp_deadline_hit()` 熔断（`rasp_check_extra` 中本项的调用未加 deadline 判断，保证这组语义探针一定跑完）。
- **环境限制**：`available` 恒为 1（本项无可用性分支），只在 raw 里给出 `probes`/`anomalies`。`/system/bin/sh` 在极少数精简镜像上缺失会以「该成功的失败」命中，属已知误报点，消费报告时应结合 MNT / INJ 类证据一起看。

## 4. 第 4 类：BPF 篡改痕迹（BPF-001 ~ BPF-004，模块预算 1500ms）

> 本章共 4 项，全部由 `rasp_checks_kernel.c` 的 bpf 段实现（1500ms 预算）：强证据 1 项（BPF-002）、间接证据 2 项（BPF-001/004）、弱线索 1 项（BPF-003）。1.0.1 未改动本章。

### BPF-001 anon_inode 异常数量统计
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：`bpf()` 创建的 map/prog 在内核里是匿名 inode，落到进程 fd 表就是 `anon_inode:bpf-map` / `anon_inode:bpf-prog`。普通应用不会有大量匿名 inode。
- **实现思路**：`rasp_checks_kernel.c::check_bpf_anon`。`rasp_raw_open("/proc/self/fd")` + `rasp_raw_getdents64()` 遍历，`readlinkat` 目标以 `anon_inode:` 开头即计数，并记录种类串（去掉前缀）；`anon > 24` 命中，置信度 0.45。
- **隐藏套件留下的痕迹特征**：**bpf 视图篡改** 工具（隐藏挂载/隐藏进程的 eBPF 程序）在加载进程内会留下 bpf anon inode；**kprobe hook** 不经 bpf 时不命中；**Shamiko** 不命中。
- **为什么 Momo 类工具检测不到**：Momo 不枚举 fd，也不识别 `anon_inode:` 前缀；本项只统计本进程，属于自证维度，不受 `hidepid` 与 SELinux 跨进程限制影响。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：`/proc/self/fd` 打不开 → `available=false`。阈值 24 是经验值，高并发 App（大量 dmabuf/eventfd）可能误报。

### BPF-002 进程 fd 中 bpf 类型匿名文件识别
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：`/proc/self/fdinfo/<fd>` 对 bpf 对象会输出 `map_type`/`prog_type` 等字段，这是内核直接给出的类型信息，无法用改名绕过。一旦在本进程出现，说明当前进程持有 eBPF 对象。
- **实现思路**：`rasp_checks_kernel.c::check_bpf_fdinfo`。遍历 `/proc/self/fd` 的数字项，逐个 `rasp_read_file_raw("/proc/self/fdinfo/<fd>")`，内容含 `bpf`/`map_type`/`prog_type` 即计入 `bpf_fds`；命中即置信度 0.9。
- **隐藏套件留下的痕迹特征**：**bpf 视图篡改**（在目标进程上下文加载过滤程序）最强命中；**kprobe hook** 若通过 `perf_event_open`+bpf 部署也命中；**Zygisk/Shamiko/LSPosed** 均为用户态方案，不命中。
- **为什么 Momo 类工具检测不到**：fdinfo 是内核结构化输出，黑名单工具既不打开展示也不解析；本项不依赖任何字符串黑名单，改名/换路径无效。
- **性能开销 / 调度策略**：中（对每个 fd 做一次小文件读取，通常 <100 个 fd）· 全量执行。
- **环境限制**：`/proc/self/fd` 打不开 → `available=false`。本项只覆盖「本进程持有 bpf 对象」，系统级 bpf 程序（由其它进程持有）不在范围内，需靠 BPF-001/BPF-004 补充。

### BPF-003 网络包处理时延异常统计
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：若在 socket 收发路径上挂了 eBPF（`cgroup/skb`、`tc`、`kprobe` on `unix_dgram_sendmsg`），本地 `AF_UNIX` 往返的尾部延迟会明显变长。用 `socketpair` 自环测量可避开网络噪声。
- **实现思路**：`rasp_checks_kernel.c::check_net_latency`。`socketpair(AF_UNIX, SOCK_DGRAM)` 后做 120 次 `send`/`recv` 往返，`rasp_mono_ns()` 计时，`qsort` 取 `median/p99/max`；`max > median*20 && max > 500000ns` 命中，置信度 0.3。
- **隐藏套件留下的痕迹特征**：**bpf 视图篡改** 的 socket 层过滤、**kprobe hook** 挂在 unix socket 路径上会命中；**syscall 劫持** 若只改返回值不增加延迟，则不明显。
- **为什么 Momo 类工具检测不到**：需要本地微基准与时序统计；Momo 类工具没有任何延迟基线，也不构造自环流量。
- **性能开销 / 调度策略**：中（120 次往返）· 全量执行，受 1500ms 预算约束。
- **环境限制**：`socketpair` 失败或收发失败 → `available=false`。低端机、CPU 调频、GC 抖动都可能造成离群，故只给弱线索且不单独升级。

### BPF-004 cgroup 视图跨进程比对
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：cgroup v2 下，进程的 cgroup 层级路径由内核维护。若对本进程的 cgroup 视图做了隐藏/伪造（常见于「隐藏 root 痕迹」的内核补丁），层级行数会与 init 进程的基线不一致。
- **实现思路**：`rasp_checks_kernel.c::check_cgroup_view`。`rasp_read_proc(self_pid, "cgroup")` 与 `rasp_read_proc(1, "cgroup")` 分别读取，用 `rasp_count_lines()` 比对层级数量，不等即 `differ`，置信度 0.4。
- **隐藏套件留下的痕迹特征**：**procfs 视图隐藏**（只对本包过滤 cgroup 行）、**mount namespace 隔离** 带来的 cgroup 挂载差异会命中；**Shamiko/HMA Next** 通常不碰 cgroup，不命中。
- **为什么 Momo 类工具检测不到**：需要 init 的 cgroup 作为对照，黑名单工具没有跨进程基线；本项比较的是结构行数而非字符串，改写路径名无效。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：自身 cgroup 读不到 → `available=false`；**init 的 cgroup 读不到时实现仍输出 `available=1`**，只在 `error` 字段标注 `init cgroup unreadable (SELinux scope)` —— 这是已知的语义降级点，消费报告时应同时看 `error` 字段。

## 5. 第 5 类：Zygisk / Shamiko / LSPosed / HMA（ZYS-001 ~ ZYS-008，模块预算 2500ms）

> 本章共 8 项：ZYS-001 ~ ZYS-004 由 `rasp_checks_zygisk.c` 实现（2500ms 预算）；ZYS-005 / ZYS-006 / ZYS-008 是 Java 层探针（`JavaProbes.kt`，在 native 之前执行并经 `submitEvidence` 回注）；ZYS-007 是 1.0.1 新增的 native 项，由 `rasp_checks_extra.c` 实现、`category` 仍为 `zygisk`。本章强证据 2 项（ZYS-003/004）、间接证据 5 项（ZYS-001/002/005/006/008）、弱线索 1 项（ZYS-007）。

### ZYS-001 Zygote 注入间接痕迹检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：正常 App 的 maps 不应出现 `rwx` 段、不应有超过 3 个匿名可执行段、不应有**非 JIT** 的 memfd 可执行段或 `(deleted)` 可执行段，路径里也不应出现 `/data/adb/`、`zygisk`、`riru`、`lspd`、`edxp`。
- **实现思路**：`rasp_checks_zygisk.c::check_zygote_injection` → `rasp_memory.c::rasp_maps_stats`（解析 `/proc/self/maps`，统计 `rwx`、`anon_exec`、`memfd_exec`、`deleted_exec`、`suspicious_path`、`art_writable`、`big_anon_rw`）。ART 的 JIT 代码缓存本身就是 `memfd:jit-cache` 映射，统计时排除路径含 `jit`/`dalvik`/`boot.art`/`boot.oat` 的映射，避免干净设备误报。命中条件 `rwx>1 || anon_exec>3 || memfd_exec>0 || deleted_exec>0 || suspicious_path>0`，置信度按 0.55/0.30/0.50/0.45/0.70 累加封顶 0.95。
- **隐藏套件留下的痕迹特征**：**Zygisk**（注入 zygote 后把模块 so 映射进每个 App）、**LSPosed 全隐藏**（模块代码段可写）、**HMA Next**（若以 native 模块加载）会命中；**Shamiko** 只做挂载/视图层，通常不命中本项。
- **为什么 Momo 类工具检测不到**：Momo 读 maps 只找固定 so 名；本项同时看权限位（`rwx`）、匿名可执行段数量与来源路径前缀，模块改名/搬路径仍会因 `rwx` 或匿名可执行段暴露。
- **性能开销 / 调度策略**：中（解析一次 maps，上限 1024 条）· 全量执行。
- **环境限制**：maps 读不到 → `available=false`。部分加固/热修复框架也会产生匿名可执行段，故本项为间接等级。

### ZYS-002 Zygisk native bridge 异常检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：Zygisk 依赖替换 native bridge（`ro.dalvik.vm.native.bridge`）在 zygote 阶段获得执行权。正常设备该属性为空或 `0`，且 bridge 相关 so 只应从 `/system`、`/apex` 加载。属性非 0、或 bridge so 出现在非系统路径，都是强指向。
- **实现思路**：`rasp_checks_zygisk.c::check_native_bridge`。`__system_property_get` 读 `ro.dalvik.vm.native.bridge` 与 `persist.sys.nativebridge`；`rasp_maps_find_module()` 查 `libnativebridge.so`/`libhoudini.so`/`libndk_translation.so`；`rasp_maps_load()` 遍历 maps，bridge 路径不以 `/system/`、`/apex/` 开头即 `bridge_off_system`；`rasp_maps_stats()` 的 `art_writable`（仅统计 libart.so 中同时 `w+x` 的段）作为附加信号。
- **隐藏套件留下的痕迹特征**：**Zygisk** 本体、**Zygisk DenyList** 的部署痕迹会改 bridge 属性或路径；**Shamiko** 依赖 Zygisk，间接相关；**LSPosed 全隐藏** 若通过 zygisk 生效也相关。
- **为什么 Momo 类工具检测不到**：Momo 只读 `ro.dalvik.vm.native.bridge` 一个属性值；本项把属性与「so 实际加载路径」「libart 是否可写」三路合并，改属性值但保留注入仍需在 maps 里露出路径。
- **性能开销 / 调度策略**：低（2 次属性读取 + 2 次 maps 解析）· 全量执行。
- **环境限制**：`available` 恒为 1；arm64 设备上 `libhoudini` 等缺失是正常现象（只作为 raw 输出，不计命中）。属性读取依赖 `__system_property_get`，若该符号被 hook，可用 AHK-001 交叉发现。

### ZYS-003 Shamiko 挂载隔离特征
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：Shamiko 的核心手法是「对指定包隐藏挂载」：用 tmpfs 覆盖 `/system` 相关目录、把 `/data/adb` 相关挂载摘掉、让系统挂载出现 `size=0`、或在来源里留下 `worker`/`KSU`。
- **实现思路**：`rasp_checks_zygisk.c::check_shamiko`。逐行扫描 `/proc/self/mountinfo` 文本，计数：` - tmpfs ` 且挂载点含 ` /system| /vendor| /product`；来源含 `worker`；来源含 `KSU/ksu`；系统挂载含 `size=0`；出现 ` /data/adb`。置信度按 0.55/0.6/0.7/0.3/0.4 累加封顶 0.95。
- **隐藏套件留下的痕迹特征**：**Shamiko** 直接命中（tmpfs over system / `/data/adb` 摘除）；**Zygisk DenyList** 的原始实现也会摘挂载；**mount namespace 隔离** 造成同包视图差异同样命中。
- **为什么 Momo 类工具检测不到**：Momo 用固定挂载点黑名单（`/data/adb`、magisk）匹配；本项额外看 `size=0`、来源 fragment（`worker` 是 Shamiko/KSU 的典型名字）与文件系统类型组合，能覆盖「已改名但仍用 tmpfs 覆盖」的实现。
- **性能开销 / 调度策略**：中（读取并逐行解析 128KB mountinfo）· 全量执行。
- **环境限制**：mountinfo 不可读 → `available=false`。若隐藏方案把可疑行彻底删除且不改 tmpfs 结构，本项可能漏报，由 MNT-001/MNT-004 兜底。

### ZYS-004 LSPosed 方法 Hook 间接特征
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：LSPosed 的 native 侧必然把模块 so 映射进目标进程，且为支持运行时 hook 常出现 `rwx` 段或 `libart.so` 代码段可写（`art_writable>0`，仅统计同时 `w+x` 的段）。这些是内核维护的映射权限，用户态改名无效。
- **实现思路**：`rasp_checks_zygisk.c::check_lsposed`。`rasp_maps_load()` 遍历 maps，路径含 `lspd`/`lsposed`/`edxp`/`xposed`/`riru` 计 `module_hit`；再取 `rasp_maps_stats()` 的 `rwx`（阈值 >1）与 `art_writable`。置信度 0.85 / 0.45 / 0.6 累加封顶 0.95。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏**（模块自改名，但 `art_writable` 仍在）、**EdXposed/Riru** 遗留、**Zygisk** 注入导致的可写代码段都会命中；**HMA Next** 纯 Java 层过滤不命中（其 native 部分视版本而定）。
- **为什么 Momo 类工具检测不到**：Momo 只按 so 名匹配（`lspd`/`riru`）；本项增加「libart 段是否可写」这一与名字无关的权限事实，改名后仍会被 `art_writable` 抓住。
- **性能开销 / 调度策略**：中（两次 maps 解析，每次上限 512/1024 条）· 全量执行。
- **环境限制**：maps 不可读 → `available=false`。`rwx` 段在部分 JIT/热修复场景合法，故本项虽为强证据，仍需结合 AHK-003 的代码段校验确认。

### ZYS-005 多路径应用包列表查询交叉校验
- **证据等级**：间接证据（INDIRECT / 10，Java 层实现）
- **检测原理**：**HideMyApplist Next**、**Shamiko 的包名过滤**、LSPosed 模块的「应用列表隐藏」都只 hook 部分查询路径。用 4 条独立路径（`getInstalledPackages` / `getInstalledApplications` / `queryIntentActivities(MAIN+LAUNCHER)` / `getPackagesForUid`）取集合，任何两条不一致即说明其中一条被过滤。
- **实现思路**：`JavaProbes.kt::packageMultiPath`。计算 `hiddenFromInstalled = launcher - installed`、`appsMissing = installed - apps`、`appsExtra = apps - installed`；命中置信度 0.65，随后由 `RaspEngine.kt` 经 `RaspNative.submitEvidence` 提交，`rasp_util.c::rasp_ingest_external` 转成同一结构的证据并进 `rasp_score.c` 打分。
- **隐藏套件留下的痕迹特征**：**HMA Next**（启动器可见但 PackageManager 列表不可见）最典型；**Shamiko** 的 `DenyList` 配套包名隐藏也会造成 `installed` 与 `apps` 分叉；**LSPosed 全隐藏** 若 hook `getInstalledPackages` 命中。
- **为什么 Momo 类工具检测不到**：Momo 只查固定包名是否存在于列表，不比对不同 API 的返回集合；本项不需要预先知道「隐藏了谁」，只要求四条路径互相自证。
- **性能开销 / 调度策略**：中（4 次 Binder 查询，返回列表可能上千条）· 全量执行（Java 层在 native 之前运行）。
- **环境限制**：`getInstalledPackages` 抛异常 → `available=false`（error 为异常 message）。`queryIntentActivities` 在 Android 11+ 的包可见性限制下可能返回不完整集合，从而造成 `hiddenFromInstalled` 误报；这是本项只评间接等级的原因。

### ZYS-006 Binder 调用结果一致性校验
- **证据等级**：间接证据（INDIRECT / 10，Java 层实现）
- **检测原理**：隐藏套件 hook 的是上层 Java 门面（`PackageManager`），很少同时改 `IPackageManager` 的原始 binder 事务。直接走 `ServiceManager.getService("package")` 拿 binder 再 `asInterface` 查询，与门面结果比对即可暴露差异。
- **实现思路**：`JavaProbes.kt::binderConsistency` / `queryPackagesViaBinder`。反射 `android.os.ServiceManager.getService("package")` → `IPackageManager$Stub.asInterface` → `getInstalledPackages(0L, userId)`（`userId = Process.myUid()/100000`），返回类型兼容 `ParceledListSlice.getList()` 与 `List` 两种；与 `pm.getInstalledPackages(0)` 比对 `onlyBinder`/`onlyFacade`，命中置信度 0.7。
- **隐藏套件留下的痕迹特征**：**HMA Next** 与 **LSPosed 包列表 hook** 若只改门面即命中；**Shamiko** 若在 binder 层过滤则两边一致（不命中，属预期漏报）；**Zygisk DenyList** 不碰 binder。
- **为什么 Momo 类工具检测不到**：需要绕过门面直接与 system_server 的 package 服务对话，黑名单式工具不会构造原始 binder 事务；本项比较的是同一服务的两条调用路径，与包名黑名单无关。
- **性能开销 / 调度策略**：中（一次跨进程 binder 查询 + 列表比对）· 全量执行。
- **环境限制**：反射隐藏 API 被策略拦截或返回 null → `available=false`（error：`binder direct query blocked by hidden API policy`），**不伪造结论**。Android 15 上该路径在多数配置下可用，但不同 ROM 差异较大。

### ZYS-007 异常线程名与线程注入痕迹
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：注入框架常在目标进程里创建自己的工作线程（hook 分发、payload 加载、RPC 通道），线程的内核 task 名（`comm`）往往带族特征。正常 App 的线程名来自 ART / JVM 与 bionic（`main`、`Signal Catcher`、`RenderThread`、`Jit thread pool`、`binder:*` 等），出现 `zygisk` / `lspd` / `magisk` 这类命名即为线程级注入痕迹。
- **实现思路**：`rasp_checks_extra.c::check_thread_names`。`rasp_raw_open("/proc/self/task", O_RDONLY|O_DIRECTORY|O_CLOEXEC)` + `rasp_raw_getdents64()` 枚举 tid 目录项（纯数字名），逐条 `rasp_read_proc(tid, "comm")` 读内核 task 名并裁掉行尾换行；`thread_name_suspicious()` 用 `rasp_contains_ci()` 大小写不敏感匹配 `zygisk / lspd / lsposed / riru / magisk / ksu / inject / payload / inline / hook`，命中 `suspicious++` 并记录首个 `tid=... comm=...`。`threads` / `suspicious` / `detail` 入 raw，置信度 0.4。
- **隐藏套件留下的痕迹特征**：**Zygisk**（其工作线程名常含 zygisk 字样）、**LSPosed**（lspd 线程）、**Riru / EdXposed 遗留**、**注入器的 payload / inline hook 线程** 会命中；**Shamiko** 只做挂载与视图层，不建线程，不命中。
- **为什么 Momo 类工具检测不到**：黑名单工具既不遍历 `/proc/self/task`，也不读线程 `comm`；本项只依赖内核 task 名，改 so 名、换模块路径都无效。
- **性能开销 / 调度策略**：低（1 次目录遍历 + 每线程一次 `comm` 读取，正常 App 线程数为数十量级）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：`/proc/self/task` 打不开 → `available=false`（`cannot open /proc/self/task`）；其余情况 `available` 恒为 1。`comm` 最长 15 字节且可被 `prctl(PR_SET_NAME)` 任意改写，命中率因此有限，这也是它只给弱线索的原因；合法 App 自定义线程名含 `hook`（如 `hook-worker`）时会误报，需要白名单或下调权重。

### ZYS-008 系统属性 Java/native 双路径一致性
- **证据等级**：间接证据（INDIRECT / 10，Java 层 + native 属性读取）
- **检测原理**：Java 的 `Build.MODEL` / `Build.VERSION.SDK_INT` / `Build.FINGERPRINT` 在进程启动早期由属性区快照而来，此后不再跟随属性区变化；即使有模块 hook `SystemProperties.get()`（用于伪造指纹、隐藏 test-keys），这些静态字段也不会改。native 直接读属性区（`__system_property_get`）拿到的是「当前值」。两者不一致，说明属性读取路径被拦截，或属性区在进程启动后被改写。
- **实现思路**：`JavaProbes.kt::propertyCrossCheck` + `rasp_jni.c::jni_read_property`。三组对照：`ro.product.model` ↔ `Build.MODEL`、`ro.build.version.sdk` ↔ `Build.VERSION.SDK_INT`、`ro.build.fingerprint` ↔ `Build.FINGERPRINT`；每组先 `RaspNative.readProperty(key)`（注册为 `readProperty` 的 native 方法 → `jni_read_property` → `__system_property_get`，完全绕过 Java 门面），native 值非空才 `checked++`，与 Java 值不等则记入 `diffs`。`checked==0` → `available=false`；否则 `hit = diffs.isNotEmpty()`，置信度 0.6。证据经 `RaspNative.submitEvidence` 回注，由 `rasp_util.c::rasp_ingest_external` 转成同一结构后进 `rasp_score.c` 打分。
- **隐藏套件留下的痕迹特征**：**KernelSU / susfs 的 resetprop 式属性伪装**（运行期改属性，Java 静态字段仍是旧值）最典型；**Shamiko 的属性清理**、**Xposed 模块 hook `SystemProperties`** 也会命中；纯挂载层与纯目录层隐藏（不改属性）不命中。
- **为什么 Momo 类工具检测不到**：Momo 类工具只读属性的当前值（例如 `ro.build.tags` 是否 `test-keys`），没有「Java 启动快照 vs native 当前值」这个时间差维度；本项把同一属性的两个时点当作观测对象，属性值改得再干净也会与快照分叉。
- **性能开销 / 调度策略**：低（3 次 JNI 属性读取 + 3 次字符串比较）· Java 层在 native 之前执行，无 `fast_mode` 分支，可能因 native 库尚未加载而整体降级为 `available=false`。
- **环境限制**：`RaspNative.readProperty` 全部返回空或调用失败（native 库未加载成功）→ `available=false`（`native readProperty unavailable`）；单条属性返回空只跳过该条、不影响其余两条。被探测的三条 `ro.*` 属性在普通应用上下文通常可读；若个别 ROM 把它们裁掉或属性区读取被 SELinux 拒绝，结果就是「跳过」而非「异常」，因此本项不会因读不到而误报。

## 6. 第 6 类：Ptrace / 内存映射 / 注入（INJ-001 ~ INJ-005，模块预算 2000ms）

> 本章共 5 项：INJ-001 ~ INJ-004 由 `rasp_checks_inject.c` 实现（2000ms 预算）；INJ-005 是 1.0.1 新增项，由 `rasp_checks_extra.c` 实现、`category` 仍为 `inject`，执行阶段在 `extra`（自带 2500ms 预算）。本章强证据 2 项（INJ-002/003）、间接证据 3 项（INJ-001/004/005）。

### INJ-001 进程内存映射异常匿名段检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：注入的 shellcode / 加载器通常先 `mmap` 一块匿名内存再写入执行，表现为匿名可执行段、`rwx` 段或超大匿名读写段（>64MB）。
- **实现思路**：`rasp_checks_inject.c::check_maps_anomaly`。`rasp_maps_stats()` 解析 maps；命中条件 `rwx>1 || anon_exec>3 || big_anon_rw>12`，置信度 0.5/0.3/0.15 累加封顶 0.9（`big_anon_rw` 定义为 >64MB 且可写的匿名段，ART 堆常见，故阈值放宽到 12）。
- **隐藏套件留下的痕迹特征**：**Zygisk/LSPosed** 的注入载荷在无文件加载阶段会短时出现匿名可执行段；**ptrace 注入器** 留下的 RWX 段会命中；**Shamiko/HMA Next** 纯视图层不命中。
- **为什么 Momo 类工具检测不到**：注入器常用「先 RW 后 mprotect 成 RX」规避 `rwx` 检查；本项同时统计匿名可执行段数量与超大匿名读写段，覆盖「分两步映射」的实现。
- **性能开销 / 调度策略**：低（一次 maps 解析）· 全量执行。
- **环境限制**：maps 不可读 → `available=false`。ART 的 JIT 代码缓存与部分加固壳会产生匿名可执行段，故为间接等级。

### INJ-002 ptrace 后门痕迹间接检测
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：进程被 ptrace 附加时，内核会在 `/proc/<pid>/status` 把 `TracerPid` 置为跟踪者 pid，并把 `State` 置为 `t`/`T`。这是内核事实，用户态 hook 无法在不改内核的情况下伪造（除非同时改 procfs 视图）。
- **实现思路**：`rasp_checks_inject.c::check_tracer`。`rasp_read_proc(self_pid, "status")` 取 `TracerPid`、`State`、`PPid`；再对父进程读 `TracerPid` 作为旁证。`tracer_pid>0 || state 为 t/T || parent_traced` 即命中，置信度 0.95。
- **隐藏套件留下的痕迹特征**：**ptrace 注入/调试器**、部分 **Zygisk 注入器的早期阶段**、**内存 dump 工具** 会命中；**kprobe hook / bpf 视图篡改** 不改变 `TracerPid`，不命中。
- **为什么 Momo 类工具检测不到**：`TracerPid` 需要读 status 且要区分 `State` 字段；Momo 类工具多数只看 `TracerPid==0` 这一条，不看父进程旁证，也不处理 `t` 状态。本项三路取证，且与 KRN-003 的 status 一致性互为交叉。
- **性能开销 / 调度策略**：低（2 次 status 读取）· 全量执行。
- **环境限制**：自身 status 读不到 → `available=false`。父进程 status 读不到时只跳过旁证，不影响主判据。

### INJ-003 系统库函数入口完整性校验
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：inline hook 必须在函数入口写下跳转指令（aarch64 的 `B`/`BL`/`BR`，x86_64 的 `jmp`），或把入口改成 `BRK`/`int3` 断点、NOP 占位、清零。检查入口处机器码即可，同时校验地址是否仍落在对应模块的映射区间内（防 PLT/GOT 重定向到外部 trampoline）。
- **实现思路**：`rasp_checks_inject.c::check_system_lib_entries`。`dlopen("libc.so")` + `dlsym` 取 `dlsym`、`__system_property_get`、`pthread_create`、`malloc`、`JNI_GetCreatedJavaVMs` 等 6 个探针，逐个调 `rasp_memory.c::rasp_check_function_entry()`：先 `rasp_maps_find_module()` 校验地址区间，再按架构解码前 2~8 字节（aarch64 检查 `B/BL/BR/NOP/BRK/全零`，x86_64 检查 `E9/EB/FF25/CC` 与常见序言白名单）。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 的 PLT hook、**Zygisk** 的 inline hook、**syscall 劫持**（hook libc 的 `syscall`/`open`）都会命中；**Shamiko** 不 hook libc 函数，不命中。
- **为什么 Momo 类工具检测不到**：Momo 不做函数序言字节校验，也不校验「函数地址是否仍在原模块区间」；本项把「指令形态」与「地址归属」两个维度合并，改 so 名或换 trampoline 位置都无效。
- **性能开销 / 调度策略**：中（6 次 dlsym + 6 次 maps 查找 + 6 次内存读）· 全量执行。
- **环境限制**：`checked==0`（所有探针都无法定位模块）→ `available=false`（`no probeable system library`）。ARM64 上 `libart.so` 的 `JNI_GetCreatedJavaVMs` 可能实际来自 `libnativehelper.so`，代码对两者都做了探测。

### INJ-004 Dex 文件匿名内存加载检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：动态加载 dex 时，ART 会把 dex/vdex/oat 映射进内存。若路径是 `memfd:` 或带 `(deleted)`，说明代码来自内存而非磁盘上的 APK——这是内存马/热修复/隐藏模块的典型形态。
- **实现思路**：`rasp_checks_inject.c::check_anon_dex`。`rasp_maps_load(maps, 1024)` 后筛出路径含 `.dex`/`.vdex`/`.oat` 的映射，统计 `anon_dex`（`memfd:` 或以 `/memfd` 开头）与 `deleted_dex`（`(deleted)`），置信度 0.65/0.5 累加封顶 0.9。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 中把模块 dex 从内存加载、**HMA Next** 的 dex 动态加载、**Zygisk 模块的 dex 注入** 会命中；**Shamiko** 不加载 dex，不命中。
- **为什么 Momo 类工具检测不到**：需要在 maps 里识别「路径形态」而非固定文件名；黑名单工具通常只搜已知模块 so 名，不检查 `memfd:`/`(deleted)` 这类来自内核的路径标记。
- **性能开销 / 调度策略**：低（一次 maps 解析，上限 1024 条）· 全量执行。
- **环境限制**：maps 不可读 → `available=false`。Android 15 的 ART 对部分 profile/oat 也会用 `(deleted)` 映射，存在误报可能，故为间接等级。

### INJ-005 非系统代码映射来源检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：本进程所有可执行映射都应来自系统分区、应用自身安装目录、dalvik-cache，或 ART 的 JIT memfd。出现其它来源的可执行段，说明有第三方代码从非常规路径被映射进来——隐藏套件的模块 so 常放在 `/data/local/tmp`、`/data/adb/modules/...` 等目录。本项只判「有路径且路径不在允许列表内」的映射；匿名可执行段（空路径）交由 INJ-001 / ZYS-001 负责，避免两个检测项重复计分。
- **实现思路**：`rasp_checks_extra.c::check_code_mapping_origin`。`rasp_maps_load(maps, 1024)` 一次解析 `/proc/self/maps`，只处理 `perms[2]=='x'` 的可执行映射（`exec_mappings`）；`code_path_allowed()` 以**允许列表**判定合法来源：`/system/`、`/apex/`、`/vendor/`、`/product/`、`/system_ext/`、`/odm/`、`/data/app/`、`/data/dalvik-cache/`、`/data/user/`、`/data/data/`、`/dev/`、`/data/misc/`、`/mnt/expand/`，路径含 `memfd:jit` 亦放行，空路径（匿名段）直接放行（交由 INJ-001 处理）。不在列表内的计入 `offlist_mappings`，首个例子（路径 + 起止地址）写入 raw，置信度 0.7。
- **隐藏套件留下的痕迹特征**：**Zygisk 模块 so 从 `/data/adb/modules/...` 映射**、**LSPosed 模块 so 从模块目录映射**、**HMA Next 的 native 库**、**从 `/data/local/tmp` 加载的注入载荷** 会命中；**memfd 无文件加载** 因路径为 `memfd:` 而非 `memfd:jit` 同样命中；**Shamiko** 不加载 so，不命中。
- **为什么 Momo 类工具检测不到**：Momo 类工具只匹配已知模块 so 名与固定目录；本项反过来用允许列表界定合法来源，任何新路径、改名的模块都会因「来源不在白名单」而暴露，不需要预先知道它叫什么。
- **性能开销 / 调度策略**：低（一次 maps 解析，上限 1024 条）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：maps 读不到 → `available=false`（`cannot read /proc/self/maps`）。允许列表本身是已知放宽点：`/dev/`（ashmem 等）与空路径都放行，因此把代码放进匿名段或 `/dev/ashmem` 的加固壳 / 热修复框架不会被本项抓到；这是它只给间接等级的原因。

## 7. 第 7 类：SELinux & AVB & 系统完整性（SEL-001 ~ SEL-005，模块预算 1800ms）

> 本章共 5 项，全部由 `rasp_checks_security.c` 实现（1800ms 预算）：无强证据，间接证据 3 项（SEL-001/004/005）、弱线索 2 项（SEL-002/003）。1.0.1 未改动本章。

### SEL-001 SELinux 域上下文异常检测
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：普通 App 的 `attr/current` 必须是 `u:r:untrusted_app*`（或 platform_app/system_app）。域变成 `su`/`magisk`/`ksu` 说明进程被提权换域，这是 root 授权生效的直接后果。
- **实现思路**：`rasp_checks_security.c::check_selinux_context`。`rasp_read_proc(self_pid, "attr/current")`，失败回退 `rasp_read_file_raw("/proc/self/attr/current")`；匹配 `untrusted_app`、`platform_app`/`system_app`、`su/magisk/ksu` 三类。非前两类即 `hit`（0.55），域含 su 特征给 0.95。
- **隐藏套件留下的痕迹特征**：**KernelSU 的 su 授权**（域切到 `u:r:su:s0`）最强命中；**Magisk** 的 `magisk` 域同样；**Shamiko/HMA Next** 不换域，不命中。
- **为什么 Momo 类工具检测不到**：Momo 只匹配 `magisk`/`su` 字符串；本项先判定「是否处于合法应用域」，再判升级域，因此对改名后的自定义域（既非 `untrusted_app` 也无 su 关键字）同样报警。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：attr/current 读不到 → `available=false`（`cannot read attr/current`）。个别定制 ROM 使用非标准但合法的应用域，可能触发 0.55 的弱命中，需白名单。

### SEL-002 SELinux 策略偏离度检测
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：`/sys/fs/selinux/enforce` 为 0 表示 permissive（策略只审计不拦截），`policyvers` 低于 30 说明策略版本异常（老旧或被替换）。两者都是「环境被放宽」的弱信号。
- **实现思路**：`rasp_checks_security.c::check_selinux_policy`。`rasp_read_file_raw` 读 `/sys/fs/selinux/policyvers`、`enforce`、`checkreqprot`；`enforce==0` 或 `policyvers<30` 命中，置信度 0.5 / 0.25。
- **隐藏套件留下的痕迹特征**：**KernelSU/susfs** 为兼容模块常临时 permissive、**自定义内核** 可能降策略版本；**Shamiko/LSPosed** 不改变 selinuxfs。
- **为什么 Momo 类工具检测不到**：Momo 不读 selinuxfs 的 `policyvers`；本项提供的是环境宽容度画像，用来解释其它项的命中可信度（permissive 下 hook 更容易存活）。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：`policyvers` 读不到 → `available=false`（`selinuxfs not readable`）。

### SEL-003 AVB2.0 校验状态检测
- **证据等级**：弱线索（WEAK / 3）
- **检测原理**：AVB 状态由 bootloader 写入 `ro.boot.*` 属性：`verifiedbootstate` 为 `green` 才是锁定的原厂状态，`orange` 表示已解锁但校验仍跑，`red` 表示校验失败；`flash.locked`、`vbmeta.device_state` 是同一事实的其它表述。
- **实现思路**：`rasp_checks_security.c::check_avb`。`__system_property_get` 读 `ro.boot.verifiedbootstate`、`ro.boot.flash.locked`、`ro.boot.vbmeta.device_state`、`ro.boot.veritymode`、`ro.boot.warranty_bit`、`ro.boot.vbmeta.digest`；`orange/red`、`locked!=1`、`device_state=unlocked` 命中，置信度 0.7/0.55/0.4。
- **隐藏套件留下的痕迹特征**：**KernelSU 刷机** 后必然 `orange` + 解锁；**AVB 降级/自定义 vbmeta** 可能直接 `red`；**Shamiko/HMA Next** 不改变 bootloader 状态。
- **为什么 Momo 类工具检测不到**：Momo 通常不读这组属性；本项不依赖运行时 hook 痕迹，而是环境前提，因此对「已解锁但当前没装隐藏套件」的设备也会报警——这也是它只给弱线索的原因。
- **性能开销 / 调度策略**：低 · 全量执行。
- **环境限制**：`verifiedbootstate` 为空（部分模拟器/容器）→ `available=false`（`avb properties unavailable`）。`veritymode`/`warranty_bit`/`vbmeta.digest` 仅作 raw 输出，不参与命中。

### SEL-004 系统分区完整性间接校验
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：`/system`、`/vendor`、`/product` 正常应为只读挂载且非 overlay/tmpfs。出现 `rw`、`overlay`、`tmpfs` 说明系统分区被改写或覆盖。
- **实现思路**：`rasp_checks_security.c::check_system_partition`。`rasp_read_proc(self_pid, "mountinfo")` 后逐行扫描，匹配挂载点为 ` /system ` / ` /vendor ` / ` /product ` 的行，统计含 ` rw,`、` - overlay `、` - tmpfs ` 的数量；置信度 0.6/0.55/0.45 累加封顶 0.9。
- **隐藏套件留下的痕迹特征**：**KernelSU 的 overlayfs 模块挂载**、**Shamiko 的 tmpfs 覆盖**、**mount namespace 隔离** 都会命中；**HMA Next** 不碰分区挂载。
- **为什么 Momo 类工具检测不到**：Momo 只 grep 来源字符串（是否含 magisk）；本项按挂载点 + 文件系统类型 + 挂载选项三元组判定，覆盖「用非 magisk 名字做 overlay」的实现。
- **性能开销 / 调度策略**：低（一次 mountinfo 读取 + 逐行扫描）· 全量执行。
- **环境限制**：mountinfo 不可读 → `available=false`。部分 GKI 设备把 `/product` 合入 `/system`，空匹配不会误报。

### SEL-005 系统属性异常特征（属性区 vs build.prop）
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：属性区（`__system_property_get`）与磁盘 `/system/build.prop` 描述同一批构建信息。若属性区被 `resetprop` 之类的手段改写（隐藏 root 的常见动作），两边会出现不一致。
- **实现思路**：`rasp_checks_security.c::check_properties`。`rasp_read_file_raw("/system/build.prop")` 读磁盘副本，`parse_build_prop()` 逐行解析，与属性区的 `ro.build.tags`、`ro.build.version.sdk`、`ro.product.model`、`ro.build.fingerprint` 四条比对；`mismatches>0` 给 0.75 置信度。`test-keys`/`ro.debuggable=1` 只写入 raw，**不单独升级风险**（避免 userdebug 误报）。
- **隐藏套件留下的痕迹特征**：**KernelSU/susfs 的 resetprop 式属性伪装**、**Shamiko 的属性清理** 会命中；**kprobe hook / bpf 视图篡改** 不碰属性区，不命中。
- **为什么 Momo 类工具检测不到**：Momo 只读属性值本身（例如 `ro.build.tags` 是否 test-keys）；本项拿磁盘副本做对照，属性值改得再像也会与磁盘分叉。
- **性能开销 / 调度策略**：低（一次 build.prop 读取 + 4 次属性读取）· 全量执行。
- **环境限制**：`build.prop` 不可读或四条键都解析不到 → `available=false`（`build.prop not readable (scoped storage/SELinux)`）；此时本项完全静默，不推断。

## 8. 第 8 类：反 Hook 自校验（AHK-001 ~ AHK-006，模块预算 1500ms）

> 本类任意一条命中都会置 `ctx->anti_hook_hit = 1`，`rasp_score.c` 直接把总分下限抬到 85（high）。这是「检测器自身可信度」的兜底：如果检测代码被 hook，其它 45 项的证据都不再可信。其中 AHK-001 ~ AHK-004 由 `rasp_checks_antihook.c` 实现（`jni_run_detect` 末尾的 1500ms 预算段）；AHK-005 / AHK-006 是 1.0.1 新增项，由 `rasp_checks_extra.c` 实现、`category` 仍为 `antihook`，执行阶段在 `extra`（自带 2500ms 预算），命中时同样显式置 `c->anti_hook_hit = 1`。本章 6 项全部为强证据（STRONG / 30）。

### AHK-001 libc 关键函数入口完整性校验
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：检测逻辑本身要调用 libc（`open/read/mmap/__system_property_get`）。若攻击者 hook 这些函数来伪造检测结果，入口处必然出现跳转指令或地址漂移。
- **实现思路**：`rasp_checks_antihook.c::check_libc_entries`。`dlopen("libc.so")` + `dlsym` 取 `open`、`openat`、`read`、`close`、`mmap`、`__system_property_get`，逐个走 `rasp_memory.c::rasp_check_function_entry()`（模块区间校验 + 入口字节解码）；可疑即置 `anti_hook_hit`，置信度 0.95。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 的 PLT/GOT hook、**Zygisk** 的 inline hook、**syscall 劫持** 包装层都会命中；**Shamiko** 不 hook libc，不命中。
- **为什么 Momo 类工具检测不到**：Momo 没有「自我完整性」概念，也不校验函数入口字节；本项检测的是「观测工具是否还可信」，属于元检测，与任何黑名单无关。
- **性能开销 / 调度策略**：低（6 次 dlsym + 6 次内存读）· 全量执行（`rasp_check_antihook` 在 `jni_run_detect` 末尾无条件调用）。
- **环境限制**：`checked==0`（libc 符号都无法解析）→ `available=false`（`cannot resolve libc symbols`）。此时无法自证，报告应视为低可信。

### AHK-002 直调 syscall 与 libc 调用结果一致性校验
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：同一事实用两条路径取：直调 `svc`/`syscall`（绕过 bionic）与 libc 包装。若 libc 被 hook 而直调没有，两者必然分叉——这是识别「用户态 inline hook」最直接的判据。
- **实现思路**：`rasp_checks_antihook.c::check_raw_vs_libc`。三组比对：`rasp_read_file_raw` vs `rasp_read_file_libc` 读 `/proc/self/status`（长度 + `memcmp`）；`rasp_raw_statx("/system/build.prop")` vs libc `stat()`（`st_ino`/`st_size`）；`rasp_raw_getpid()` vs `getpid()`。任一分叉即置 `anti_hook_hit`。
- **隐藏套件留下的痕迹特征**：**syscall 劫持**（hook `syscall()` 或 libc 包装函数）最强命中；**LSPosed 全隐藏** 若 hook `open/read` 伪造 mountinfo 也会命中；**内核态 kprobe hook** 同时影响两条路径，反而**不**命中（这是本项的边界，需 KRN-001 兜底）。
- **为什么 Momo 类工具检测不到**：Momo 全程走 libc，没有「同一调用的另一条路径」；本项的比较基准就在同一进程内，无需外部信任根。
- **性能开销 / 调度策略**：低（2 次 status 读取 + 2 次 stat + 2 次 getpid）· 全量执行。
- **环境限制**：`(ok1 || ok4)` 为假（两条比对路径都不可用）→ `available=false`（`no readable comparison target`）。

### AHK-003 检测代码段内存完整性校验
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：如果攻击者直接改写检测函数自身的机器码（打补丁让它恒返回 0），函数入口 hook 检查可能被绕过。对自身热代码做启动时哈希快照、运行时重算，可直接发现代码段被写。
- **实现思路**：`rasp_checks_antihook.c::rasp_ahk_snapshot` 在 `JNI_OnLoad`（`rasp_jni.c`）中对 `rasp_emit` 与 `rasp_check_antihook` 各取 64 字节做 `rasp_hash64()`（FNV-1a 64）；`check_code_integrity` 运行时重算比对，并在 aarch64 上按 4 字节步进扫描 `BRK`（`0xD4200000`）指令。不一致即置 `anti_hook_hit`。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 的代码 patch、**内核模块内存擦除**（若误擦到用户态代码页）、**inline hook 的 trampoline 覆盖** 都会命中；纯数据层 hook（GOT 改写）不改代码字节，不命中（由 AHK-001 负责）。
- **为什么 Momo 类工具检测不到**：没有检测器会给自己做代码快照；本项是「检测代码是否被改」的直接证据，任何基于改代码的绕过都会留下哈希差。
- **性能开销 / 调度策略**：低（2 次 64 字节哈希 + 32 次指令扫描）· 全量执行。
- **环境限制**：`g_snap_count==0`（`JNI_OnLoad` 未执行或快照失败）→ `available=false`（`no snapshot taken`）。

### AHK-004 JNI 函数表完整性校验
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：Java 层要伪造 native 结果，最省事的方式是替换 `JNIEnv` 的函数表指针，或把关键槽位改成自己的函数。`JNIEnv*` 的第一级指针就是 `JNINativeInterface` 表，`JNI_OnLoad` 时可记录该指针，运行时比对即可发现替换。
- **实现思路**：`rasp_jni.c::rasp_jni_table_verify`（由 `rasp_checks_antihook.c::check_jni_table` 调用）。`JNI_OnLoad` 保存 `g_env_table = *(void***)env`；运行时取当前表指针，不等即 `tampered++`；再校验槽位 4（`GetVersion`）、6（`FindClass`）、31（`GetObjectClass`）指向的地址是否落在可执行映射内（`addr_executable()` 基于 maps 的 `x` 权限位）。
- **隐藏套件留下的痕迹特征**：**LSPosed 全隐藏** 的 JNI 层 hook、**Zygisk 模块替换 JNI 表** 会命中；**Shamiko** 不碰 JNI 表，不命中。
- **为什么 Momo 类工具检测不到**：JNI 表指针与槽位归属是「运行时自证」维度，黑名单工具不检查；本项在 `JNI_OnLoad` 阶段就固化基线，之后任何替换都会与基线不符。
- **性能开销 / 调度策略**：低（1 次指针比较 + 3 次 maps 查找）· 全量执行。
- **环境限制**：`available` 恒为 1；`g_vm` 为空或 `GetEnv` 失败时函数返回 0（不命中、不报不可用），属于静默降级。

### AHK-005 函数地址与可执行段一致性
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：一个合法的函数指针必须同时满足两个条件：能被 `dladdr` 反向解析到某个已加载模块（`dli_fbase != NULL`），且地址落在本进程某个 `x` 权限映射内。inline hook 若把入口改成跳到外部 trampoline、或把 `dlsym` 返回值替换成堆/匿名内存里的桩，函数地址的「来源」与「权限」就会对不上——这是与函数名、so 名都无关的物理事实。
- **实现思路**：`rasp_checks_extra.c::check_function_segment`。三个探针：`&rasp_emit`（检测器自身代码）、`dlsym(RTLD_DEFAULT, "dlsym")`、`dlsym(RTLD_DEFAULT, "open")`（libc 导出）。逐个调用 `dladdr()`，要求返回非 0 且 `info.dli_fbase != NULL`；再用 `addr_executable()`（`rasp_maps_load(maps, 512)` 后按 `start <= addr < end` 定位所属段并回读 `perms`）要求 `perms[2]=='x'`。两条件任一不满足即 `inconsistent++`，`detail` 记 `name(模块名|no-dladdr, 段权限)`；置信度 0.9，且显式置 `ctx->anti_hook_hit = 1`。
- **隐藏套件留下的痕迹特征**：**PLT/GOT 重定向到外部 trampoline**（`dlsym` 返回的地址不在 libc 的段内）、**inline hook 使用 mmap 出来的跳板**（地址落在匿名 `rwx` 段）、**LSPosed / Zygisk 对 `dladdr` 本身做 hook**（返回伪造的模块信息）都会命中。
- **为什么 Momo 类工具检测不到**：黑名单工具不做 `dladdr` 反查，也不校验「函数地址是否在可执行段」；本项把地址归属与段权限合并判定，改 so 名或换 trampoline 位置都无效。
- **性能开销 / 调度策略**：低（3 次 `dladdr` + 最多 3 次 maps 解析）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：三个探针都取不到地址（`dlsym` 全部失败）→ `checked==0` → `available=false`（`no probeable function`）。`dlsym` 被 hook 成返回假地址时会同时命中 AHK-001 与本项，属预期；对正常导出的 libc 符号，`dladdr` 即使拿不到符号名也会填出 `dli_fname` / `dli_fbase`，本项只看模块基址、不依赖符号名。

### AHK-006 openat2 与 openat 双路径一致性
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：`openat2(2)`（Linux 5.6+，`SYS_OPENAT2`=437）与 `openat(2)` 是两条独立的内核入口，打开同一个 procfs 文件必须得到字节一致的内容。隐藏套件通常只 hook libc 的 `open`/`openat` 或 `syscall()` 包装，不会同时接管 `openat2`；两条路径字节分叉即说明其中一条被改写。
- **实现思路**：`rasp_checks_extra.c::check_openat2`。构造 `struct rasp_open_how`（`flags = O_RDONLY|O_CLOEXEC`、`resolve = 0`，不启用任何 `RESOLVE_*` 语义），先 `rasp_raw_openat2(AT_FDCWD, "/proc/self/mountinfo", &how, sizeof(how))`，再 `rasp_raw_open("/proc/self/mountinfo", ...)`，各自 `rasp_read_all_fd()` 读入 64KB 静态缓冲得到 `len2` / `len1`（读完即 `rasp_raw_close`）。长度不等，或等长但 `memcmp` 非 0，即 `divergence=1`：置信度 0.92 并显式置 `c->anti_hook_hit = 1`。
- **隐藏套件留下的痕迹特征**：**syscall 劫持**（hook `openat` 或 `syscall()` 以伪造 mountinfo）最强命中；**procfs 视图隐藏** 若只挂在其中一条入口上同样命中；**内核态 kprobe hook** 同时作用于两条入口，**不命中**（由 KRN-001 / MNT-001 兜底）。
- **为什么 Momo 类工具检测不到**：Momo 全程走 libc 单路径，没有第二条入口做对照；本项把「内核提供的另一条等价 API」当作独立信源，不需要外部信任根。
- **性能开销 / 调度策略**：中（2 次 64KB 读取 + 一次逐字节比较）· 全量执行，受 `extra` 模块 2500ms 预算约束。
- **环境限制**：`openat2` 打开失败（典型为 `ENOSYS`：内核 < 5.6 或 seccomp 未放行该 syscall；其它 errno 也走同一分支）→ `available=false`（`openat2 unavailable on this kernel`），raw 里记录 errno 与 `strerror`；任一路径读取失败 → `available=false`（`read failed on one path`）。本项**不**退化成「openat vs openat」，以保证「两条独立入口」的语义。

## 9. 沙箱类：clone3 干净进程与独立性（MNT-007、SBX-001，模块预算 2500ms）

> 本章共 2 项：MNT-007（强证据）与 SBX-001（间接证据），`category` 均为 `sandbox`，随 `sandbox` 开关一起生效。实现文件 `rasp_sandbox.c`。子进程经 `rasp_raw_clone3()` 创建（内核不支持时回退 `rasp_raw_clone(SIGCHLD, NULL)`，即 fork 语义），**不共享地址空间**、不初始化 Java 运行时、不调 `malloc`、不加锁、只用直调 syscall 与静态缓冲。**不调用 `setns`**（需要 CAP_SYS_ADMIN），子进程天然继承同一 mount namespace —— 这一点决定了它只能校验「用户态视图是否被伪造」，不能校验「内核态隐藏」。

### MNT-007 沙箱子进程视图一致性
- **证据等级**：强证据（STRONG / 30）
- **检测原理**：父进程若被用户态 hook 伪造了 `/proc/self/mountinfo`，那么「没有任何 hook 的新 fork 子进程」读到的必然是内核原文。对同一文件计算 FNV-1a 64 哈希，父子不一致即证明父进程的读取路径被篡改。
- **实现思路**：`rasp_sandbox.c::rasp_check_sandbox`。父进程先 `rasp_read_file_raw("/proc/self/mountinfo")` 算 `phash` 与行数；子进程 `sandbox_child_main()` 用 `rasp_raw_open/read` 读同一文件、`rasp_hash64()` 算 `shm->mountinfo_hash` 与 `mount_entries`，并额外 `statx` 取 `/system/bin/app_process64` 的 `ino/size` 写入共享内存（`mmap(MAP_SHARED|MAP_ANONYMOUS)`）。父进程 `wait4(WNOHANG)` + 2ms 睡眠轮询，最长 1500ms，超时 `SIGKILL` 回收。
- **隐藏套件留下的痕迹特征**：**syscall 劫持 / libc inline hook** 只影响父进程 → 哈希分叉，命中；**procfs 视图隐藏** 若在用户态实现同样分叉；**Shamiko/Zygisk DenyList/LSPosed/HMA Next** 的用户态部分都会命中。**内核态 kprobe hook / bpf 视图篡改 / 内核模块内存擦除** 同时作用于父子进程 → 两边一致，**不命中**（这是本项的明确边界）。
- **为什么 Momo 类工具检测不到**：Momo 只有一个观测进程，没有「干净对照进程」；本项把「新进程读同一内核文件」当作对照组，且对照进程不加载任何第三方代码，可信度天然更高。
- **性能开销 / 调度策略**：中（一次 fork + 128KB 读取 + 1500ms 上限等待）· 仅当 `sandbox` 配置开启时执行（默认开启，`rasp_jni.c` 的 `sandbox_enabled`）；关闭时本项与 SBX-001 都不产出证据。
- **环境限制**：`clone3`/`clone` 失败、子进程读取 errno 非 0、或 1500ms 超时 → `available=false`，error 分别是 `sandbox failed` / `sandbox timeout`。子进程 `mmap` 失败时只输出 SBX-001 的 `cannot allocate shared memory` 并提前返回。

### SBX-001 clone3 沙箱独立性校验
- **证据等级**：间接证据（INDIRECT / 10）
- **检测原理**：沙箱证据的效力取决于「子进程是否真的是一个独立新进程、且确实完成了 procfs 读取」。若 `clone3` 被 hook 成空实现（返回假 pid），MNT-007 的「一致」就毫无意义，必须先验证独立性。
- **实现思路**：`rasp_sandbox.c::rasp_check_sandbox` 的后半段。子进程启动时回填 `shm->child_pid` 与 `shm->parent_pid`；判据 `independent = child_ok && shm->child_pid == child && shm->parent_pid == self_pid`，其中 `child_ok = shm->ready && shm->read_errno == 0 && !timed_out`；raw 中输出 `spawned_pid`、`child_reported_pid`、`child_reported_ppid`、`independent`、`stat_available`。
- **隐藏套件留下的痕迹特征**：**syscall 劫持 `clone3`**（伪造返回值）是本项的目标；**内核态 kprobe hook** 若拦截 `clone3` 也会被本项看到（子进程不 ready 或 pid 不符）。
- **为什么 Momo 类工具检测不到**：黑名单工具不会自建进程，也不校验「新建进程是否真的存在」；本项把「沙箱可用性」本身当作一条证据，避免在沙箱失效时误信 MNT-007 的「一致」结论。
- **性能开销 / 调度策略**：低（复用 MNT-007 的同一次 fork，不额外创建进程）· 仅当 `sandbox` 开启时执行。
- **环境限制**：`child_ok=false` 时本项 `available=false`（`sandbox not available`）；若 `clone3` 被 hook 成返回假 pid，则 `child_reported_pid != spawned_pid` 或子进程永不 `ready`，本项会以 0.5 置信度命中。

## 11. 声明与边界

1. **纯痕迹采集**：本文所列 51 项全部是只读观测（`statx`/`statfs`/`getdents64`/`openat`/`openat2`/`readlinkat`/`read`/`clock_gettime`/`uname`/`__system_property_get`/`dladdr`/`clone3` 空白子进程）。**不实现、也不包含任何绕过、攻击、提权、修改 KernelSU / Magisk / Shamiko / LSPosed 环境的代码**；不写文件、不改属性、不改挂载、不 ptrace、不注入、不加载内核模块。
2. **无远程校验**：不使用 SafetyNet Attestation、Play Integrity API、Google 服务端判定或任何联网校验；所有结论来自本进程可观测的本地状态，因此可在离线设备上运行。
3. **不追求单点定罪**：单项命中只提供一条证据，最终判定由 `rasp_score.c` 按强 30 / 间接 10 / 弱 3 加权并做同类衰减；`anti_hook_hit` 是唯一能单独把结论推到 high 的信号。
4. **不可用 ≠ 安全**：`available=false` 必须与 `hit=false` 区分阅读。建议在 UI/报告中显式展示「不可用项数」，覆盖度过低时提示复测（例如换用可读 `/proc/<pid>` 的取证上下文）。
5. **已知实现降级点**（消费报告时需注意）：MNT-001 读不到 mountinfo 时本轮 MNT-002~006 缺席；BPF-004 在 init cgroup 不可读时仍报 `available=1`（仅在 `error` 字段标注原因）；`rasp_whitelisted()` 未被模块调用，白名单只在打分阶段生效；AHK-006 在内核无 `openat2`（`ENOSYS`）时直接置 `available=false` 而**不**退化成 openat 双读；FOPS-001 的扫描上限为 fd 编号 512，编号更大的 fd 不在覆盖范围；ZYS-008 依赖 `RaspNative.readProperty`，native 库加载失败时整项降级为 `available=false`。
6. **静态分析、需真机复测**：本文所有判据、阈值与 `available` 分支均来自当前源码（1.0.1-rc）的静态阅读与常量推导，**未在真实 Android 15 + KernelSU 设备上逐项复测**。阈值（如 KRN-006 的 8s/5s、INJ-005 的允许列表、FOPS-001 的 512 上限）属于经验值，实际命中率与误报率需要在真机上按「干净设备基线 → 逐项注入隐藏套件 → 观察 `hit`/`available`/`raw`」的流程重新标定；报告中 `confidence` 在覆盖度不足时会自动降低，不能当作已标定结果使用。
