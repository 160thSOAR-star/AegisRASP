# 00 设计理念

> 这份文档不描述"怎么实现"，而是回答"为什么这样做"。
> 检测项细节见 `01-检测项清单.md`，误报治理见 `02`，对抗演参见 `03`，验收标准见 `04`。

---

## 0. 一句话主张

**我们不检测"是否 Root"，我们检测"隐藏行为是否在系统各处留下了互相矛盾的说法"。**

Root 是一个状态，隐藏是一组行为，而任何隐藏都要付出"让多个观测面保持一致"的代价。
 RASP 的全部设计，都围绕一个判断：**伪造一个视图便宜，让所有视图同时自洽很贵。**

---

## 1. 问题定义：先把"敌人"定义清楚

### 1.1 对抗的不是 Root，而是"隐藏套件"

一台装了 KernelSU 但毫无隐藏的设备，对检测方几乎不构成挑战——`ksud` 进程、su 痕迹、可写系统分区都在明面上。
真正难的是下面这条隐藏链，它由若干**独立的伪造层**叠起来：

| 层次   | 隐藏手段                                  | 它试图维持的假象    |
| ---- | ------------------------------------- | ----------- |
| 内核态  | KernelSU / susfs 内核模块、内存擦除            | 内核里"没有这个东西" |
| 挂载   | Shamiko、mount namespace 隔离、overlay 覆盖 | 系统分区"没被改过"  |
| 进程视图 | procfs 过滤、pid 隐藏                      | 没有可疑进程      |
| 注入   | Zygisk、LSPosed                        | 目标进程"没被注入"  |
| 框架层  | HideMyApplist Next                    | 应用列表"本来就这样" |
| 检测对抗 | 对检测函数本身做 Hook                         | 检测"什么都查不到"  |

每一层单独看都能做到近乎完美；**但层与层之间必须互相配合**，而配合就有缝隙。

### 1.2 为什么 Momo 类工具会失效

不是它们技术不行，而是它们的方法论停在"特征匹配"：

- 只查**单一视图**（自己的 `/proc`），视图被伪造就全瞎；
- 只做**静态黑名单**（固定路径、固定进程名、固定属性），改名/搬路径即失效；
- 把"读不到"当成"没问题"，于是隐藏套件只要让读取失败就能过关；
- 不做**返回值一致性**校验，用户态 Hook 改了 `open()` 的结果也发现不了；
- 不检查**检测代码自己**有没有被改。

Momo 的失效不是漏洞，是**观测模型的天花板**。Aegis 的设计起点，就是换一套观测模型。

## 2. 五条设计准则

这五条不是口号，每一条都能在代码里找到对应实现。

### 准则一：优先相信"不可伪造的物理事实"

字符串可以被抹掉，进程名可以被擦掉，但**内核给用户态的若干返回值之间存在物理约束**：

- 一个路径 `statx()` 出来的 `stx_mnt_id`，必须出现在 `/proc/self/mountinfo` 的挂载 ID 集合里；
- `/proc/self/status` 的 `Uid` 行必须等于 `getuid()` 的返回值；
- `task` 目录项数必须和 `Threads` 字段对得上；
- 同一路径经 `/proc/self/root/...` 与直接访问，`inode/dev/size` 必须一致。

这些约束由内核数据结构本身保证，**用户态要伪造就必须同时改多处**，而改得越多，破绽越多。
实现见 `MNT-001`、`KRN-003`、`KRN-004`、`MNT-003`、`AHK-002`。

### 准则二：任何结论至少两个独立来源

单一证据永远只是线索。我们对同一事实故意走多条路径：

```
libc 读取  ─┐
直调 syscall ├─→ 逐字节比对 ─→ 不一致即判 Hook
pidfd 读取  ─┤
沙箱子进程  ─┘
```

这就是 `AHK-002`、`MNT-006`、`MNT-007` 的存在理由：**不是多查一遍，而是让"多查一遍"本身成为检测手段。**

### 准则三：不可用 ≠ 安全（三态模型）

普通应用读 init / system_server 的 `/proc` 会被 SELinux 拒绝，这是设计使然。
如果把它当成"没发现异常"，检测就退化成"谁让我读不到谁就安全"。

所以每个检测项是**三态**：

| 状态      | 含义         | 打分处理                                    |
| ------- | ---------- | --------------------------------------- |
| 命中      | 发现了异常      | 按等级与置信度计分                               |
| 未命中     | 正常执行，未发现异常 | 不计分                                     |
| **不可用** | 环境受限，无法判定  | **不计分，但报告里明确标注 `available=false` + 原因** |

配套的是**可执行覆盖率**这一元信号：当报告里"不可用"比例异常偏高时，本身就是可疑征兆（见 `03` 文档的二阶对抗）。

### 准则四：检测路径本身就是被攻击对象

对抗升级到一定程度，攻击者不会去改系统，而是**改检测器**。因此：

- 核心读取不走 bionic 的 `open/read/stat` 包装，直接 `svc #0`（aarch64）/ `syscall`（x86_64）；
- 关键函数入口做序言字节校验，识别 `B` 跳板、`BR` 蹦床、`NOP` 占位、`BRK` 断点、全零内存；
- 检测函数自身的代码段做启动快照 + 运行时比对；
- JNI 函数表指针与关键槽位做完整性校验；
- 任一反 Hook 命中，直接判定高风险（一票否决）。

这不是"防御措施"，而是**保证其他 40 项结论可信的前提**。检测器被改过，其他结论就没有意义。

### 准则五：只取证，不攻击

我们只读、只比对、只记录。不写文件、不改属性、不 `ptrace`、不加载内核模块、不绕过任何保护。
权限边界是设计的一部分，不是妥协：

- 不 `setns` 第三方命名空间（需要 CAP_SYS_ADMIN，普通应用没有）；
- 不调用 `bpf()`（无权限，也不该尝试）；
- 不依赖 root 才能运行的逻辑；
- 不做任何远程校验（无网络权限，Manifest 里连 `INTERNET` 都没有）。

## 3. 架构理念：把信任放在正确的地方

### 3.1 信任分层：Java 层最不可信

LSPosed 这类框架的主战场就是 Java 层：`PackageManager`、`ActivityManager`、`SystemProperties`、反射、JNI 桥。
因此我们把**所有核心检测下沉到 C**，Java 层只做三件事：调度、转发、持久化。

```
UI（不可信，随时被注入）
  → ViewModel（不可信，只在主线程做状态）
    → RaspEngine（半可信，只负责组装参数）
      → JNI（窄接口，5 个方法）
        → Native（核心信任域，直调 syscall）
```

接口越窄，攻击面越小。JNI 只暴露 `runDetect / submitEvidence / cancelDetect / nativeVersion / readProperty` 五个方法，
且通过 `RegisterNatives` 显式注册、符号不导出（`-fvisibility=hidden`，链接后只剩 `JNI_OnLoad`）。

例外是 `ZYS-005 / ZYS-006`：包列表多路径校验必须调用 `PackageManager` 与 binder，native 层没有合法接口。
我们的处理是**把它们的结论作为"补充证据"回注同一套聚合模型**，而不是在 Java 层自己打分——
架构上仍然保持"Java 只做接口与转发"。

### 3.2 直调 syscall：为了绕开"最容易被 Hook 的那一层"

bionic 的 `open()` 是 PLT 跳转 + libc 实现，天然是 inline hook 的首选目标。
直调 syscall 不是炫技，而是**给自己留一条没被封的观测通道**：

```c
register long x8 __asm__("x8") = SYS_OPENAT;
register long x0 __asm__("x0") = dirfd;
...
__asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), ...);
```

它的代价是必须自己处理 ABI、错误码、结构体布局（所以 `statx` 用自定义 `struct rasp_statx` 而不是 `struct stat`）。
收益是：即使 libc 被完全接管，我们仍有一条能返回真实数据的路径——**而这条路径与 libc 路径的差异，本身就是证据**。

### 3.3 clone3 沙箱：用"新进程"换一个干净的观测点

当前进程可能已经被注入：GOT 被改、PLT 被劫、JIT 里有内联补丁。
`clone3(flags=SIGCHLD)` 创建的新进程不共享地址空间、不加载 Java 运行时、不跑第三方 so，
它继承的是内核同一份 namespace 视图，但**没有继承用户态的所有 Hook 装置**（除非攻击者连 fork 后的子进程也布防）。

沙箱子进程用直调 syscall 重读 mountinfo 并计算哈希，经 `MAP_SHARED|MAP_ANONYMOUS` 回传；
父子哈希不一致 → 父进程的视图被伪造（`MNT-007`）。
同时校验子进程回填的 pid/ppid，防"clone3 被 Hook 成空实现"（`SBX-001`）。

这里体现的是**成本不对称**：让检测方多 fork 一个进程几乎零成本，让攻击方在每个新进程里都维持伪造却很贵。

### 3.4 pidfd：减少"路径级"伪造面

`pidfd_open(pid)` + `openat(pidfd, "mountinfo")` 与传统 `/proc/<pid>/mountinfo` 是**两条不同的路径**。
前者拿到的是内核对象句柄，后者要经过路径解析——而路径解析、字符串比较、`name_to_handle` 附近正是用户态 Hook 的高发区。

当 pidfd 路径与 procfs 路径结果不一致时，我们记录的是"两条路径的差异"，而不是"某个路径的结果"。
（在普通应用权限下，两者多数都会 `EACCES`；此时按准则三标记为不可用。）

## 4. 证据哲学与打分模型

### 4.1 为什么不是布尔判断

"是/否 Root"这种输出在真实世界里几乎总是错的：要么漏（隐藏得好），要么误（userdebug、模拟器、厂商调试模块）。
我们输出的是**连续的风险分数 + 置信度 + 证据清单**，让决策者自己设定阈值：

```
0-20   安全     未发现明显痕迹
21-50  可疑     存在异常特征，需进一步确认
51-100 高风险   高度疑似 KernelSU 隐藏环境
```

分数回答"有多危险"，置信度回答"我有多确定"——**两者必须分离**。
一个 90 分但置信度 0.3 的结论，和一个 45 分但置信度 0.9 的结论，处置方式完全不同。

### 4.2 权重为什么是 30 / 10 / 3

- **强证据 30**：单条就能把结论推到"可疑"（下限 25），因为它背后是物理约束被违反，正常设备不会出现；
- **间接证据 10**：单独看有合理解释，需要组合；
- **弱线索 3**：只作参考，单条命中还会把总分 ×0.5，避免"一条无害特征拉高风险"。

### 4.3 为什么同类要衰减（0.7^n）

同一类证据往往同源。比如一个 overlay 挂载会同时触发挂载类的好几项——如果简单累加，
分数会被"一个事实的多种表述"刷爆。`0.7^n` 让第 2、3 条同类证据的边际贡献递减，
**逼近"证据之间相互独立"这个理想假设**。

### 4.4 为什么强证据只给下限 25，而反 Hook 直接 85

- 强证据 → 25：承认**单点强证据仍可能是罕见合法场景**（比如某些 OEM 的 overlay 分区），留出人工复核空间；
- 反 Hook → 85：检测器被改，意味着它给出的所有"正常"结论都不可信。这是**信任链断裂**，不是"多了一条证据"。

### 4.5 白名单是"认知边界"，不是"特权"

白名单的本质是承认：**我们见过某些合法形态，愿意为它降低分数**。
因此它有严格约束（v3 规则）：

1. 与检测项 ID 完全相等 → 显式豁免（可审计、可追责）；
2. 普通片段必须够长（≥10 字节）、不是纯挂载路径、不是通用进程名；
3. **强证据**要求更具体的锚点（≥14 字节且含 `=`、`.` 或 ` on `），否则不允许豁免；
4. 片段之间用 `;` 分隔，让 `overlay on /system_ext` 这种多词锚点不被拆散。

这条演进线本身就是设计理念的一部分：**第一版"任意片段子串匹配"导致 `overlay on /system` 这类强证据被整体豁免——
白名单越方便，检测就越容易被绕过。** 所以白名单必须"难写但准确"，而不是"好写但危险"。

## 5. UI 设计理念

### 5.1 为什么是"仪表盘"而不是"报告列表"

安全检测的结果不是"一个列表"，而是**一个需要被快速判断的风险状态**。
所以首屏是一块 270° 环形仪表：分数、等级、置信度、证据分布在一屏内完成"我现在该不该紧张"的判断。
列表是第二层——用于解释"为什么是这个分数"。

### 5.2 颜色语义固定

- 冷蓝 / 青灰：信息与结构，不承载风险含义；
- 绿：安全；黄：可疑；红：高风险；
- 证据等级同样三色：强红、间接橙、弱灰。

颜色只表达**风险维度**，不表达"好看"。这样在弱光、色弱、快速扫视的场景下，语义仍然唯一。

### 5.3 过程要可见，而不是转圈

检测耗时 2-6 秒，如果只有一个 loading，用户无法判断"卡住了"还是"在跑"。
所以：

- 骨架屏逐行出现，已完成的证据**流式插入**列表；
- 顶部显示 `已完成 / 总数`；
- 每条证据可展开，看到**原始 JSON**、错误信息、采集时间。

这是"可解释性优先"：**用户必须能自己复核结论**，而不是只能相信一个数字。

### 5.4 为什么一个安全工具要有背景图和雪花

这不是装饰，而是三个真实需求：

1. **长时间驻留**：这类工具常在测试机上反复打开，视觉疲劳是真实成本；
2. **设备归属感**：同一套 SDK 会嵌到不同业务里，UI 需要可品牌化；
3. **演示场景**：给甲方/评审演示时，可定制的仪表盘比默认 Material 列表更有说服力。

同时我们对"好看"设了硬约束：背景与雪花全部是可关闭、可降级、可暂停的**表现层**，
永远不参与检测逻辑，也永远不阻塞主线程——**视觉享受不能以牺牲检测时延为代价**。

### 5.5 性能上的"礼貌"

- 雪花在页面不可见时自动暂停（`ON_PAUSE` 即停），不做后台耗电；
- 低端设备（`isLowRamDevice`）自动减半粒子数、降到 30fps；
- 背景模糊优先用 `RenderEffect` 硬件高斯，ROM 不支持则退化为半透明 + 阴影 + 磨砂；
- 检测全程在 `Dispatchers.Default`，主线程只负责渲染状态。

### 5.6 动效的意义：给"状态变化"以空间

淡入 + 缩放用于页面进入（建立层级），底弹 + 模糊遮罩用于报告（聚焦），
高度动画用于卡片展开（保持上下文），水波纹 + 微缩放用于按钮（确认反馈）。
动效不是让界面"活起来"，而是让**用户知道发生了什么、发生在哪里**。

## 6. 工程理念

### 6.1 构建必须可复现

- 版本全部锁定（Gradle 8.9 / AGP 8.7.3 / Kotlin 2.0.21 / Compose BOM 2024.10.01 / NDK 27.1）；
- 依赖仓库镜像优先、官方源兜底；
- wrapper 随仓库提交，`distributionUrl` 指向可访问的镜像；
- 构建脚本里不写死本机路径（SDK 走 `local.properties`）。

### 6.2 失败必须显式

- 读不到 → `available=false` + `errno` + 原因字符串，绝不静默；
- 超时 → 该模块熔断，其他模块继续，报告里能看出"哪一段没跑完"；
- 导出失败 → Toast 明确提示，不假装成功。

### 6.3 文档写"做不到什么"

`README` 与 `docs/05` 都明确列出：跨进程 `/proc` 多半读不到、`ZYS-006` 可能被隐藏 API 拦截、
`KRN-005` 在多数设备不可读、未做真机验证。
**把边界写清楚，比把能力写满更重要**——使用者需要知道结论的可信范围。

### 6.4 测试矩阵按"对抗强度"分层，而不是按功能点

8 个场景不是"功能列表"，而是一条对抗强度轴：

```
干净 AOSP → 干净 CloreOS → 模拟器 → KSU 裸装 → DenyList → Shamiko → 全隐藏 → 检测器被 Hook
```

验收标准是"分数落在预期区间 + 命中预期 ID 集合"，而不是"某一项返回 true"。
因为检测系统的价值在于**整体判断**，不在于单个函数的返回值。

## 7. 我们刻意没做的事（反模式清单）

| 不做                         | 原因                              |
| -------------------------- | ------------------------------- |
| 扫 su 二进制路径                 | 隐藏套件第一件事就是换路径，静态路径等于自欺          |
| 用 `ro.debuggable` 单点判断     | userdebug 固件、模拟器、厂商调试机全会误报      |
| 扫 busybox                  | 与 KernelSU 无关，只是 Magisk 时代的遗留特征 |
| SafetyNet / Play Integrity | 远程校验依赖网络与 Google 服务，且不能离线取证     |
| 把检测逻辑写进 Compose 组件         | UI 随时被注入，检测必须在 native           |
| 检测失败时输出"安全"                | 这是最危险的错误：把"不知道"伪装成"没问题"         |
| 用 root 才能跑的检测              | 违背"普通应用"前提，且一装就暴露               |

## 8. 演进方向

**短期（可用性）**

1. 真机校准：把 `04` 里的静态推算换成实测分布，修正阈值；
2. 元信号化：把"不可用比例、耗时分布、证据自相矛盾"做成独立的低权重证据项；
3. 报告可复现：加设备指纹与检测版本号，便于横向比对。

**中期（模型）**

1. 用证据图（evidence graph）替代线性加权，表达"某几条证据共同成立才有意义"；
2. 引入先验：按机型/ROM/系统版本给出基线，减少跨设备方差；
3. 时间维度：多次检测之间的差分（新增映射、新增进程）比单次快照更有信息量。

**长期（对抗）**

1. 可选内核探针：仅在已授权环境提供更高精度的内核态视图，主体检测永不依赖它；
2. 侧信道：syscall 路径长度、页错误分布、调度延迟，作为"内核被插桩"的间接证据；
3. 检测器自身的最小可信基：把最关键的自校验做成独立、极小的代码段，降低被整体替换的概率。

---

## 9. 结语

这套方案的核心不是 41 个检测项，而是三个判断：

1. **隐藏的代价是自洽**——伪造一个视图便宜，让所有视图一致很贵；
2. **检测器的可信度是前置条件**——所以先证明"我没被改"，再谈"我查到了什么"；
3. **诚实地表达不确定性**——"不可用"是一个结论，"安全"是另一个结论，二者不能混为一谈。

只要这三条成立，检测项可以增删、阈值可以调整、UI 可以重做；
一旦这三条被放弃，再多的检测项也只是在制造"安全感"的幻觉。
