# 03 风险说明与未来绕过可能性

> 对应《生成要求》⑤「风险说明 & 未来绕过可能性 & 兜底备选检测思路」。
> 适用版本：aegis-rasp/2.0.0-beta（versionCode 6；纯用户态、无 Root 权限、51 个检测项：8 大类 + 沙箱独立性 + 文件系统视图一致性）。
>
> **本文档只做威胁分析与检测取证思路的讨论，不包含、也不会给出任何 Hook、隐藏、绕过、免杀的实现代码。** 文中出现的「攻击者可以……」均为风险评估，用于指导检测项加固；任何一条都不构成可执行方案。

## 0. 文档定位

本方案运行在 `untrusted_app` 沙箱内，没有 Root、没有内核模块、不能调用 `bpf()`、不能 `setns` 进入别人的 namespace、不能读内核内存。对抗的另一方拥有内核模块、可以改内核函数、可以伪造任意 `/proc` 文件。**这是不对称对抗**：我们不追求「一定检出」，而是追求：

1. 抬高隐藏成本，让「完整隐藏套件」必须同时伪造多条互相独立的观测面；
2. 把「检测失败」本身变成一种可观测信号（可用率、耗时、结果矛盾）；
3. 明确哪些痕迹是**可以彻底擦除的**（不要在这些点上写死判据），哪些是**很难彻底抹除的本质性痕迹**（应作为核心判据）。

## 1. 威胁模型与对抗层级

### 1.1 能力对照

| 能力 | 隐藏方（KSU + 隐藏模块） | 本方案（普通应用） |
| --- | --- | --- |
| 修改内核函数返回值 | 可以（kprobe / ftrace / inline patch / static call） | 不可以 |
| 修改 `/proc/<pid>/*` 输出 | 可以（内核侧或用户态 LD_PRELOAD 级） | 只能读取，不能校验「内核是否说了真话」 |
| 修改自身进程内存 | 可以（注入、mprotect、代码 patch） | 只能读取自身只读代码段做自校验 |
| 调用 `bpf()` / 加载模块 | 可以（root） | 不可以 |
| 跨 namespace 查看其它进程 | 可以（root 可 setns，内核模块可直接读 task 结构） | 只能 `pidfd_open` 优先、失败回退 `/proc/<pid>/*`，读可读文本 |
| 观察自身进程的完整视图 | 可以（它就是内核） | 只能通过多条独立路径交叉验证 |

### 1.2 对抗层级（由浅入深）

| 层级 | 典型形态 | 本方案的有效性 |
| --- | --- | --- |
| L1 仅 Root，无隐藏 | Magisk/KSU 默认安装，ksud、模块、overlay 均可见 | 高（KSU-001、ZYS 系列、MNT 系列都有信号） |
| L2 用户态隐藏 | Shamiko、DenyList、Zygisk 隐藏、HMA 包列表过滤 | 中高（跨视图、Java 多路径、反 Hook 仍有效） |
| L3 内核态隐藏 | 自定义内核模块过滤 `/proc`、隐藏进程、擦除模块链表 | 中（依赖物理一致性、时间侧信道、自校验） |
| L4 内核态完整伪造 | 对所有进程返回自洽的假视图，同时抹掉时间差异 | 低（只能靠「二阶对抗」的元信号与不可消除的物理约束） |

## 2. 8 大类 + 沙箱 + 文件系统视图的绕过路径与兜底

每一节统一按「现状能力 → 未来可能的绕过手段 → 兜底检测思路 → 痕迹属性」组织。检测项编号含义见 [CheckCatalog.kt](../rasp-detect-native/src/main/java/com/rasp/detect/CheckCatalog.kt)。1.0.1-rc 把检测项从 41 扩到 51：新增的 MNT-008/009、KRN-006/007、INJ-005、AHK-005/006、ZYS-007/008 分别并入 §2.1、§2.3、§2.6、§2.8、§2.5；FOPS-001 单独构成新类别 `fops`，见 §2.9。

### 2.1 Mount Namespace 与文件视图隔离（MNT-001～009）

**现状能力**：读取本进程 `mountinfo`，与 `statx(STATX_MNT_ID)` 返回的 `mnt_id` 做集合比对；用 `pidfd` 读 `init` / `system_server` 的 `mountinfo` 与 `root/` 路径 stat 做跨进程比对；`clone3` 子进程重读同一份视图做父子哈希比对；`/proc/self/mounts` 的直调与 libc 双路径比对。1.0.1-rc 追加两条**跨接口**一致性：mountinfo 的 ro/rw 标志 vs 直调 `statfs` 的 `ST_RDONLY`（MNT-008）、`statx` 的 `stx_dev` vs mountinfo 登记的 dev（MNT-009）。

**未来可能的技术绕过**：

1. 在内核中为**目标进程**维护一棵假的挂载树视图：`mountinfo` 返回过滤后的条目，`statx` 返回伪造的 `stx_mnt_id`，`statfs`/`stat` 一并伪造；隐藏模块只对「被检测应用的 uid」生效。
2. 通过 `move_mount`/detached mount 让模块文件不出现在目标进程的挂载树里，只在实际访问时通过路径重定向（如 overlay 的 lowerdir 不在挂载表中）完成注入。
3. 让 `clone3` 出的子进程进入不同的挂载视图（例如给子进程单独 unshare），使 MNT-007 的父子哈希比对「因为视图本来就不同」而失效。
4. 在 `read` 系统调用层过滤：对 `mountinfo` 的读取返回预先准备好的静态缓冲，且对同一 fd 的多次读取返回不同内容以规避哈希。
5. 同时篡改两套接口：既改 `mountinfo` 的 ro/rw 文本，又改 `statfs` 的 `f_flags`；既改挂载行里的 dev，又改 `statx` 的 `stx_dev`。单看任一处都自洽，但两套接口在代码里属于不同的内核路径（挂载层 vs `statfs`/`stat` 路径），改一处就会与另一处矛盾。

**兜底检测思路**：

- **物理一致性优先于文本**：MNT-001 的判据不是「文本里有 overlay」，而是「`statx` 给出的 `mnt_id` 必须存在于 `mountinfo` 的 id 集合中」。伪造文本就必须同步伪造每一个路径的 `statx` 返回；伪造 `statx` 就必须保证与 `/proc/self/mountinfo`、父子进程、`init` 视图全部自洽——成本随路径数线性上升。
- **多进程同源**：MNT-002 / MNT-003 从 `init`、`system_server` 读同一份事实。要让应用「看起来干净」，攻击者需要让三个进程的视图互相自洽，而不是只骗一个进程。
- **双路径**：MNT-006 用直调 syscall 与 libc 各读一次 `/proc/self/mounts`。只 hook 其中一条路径会直接暴露；两条都 hook 则必须同时 Hook bionic，触发 AHK-001 / AHK-002。
- **子进程重放**：MNT-007 在 fork 出的干净子进程里重读。攻击者若未在该子进程里预先布置 Hook，父子结果必然不同。
- **跨接口同义比对**：MNT-008 / MNT-009 不比文本，而是让两个不同的内核接口对同一事实表态——挂载表说 ro，`statfs` 的 `f_flags` 就必须置 `ST_RDONLY`；挂载表登记了 dev，`statx` 报的设备号就必须相等。只过滤其中一个接口会立刻产生矛盾；两个都改则要动挂载层与 `statfs`/`statx` 两套代码，且要保证同一路径在 `fstat`、`readlink` 上也自洽。
- **可扩展方向（当前未实现）**：`/proc/self/mountinfo` 的挂载 id 拓扑（父 id 链必须能追溯到根）、`statfs` 的 `f_fsid` 与 `f_type` 一致性（MNT-008 目前只用到 `f_flags`）、`/proc/self/map_files` 的反向映射、文件 `i_generation`/`i_version` 的跨视图一致性。

**痕迹属性**：

- 可完全擦除：`mountinfo` 文本、`mounts` 文本、单次 `stat` / `statfs` / `statx` 返回。
- 很难彻底抹除：**挂载视图与 `statx` `mnt_id` 的物理一致**（一个路径只能有一个真实的挂载归属）、**跨进程 inode/dev 一致**（同一文件在 init 与 app 眼中的 inode 必须相同，除非给 app 一个假的文件系统）、**挂载树的拓扑约束**（子挂载点的父 id 必须存在）、**ro 标志与 `ST_RDONLY` 的语义一致**（只存在于挂载层的只读属性必须同时体现在 `statfs` 里）、**设备号与挂载登记的一致**（同一路径只能属于一个真实 mount）。

### 2.2 KernelSU 本体与进程痕迹（KSU-001～005）

**现状能力**：有界扫描 `/proc`（完整模式最多 700 个进程、快速模式 220），对 `comm`/`cmdline` 做特征匹配；读 `stat` 校验 pgrp/sid；回溯父进程链；检查 `memfd:` 与 `(deleted)` 的可执行文件；统计 fd 中的匿名 inode。

**未来可能的技术绕过**：

1. 进程名随机化 / 伪装成系统进程名（`comm` 是用户态可写的，`cmdline` 可清空），ksud 改为按需 `exec`、常驻进程退出。
2. 用 `memfd_create` + `fexecve` 完全无文件启动（KSU-004 可见，但可以配 `hidepid`）。
3. 通过 PID namespace 隔离，让应用的 `/proc` 根本看不到 root 域的进程。
4. 内核模块在 `proc_pid_readdir` / `filldir` 层过滤条目，`/proc` 目录列表里直接不出现目标 pid。
5. 伪造进程属性：把 pgrp/sid 改成正常值，把父进程链指向 zygote。

**兜底检测思路**：

- KSU-003 的「父链必须终止于 zygote/init」是结构性约束：应用进程由 zygote fork，这条链在内核 task 结构里，改它要动 `task_struct->real_parent`。
- KSU-004 / KSU-005 不看名字看行为：无文件可执行、fd 表里的 bpf/memfd 类型，与进程名无关。
- KRN-004 的 uid/cred 互证：使用 root 能力就会在 `CapEff`、`Uid` 四元组上留下痕迹，这与进程名无关。
- 可扩展方向（当前未实现）：`/proc/net/unix` 的抽象 socket、su 请求的 binder 事务侧信道、`/proc/<pid>/stack`（普通应用不可读）、进程的 `seccomp` 状态、`/proc/<pid>/oom_score_adj` 等 root 进程常见特征。

**痕迹属性**：

- 可完全擦除：进程名、命令行、启动时间、可执行文件路径（memfd）。
- 很难彻底抹除：**父进程链与会话/进程组的结构一致性**（伪造需要同时改多个 task 的字段，且要与 `wait4`/`getpgid` 的返回值一致）、**cred 与 `/proc` 视图的互证**（`CapEff`、`Uid` 必须与实际系统调用行为一致）、**内存与 cgroup 统计**（root 守护进程会占用内存页，cgroup 计数不会因为改名而消失）。

### 2.3 内核态间接痕迹（KRN-001～007）

**现状能力**：`getpid` 直调 240 次（快速模式 80 次）统计中位数/分位数/离群点；`/proc/version` 与 `uname`、`osrelease` 三源比对；`status` 的 Pid/Tgid/Threads 与直调 `getpid/gettid`、`/proc/self/task` 条目数比对；`Uid`/`CapEff` 与直调 `getuid/geteuid` 比对；`kallsyms` 地址可见性。1.0.1-rc 追加两条**语义与时间**的旁证：`btime` ≈ `now − CLOCK_BOOTTIME` 且 `/proc/uptime` ≈ `CLOCK_BOOTTIME`（KRN-006）；5 个固定探针的 errno 语义必须符合预期（KRN-007）。

**未来可能的技术绕过**：

1. 不用 kprobe，改用 `static_call` / inline patch / 直接改内核函数体，避免在 `kprobe` 链表留下条目。
2. 在 `seq_file` 层过滤 `/proc/version`、`/proc/kallsyms`，或在 `uname` 系统调用返回前改写 `utsname`。
3. 直接修改 `cred` 结构（而不是 setuid），使 `Uid` 看起来仍是应用 uid，但实际拥有 root 能力——这会让 KRN-004 的 `Uid` 比对失效。
4. 把 hook 点的开销摊平（例如只在特定调用路径上启用），规避时间统计。
5. 让时间账本自洽：把 `btime`、`/proc/uptime`、`clock_gettime(CLOCK_BOOTTIME)` 三者同时改写。它们来自内核里三本不同的账（RTC 基准、tick 累加、时钟源），同步修改会波及**所有进程**的时间观，而不只是被检测应用。
6. 把所有 errno 都伪装成「正常内核」的样子：需要同时覆盖「不存在路径 → `ENOENT`」「空路径 → `ENOENT`」「正常文件 → 成功」三类语义。任何一处改写都会与另一处的行为矛盾；而「一律返回 ENOENT」这种粗糙过滤会立刻让 `/system/bin/sh`、`/proc/version` 打不开。

**兜底检测思路**：

- KRN-001 是**统计性**判据：单个 syscall 可以被优化，但 kprobe/ftrace 的逐次回调会在分布上留下长尾；判据是「离群点比例 > 1/40 且单次 > 12×中位数且 > 20µs」，这是分布特征，不是单点特征。
- KRN-002 的三源一致性（`/proc/version`、`uname`、`/proc/sys/kernel/osrelease`）需要同时伪造三处；只改一处会直接暴露。
- KRN-003 把 `status` 与**直调 syscall 的返回值**对照：伪造 `status` 不能让 `getpid` 说谎（除非同时 hook syscall，触发 AHK-002）。
- KRN-005 是弱线索，仅在 kallsyms 泄漏时给 0.25，不单独升级。
- **时序自洽是「内核插桩」的旁证**：任何在 syscall 入口插桩的方案都要额外读数据、构造返回值，插桩本身不改 `btime`；但如果伪造层为了「让视图看起来像刚启动」去改 `/proc/uptime` 或时间返回值，就会与 `CLOCK_BOOTTIME` 的差值对不上（KRN-006 的 8 s / 5 s 两个阈值）。这是一条**不依赖任何文本**的判据，且改动会波及全系统。
- **errno 语义是「伪造层不够细」的旁证**：KRN-007 只问「该失败的是不是失败、errno 对不对」。隐藏套件惯用的手法是「对可疑路径一律返回 `ENOENT` 假装不存在」，这会立刻与本应成功的 `/system/bin/sh`、`/proc/version` 冲突；反之「一律放行」会让不存在的路径也 `open` 成功。要让 5 个探针全部符合真实内核的语义，伪造层必须逐路径判断，成本远高于挂一个返回常量。
- 可扩展方向（当前未实现）：同一语义的多个 syscall 交叉（`getpid` vs `gettid` vs `getppid`、`stat` vs `statx` vs `fstatat`）、`clock_gettime` 与 `gettimeofday` 的单调性（KRN-006 目前只做了 BOOTTIME 与 `btime`/`uptime` 的交叉）、`sched_getaffinity` 与 cgroup cpu 配额的矛盾。

**痕迹属性**：

- 可完全擦除：`kallsyms` 文本、`version` 文本、单次 syscall 返回值。
- 很难彻底抹除：**syscall 耗时的统计分布**（任何内核 hook 都会引入抖动，且抖动分布与正常调度不同）、**内核函数返回值一致性**（同一事实的多个 syscall 必须给出相容答案）、**cred 与 `/proc` 视图的互证**（`CapEff` 可以被伪造，但「有 root 能力却报 0 能力」会导致能力相关 syscall 的行为矛盾）、**时间账本的自洽**（`btime` / `/proc/uptime` / `CLOCK_BOOTTIME` 必须与真实运行时长一致）、**syscall 返回码与 errno 的语义正确性**（由内核 VFS 语义决定，任一处改写就与其它路径矛盾）。

### 2.4 BPF 篡改痕迹（BPF-001～004）

**现状能力**：统计自身 fd 中的 `anon_inode`、`bpf` 类型 fd、fdinfo 关键字；socketpair RTT 分布；自身与 init 的 cgroup 行数比对。

**未来可能的技术绕过**：

1. 根本不在目标进程里留 bpf fd：eBPF 程序由 root 进程加载、挂在 cgroup/tracepoint 上，目标应用看不到任何 fd。
2. 隐藏 bpf map id / prog id（`bpf_obj_get_info_by_fd` 对无权限者返回空）。
3. 用 `tc`/`nftables` 或内核模块替代 eBPF 完成同样的过滤，完全不留 bpf 痕迹。

**兜底检测思路**：

- BPF-004（cgroup 视图行数）与 BPF-003（网络时延分布）是**间接**判据：bpf 程序挂在路径上会改变该路径的耗时分布，即使 fd 不可见。
- BPF-001 / BPF-002 只对「注入到本进程的 bpf fd」有效，属于弱信号，不要作为主判据。
- 可扩展方向（当前未实现）：socket 选项与 `SO_ATTACH_BPF` 的副作用、`/proc/net/tcp` 的统计异常、DNS/UDP 首包时延的分布差异。

**痕迹属性**：

- 可完全擦除：fd、fdinfo 文本、map/prog id。
- 很难彻底抹除：**附着点带来的时延分布偏移**（内核执行 bpf 程序的指令周期无法凭空消失）、**cgroup 层级与 attach 的一致性**（挂在某个 cgroup 上，该层级的统计会变化）。

### 2.5 Zygisk / Shamiko / LSPosed / HMA Next（ZYS-001～008）

**现状能力**：`/proc/self/maps` 的 rwx/匿名可执行/非 JIT memfd 可执行/可疑路径统计；native bridge 属性与模块映射路径；Shamiko 式挂载特征；LSPosed 模块路径与 libart 代码段可写（仅 w+x）；Java 层三条包列表路径交叉（ZYS-005）与 binder 直查 vs PackageManager 门面（ZYS-006）。1.0.1-rc 追加两条：`/proc/self/task/*/comm` 的线程名特征（ZYS-007）与 Java 静态字段 vs 属性区当前值的双路径比对（ZYS-008，Java 层执行、回注同一套打分模型）。

**未来可能的技术绕过**：

1. 完全用户态隐藏：不落盘、不映射具名 so，模块用 memfd 加载并从内存 `dlopen`，路径里看不到 `lspd`/`zygisk`。
2. 注入后擦除痕迹：模块加载完成后 `munmap` 自己的映射，只留下被 patch 的 ART 方法入口（本方案当前不检查 ArtMethod，属于可扩展方向）。
3. HMA Next 类方案同时 Hook 三条包列表路径（`getInstalledPackages`、`getInstalledApplications`、`queryIntentActivities`），并让 binder 直查也返回过滤后的列表。
4. Shamiko 在应用进程的 mount namespace 里彻底 unmount 模块，使 `mountinfo` 与「干净设备」完全一致。
5. DenyList 只对目标应用关闭注入，使 `maps` 干净——但 root 本体仍在。
6. **线程改名**：注入框架改名自己的工作线程（`comm` 是可写字段，`prctl(PR_SET_NAME)` 想写什么写什么），让 ZYS-007 的 10 个关键字（zygisk/lspd/lsposed/riru/magisk/ksu/inject/payload/inline/hook）整体 miss。线程名本来就是可完全擦除项。
7. **在进程启动前把属性区改成与目标机型一致**：Zygisk 模块在 zygote fork 之后、`Build` 类初始化之前改写属性，会让 Java 静态字段与属性区**同时**是假值，ZYS-008 的比对自然成立（两项都是假值且相等）。代价是这套假值必须与磁盘 `build.prop` 也一致，否则被 SEL-005 抓到。

**兜底检测思路**：

- **注入必然改变进程的内存布局**：ZYS-001 / ZYS-004 检查 rwx、匿名可执行、可疑路径；即使换成 memfd，也会落在「非 JIT memfd 可执行」这一路（ART 的 JIT / dalvik / boot.art / boot.oat 已在 `rasp_maps_stats` 中排除，见 02 文档 §2.10；因此该项的 memfd 证据只可能来自注入或加固壳）。
- **包列表的多路径交叉**：ZYS-005 / ZYS-006 的价值在于「同时骗过 4 条语义不同的查询路径」的成本；注意 `getInstalledPackages` 与 `queryIntentActivities` 的可见性差异本身可能是正常行为（工作资料、instant app），因此只算间接证据（0.65 / 0.70）。
- **挂载与视图**：Shamiko 的 unmount 会让应用视图「看似干净」，但 MNT-003（与 `system_server` 的 root 视图比对）会暴露差异——unmount 只发生在应用的 namespace 里。
- **属性区与 Java 静态字段的时间差**：`Build.MODEL` / `Build.FINGERPRINT` / `Build.VERSION.SDK_INT` 是进程启动早期从属性区**快照**下来的常量，之后不再重读；而 native 的 `__system_property_get` 读的是**当前值**。因此运行期用 `resetprop` 改属性（最常见的隐藏手法，用来伪造指纹、隐藏 `test-keys`）会让静态字段与当前值不一致（ZYS-008）。要消除这个差异，必须把改写提前到 `Build` 类初始化**之前**，即把攻击窗口从「运行期」推到「进程启动前」，并且要与磁盘 `build.prop`、`ro.boot.*` 一起自洽（与 SEL-005 交叉验证）。
- 可扩展方向（当前未实现）：`ArtMethod` entrypoint 与 `dex pc` 的互证、JIT code cache 的完整性、`libart` 内部表的写保护状态，以及线程名与「线程创建时间 / 栈范围 / `task` 目录可见性」的联合判定（ZYS-007 目前只做 `comm` 名字匹配）。

**痕迹属性**：

- 可完全擦除：模块 so 路径、maps 里的具名映射、包列表差异（如果 4 条路径全部 Hook）、线程名（`prctl(PR_SET_NAME)` 任意改）。
- 很难彻底抹除：**进程内存布局的整体自洽**（注入需要在某处留下可执行页或改写已有页，代码段自校验会发现改写）、**Java 方法 Hook 对 ART 内部结构的修改**（ArtMethod 入口必须指向别处，这是「指针必然存在」的痕迹）、**调用耗时的变化**（Hook 路径比原路径慢）、**Java 静态字段与属性区当前值的时间差**（快照早于运行期改写；要消除必须提前到启动前，且与磁盘属性自洽）。

### 2.6 Ptrace / 内存映射 / 进程注入（INJ-001～005）

**现状能力**：maps 异常段统计；`TracerPid` / `State` / 父进程 trace 状态；libc/libart 关键符号入口完整性；dex/vdex/oat 的 memfd 与 `(deleted)` 检测。1.0.1-rc 追加：可执行映射的**来源前缀白名单**（INJ-005）——`/system`、`/apex`、`/vendor`、`/product`、`/system_ext`、`/odm`、`/data/app`、`/data/dalvik-cache`、`/data/user`、`/data/data`、`/dev`、`/data/misc`、`/mnt/expand` 与 `memfd:jit` 放行，其余来源的可执行段视为可疑；匿名段仍由 INJ-001 负责。

**未来可能的技术绕过**：

1. `ptrace` attach 完成注入后立即 `detach`，`TracerPid` 归零——INJ-002 只在 attach 窗口内有效。
2. 注入后把原始页恢复（保存 → 写入 → 还原），使代码段自校验（AHK-003）在检测时刻看不出差异。
3. 用内核模块直接改目标进程内存，绕过 `ptrace` 与 `/proc/pid/mem` 的用户态痕迹。
4. 匿名加载 dex 后立即 `mprotect(PROT_NONE)` 或释放映射，使 maps 中看不到。
5. 把注入代码伪装成系统库：预置到 `/data/local/tmp` 再 `dlopen`（对 INJ-005 是直接命中），或用 `memfd` 加载后让 maps 里的路径显示成系统路径（要改 VFS 层，会与 `dladdr`、`stat` 的结果冲突）。

**兜底检测思路**：

- INJ-003 / AHK-001 检查的是**符号入口的指令形态**（B/BL/BR/NOP/BRK/全零），注入必须让入口跳走，这与是否 detach 无关。
- AHK-003 在 `JNI_OnLoad` 记录自身热代码 64 字节指纹，检测时重算。攻击者要绕过，必须在**加载前**改文件（此时依赖 APK 签名校验，本方案未实现）或**每次检测前**精确还原（成本极高且与「注入要生效」矛盾）。
- INJ-004 的 dex/vdex/oat + memfd/`(deleted)` 组合，与「是否 detach」无关。
- **来源路径是「注入必须落地」的约束**：注入代码一定落在某个可执行映射里——要么是真文件（路径可追溯），要么是匿名/memfd 段（由 INJ-001 / ZYS-001 覆盖）。INJ-005 只问「这个可执行段是否来自系统/应用允许的来源」，与进程名、模块名、线程名都无关，改名换壳都躲不过。
- 可扩展方向（当前未实现）：`/proc/self/pagemap`（普通应用不可读）、`mincore` 探测页驻留、代码段与文件哈希的逐页比对、`mprotect` 后可执行页的写时复制状态。

**痕迹属性**：

- 可完全擦除：`TracerPid`、ptrace 会话、临时映射。
- 很难彻底抹除：**代码段自校验的物理一致性**（内存中的代码必须与文件哈希一致，除非攻击者永不 hook）、**调用路径的耗时**（跳板必然多一次间接跳转）、**注入引入的可执行页**（rwx 或匿名可执行，除非复用已有可执行页并精确还原）、**可执行映射的来源**（路径要么真实可追溯、要么就是匿名段，二者都与干净进程的映射画像不同）。

### 2.7 SELinux / AVB / 系统完整性（SEL-001～005）

**现状能力**：`attr/current` 域检查；`policyvers`/`enforce`/`checkreqprot`；AVB 相关 `ro.boot.*` 属性；系统分区 rw/overlay/tmpfs 挂载；运行时属性区 vs 磁盘 `/system/build.prop` 四键比对。

**未来可能的技术绕过**：

1. `resetprop` 类方案只改内存中的属性区，磁盘 `build.prop` 不变——SEL-005 正是为此设计（双源比对）；但如果同时改磁盘（需要 remount /system），AVB 会失败、`verifiedbootstate` 变 orange。
2. 动态重载 SELinux policy（`magisk policy`），让应用域看起来正常，但 policy 版本号/规则集发生变化。
3. 通过 Hook 属性读取（`__system_property_get`）让所有属性看起来是绿色状态——这会触发 AHK-001（libc 入口）与 AHK-002（直调 vs libc）。
4. 解锁 bootloader 后把 `ro.boot.verifiedbootstate` 伪造成 green——但 bootloader 状态在部分设备上可通过 `/proc/cmdline`、`ro.boot.*` 多源交叉发现（本方案当前只读了 `ro.boot.*`，属于可扩展方向）。

**兜底检测思路**：

- SEL-005 的双源比对是核心：属性区与磁盘必须一致；不一致就说明有人改了运行时属性。
- SEL-001 的域检查与 KRN-004 的 cred 检查互补：域正常但能力异常、或域异常但能力正常，都是矛盾信号。
- SEL-002 的 `enforce=0` / `policyvers` 偏低是弱线索，配合 SEL-004 的 rw/overlay 挂载一起看。
- SEL-003 明确只作弱线索（置信度 0.40–0.70），因为解锁 bootloader 的合法用户机也会是 orange。
- 可扩展方向（当前未实现）：`/proc/cmdline` 与 `ro.boot.*` 的交叉、`/sys/fs/selinux/policy` 的规则集哈希、`avb` 的 vbmeta digest 与分区哈希比对。

**痕迹属性**：

- 可完全擦除：属性值、`attr/current` 文本、AVB 属性。
- 很难彻底抹除：**属性区与磁盘/内核 cmdline 的多源一致性**（改一处必然与另一处矛盾）、**enforcing 与 su 域并存的矛盾**（能执行 su 就意味着有域转换）、**系统分区的只读性**（rw 挂载与 AVB green 不可能同时成立）。

### 2.8 反 Hook 自校验（AHK-001～006）

> **⚠️ 1.0.2 引入的假阴性窗口（补记，此前未记录在任何文档中）**
>
> 1.0.2 把 AHK-006 从「单次比对不一致即命中」改成「连续两轮都不一致才命中」，目的是消除挂载/卸载抖动
> 造成的 85 分假阳性。这个修正是对的，但**代价是一个新的、攻击者不需要识破检测就能利用的绕过面**：
>
> - 攻击者只需要让**任意一轮**读取「看起来一致」。低成本手法：在 `openat2` 路径上按调用计数间歇性放行
>   （例如每 2 次返回一次真实内容），或在每次 hook 时短暂还原原函数，使两轮里有一轮一致。
> - 一旦出现「任一轮一致」，本项立即结束且**不产生任何证据**，`anti_hook_hit` 不置位，85 分下限不触发。
> - **量化**：设攻击者能让单轮读取「看起来一致」的概率为 `q`，则旧实现漏检概率 ≈ `q`，
>   新实现 ≈ `2q − q²`（`q` 较小时**约等于翻倍**）。假阳性同理从 `p` 降到 `p²`。
>   也就是说，这次改动**用「约两倍的漏检概率」换「平方级的误报下降」**。
> - **不要用「再多几轮」来补救**：改成「3 轮全不一致才命中」会把漏检概率推到 ≈ `3q`，方向是反的。
> - 正确的加固方向是**换判别维度**：任一轮不一致就继续深查，用 `mountinfo` 的 `mnt_id` 集合差集
>   区分「合法挂载变化」与「内容被改写」——挂载抖动只会增删 `mnt_id` 行，而 Hook 改写会让
>   同一 `mnt_id` 的内容/长度变化。这一条尚未实现，已记入 `ROADMAP.md` 技术债。
>
> 结论：**AHK-006 在 1.0.2 之后不再是「强到可以单独定罪」的判据**。报告里出现 `available=false` 或
> 「两轮一致」时，不应据此判定环境干净。

**现状能力**：libc 关键符号入口指令检查；直调 syscall 与 libc 结果一致性；自身热代码指纹（`JNI_OnLoad` 快照）；JNI 函数表指针与槽位可执行性校验。任何一项命中都会把 `anti_hook_hit` 置位，最终分数不低于 85。1.0.1-rc 追加两条结构性校验：函数地址必须同时满足「可被 `dladdr` 反解到模块」与「落在 `x` 权限段」（AHK-005）；`openat2` 与 `openat` 两条 syscall 对同一文件逐字节一致（AHK-006）。**1.0.2 起 AHK-006 改为「最多 2 轮、连续 2 轮都不一致才命中」，且 `openat2` 是否可用先由兼容探测门控**（见下方「1.0.2 引入的假阴性窗口」）。

**未来可能的技术绕过**：

1. **按需 Hook**：只在检测函数执行期间还原原始字节，检测结束后再写回跳转——需要精确定位检测窗口，且要 Hook 调度/时序。
2. **内核级返回伪造**：不碰用户态代码，直接让 `read` 返回准备好的内容，让 `statx` 返回假元信息。这类攻击不会触发 AHK-001（libc 入口没变）；由于直调与 libc 走的是同一个被伪造的内核路径，AHK-002 也可能被"一致地骗过"，只剩物理一致性（`mnt_id`/`ino`/跨进程视图）与元信号（§4.3）可以发现。
3. **双视图内存**：用 `mmap` 双映射让检测线程看到原始页，其他线程看到 hook 页（需要内核配合）。
4. **Hook JNI 表后再还原**：在 `JNI_OnLoad` 之后替换表指针，检测前还原——AHK-004 只校验表指针与 3 个槽位，攻击者可以只替换 `CallVoidMethod` 等未校验槽位（当前只校验 4/6/31）。
5. **在 so 加载前改文件**：重打包 APK / 替换 so，使 `JNI_OnLoad` 的快照本身就是被污染的版本。这是 AHK-003 的**根本局限**，需要签名校验配合（本方案未实现）。
6. **同时 hook `openat` 与 `openat2`**：两条路径的内核入口不同（`openat2` 要解析 `open_how`，走的是另一条分发），要骗过 AHK-006 必须改两套 syscall 的处理；只挂 libc 的 `open`/`openat` 符号对直调 `SYS_openat2` 无效，而两边都改还要让两份内容逐字节一致。

**兜底检测思路**：

- 自校验的价值不在于「一定发现」，而在于**让 Hook 必须做到「检测时刻还原 + 检测后恢复」**，这会引入可被观测的时间窗口与耗时异常（见 §4.3）。
- AHK-002（直调 vs libc）不依赖代码段完整性，只依赖「两条路径必须给出同一答案」。
- AHK-004 的槽位校验可以扩展（当前 4/6/31，可加入 `CallVoidMethod`、`GetMethodID`、`NewStringUTF` 等本库实际使用的槽位）。
- **双 syscall 比对为什么难同时伪造**：`openat2` 与 `openat` 进入内核的入口不是同一个函数，用户态 inline hook 通常只挂在 libc 的 `open`/`openat` 符号上，而 AHK-006 的 `openat2` 是**直调 syscall**（带 `open_how`），绕开了被 hook 的符号；要让两条路径返回一致的伪造内容，攻击者必须同时改 libc 符号与 syscall 分发（或在内核里改两条路径），并且让读到的长度、内容与随后的 `fstat`、`readlink` 互相自洽。成本从「改一处返回值」变成「改两条 syscall + 保证跨接口一致」。
- **地址 ↔ 段权限 ↔ 模块归属的三方一致**：AHK-005 要求函数指针既能被 `dladdr` 反解到某个模块，又落在 `perms[2]=='x'` 的映射内。跳板式 Hook 往往让指针指向匿名可执行页（`dladdr` 失败）或指向 `rw-` 段（不可执行），两者都会命中；要在保持跳板的前提下绕过，必须让跳板页看起来像「某个模块的可执行段」，而模块归属又会与 maps 里的文件路径、`dladdr` 的 `dli_fname` 交叉。
- 可扩展方向（当前未实现）：签名校验（APK 证书 + so 哈希）、`/proc/self/maps` 中自身 so 的映射范围与文件哈希、检测代码分散到多个 so。

**痕迹属性**：

- 可完全擦除：代码段改写、JNI 表指针、libc 入口跳板（只要检测时还原）。
- 很难彻底抹除：**代码段自校验的物理一致性**（内存 ↔ 文件哈希）、**多路径读取的互证**（同一事实的多条路径必须一致）、**Hook 引入的耗时分布偏移**、**Hook 需要常驻的可写可执行内存或常驻 trampoline**（即使还原字节，trampoline 页仍在）、**函数指针的段权限与模块归属**（跳板会让指针指向匿名页或 `rw-` 段）、**`openat2` 与 `openat` 两条 syscall 的读取结果一致**（入口不同，同时伪造要动两套分发）。

### 2.9 文件系统视图一致性（FOPS-001，新类别 `fops`）

**现状能力**：打开 `/proc/self/fd` 后，先用 `getdents64` 枚举所有纯数字条目，再对 0–511 中**未出现**的 fd 号逐个 `readlinkat(dir, "N")`。真实的 fd 一定同时满足「目录里有」与「按名字能读到指向」；只有「目录里看不到、但按名字仍 `readlink` 成功」才计入 `hidden_entries`，> 0 即 0.85 的强证据。

**未来可能的技术绕过**：

1. 只在 `getdents64`（或 `iterate_dir`）里过滤目录项，路径解析不动——这正是 FOPS-001 要抓的形态：**目录看不到 ≠ 路径不可达**。隐藏套件把 `/data/adb`、模块目录、可疑进程从列表里摘掉时，最容易只做这一层。
2. 反过来只改路径解析（让 `readlinkat` 对目标 fd 返回 `ENOENT`），但目录里仍列出来——方向相反的不一致同样暴露；当前实现只统计「目录缺失 + 路径可达」一侧，反向不一致属可扩展方向。
3. 对 `/proc/self/fd` 做 per-process 的完整视图伪造，让枚举与解析都指向同一份假快照——需要同时拦截 `proc` 的 `readdir` 与 `readlink` 两套回调，且要与 `stat`/`open` 的行为自洽。

**兜底检测思路**：

- **枚举与直接访问必须一致**：这条判据不依赖任何文本内容，只依赖「同一个对象，两种访问方式给出不同答案」这一逻辑矛盾。只做目录级过滤时，按名字访问仍然成功；要消除矛盾就必须同时改路径解析，而路径解析一改会波及所有进程的 `stat`/`open` 行为。
- **与 MNT 系列互补**：MNT-001 / MNT-006 比的是「挂载文本 vs 返回值」，FOPS-001 比的是「目录枚举 vs 按名解析」，三者合起来覆盖挂载层、文本层与目录层。
- **竞态要先排除**：干净设备上偶发的 `hidden>0` 多半是「枚举之后新开了 fd」造成的（ART、socket、数据库都可能），不是过滤。验收时应复测两次再定性，详见 02 文档 §2.9。
- 可扩展方向（当前未实现）：把「枚举 vs 直接访问」扩展到 `/proc/self/task`、`/data/app`、`/system/lib64` 等目录；对「路径不可达但目录可见」的反向不一致也计入。

**痕迹属性**：

- 可完全擦除：单次 `getdents` 的文本、单个目录项的可见性。
- 很难彻底抹除：**目录枚举与路径解析的一致性**（只改一侧立刻产生矛盾；两侧都改要动 VFS 的 `readdir` 与 `lookup` 两条路径，且要与所有进程的访问行为自洽）。

## 3. 可完全擦除 vs 本质性痕迹（总表）

| 痕迹 | 所属类 | 能否被完全擦除 | 原因 | 本方案对应项 |
| --- | --- | --- | --- | --- |
| 模块文件、so 路径、`/data/adb` 目录 | Mount / Zygisk | 能 | 纯用户态文件，删掉即无痕 | MNT-004、ZYS-001、ZYS-003 |
| 进程名、cmdline、comm | KSU | 能 | 用户态可写、可随机化 | KSU-001 |
| `/proc/<pid>/mountinfo` 文本 | Mount | 能 | 内核 seq_file 可被过滤 | MNT-002、MNT-004 |
| 单次 `stat` / `statx` 返回 | Mount | 能 | 返回值可被伪造 | MNT-003 |
| 单次 syscall 返回值、单次耗时 | Kernel | 能 | 单点数据无记忆 | KRN-001、KRN-003 |
| bpf fd / map id | BPF | 能 | 可以不留 fd | BPF-001、BPF-002 |
| 属性值、AVB 属性 | SELinux | 能 | 属性区可被重置 | SEL-003、SEL-005 |
| `TracerPid`、ptrace 会话 | Inject | 能 | detach 后消失 | INJ-002 |
| **`statx` `mnt_id` 与 `mountinfo` 的物理一致** | Mount | **很难** | 一个路径只有一个真实挂载归属，伪造文本必须同步伪造所有路径的 statx，且跨进程自洽 | MNT-001、MNT-007 |
| **跨进程 inode/dev 一致** | Mount | **很难** | init、system_server、app 看到同一文件必须有相同 inode/dev | MNT-002、MNT-003 |
| **父进程链 / pgrp / sid 的结构一致** | KSU | **很难** | 需要改多个 task 字段并与 `wait4`/`getpgid` 返回值一致 | KSU-003、KSU-002 |
| **cred 与 `/proc` 视图互证** | Kernel | **很难** | 有 root 能力却报 0 能力，会让能力相关 syscall 行为矛盾 | KRN-004、SEL-001 |
| **syscall 耗时统计分布** | Kernel | **很难** | 任何内核 hook 都会改变长尾分布，单次可优化、分布难伪装 | KRN-001、BPF-003 |
| **代码段自校验（内存 ↔ 快照）** | 反 Hook | **很难** | 只要 hook 就必须改写代码页，还原需要精确的时序窗口 | AHK-003、AHK-001 |
| **直调 syscall 与 libc 的双路径一致** | 反 Hook | **很难** | 只 hook 一条路径必暴露；两条都 hook 会改动 libc 入口 | AHK-002 |
| **JNI 函数表与表指针** | 反 Hook | **很难** | 替换表必须让指针指向可执行映射，且要覆盖所有使用槽位 | AHK-004 |
| **进程内存布局的整体自洽** | Zygisk / Inject | **很难** | 注入必须留下可执行页或改写已有页 | ZYS-001、ZYS-004、INJ-001 |
| **属性区与磁盘 build.prop 的双源一致** | SELinux | **很难** | 同时改磁盘会导致 AVB 状态变化 | SEL-005、SEL-004 |
| **系统分区只读性与 AVB green 的相容** | SELinux | **很难** | rw 挂载与 locked/green 不可同时成立 | SEL-004、SEL-003 |
| **内核函数多语义一致性** | Kernel | **很难** | `getpid`/`gettid`/`stat` 等多个 syscall 必须给出相容答案 | KRN-003、AHK-002 |
| `statfs` 的 `f_flags` 与 mountinfo 的 ro/rw | Mount | 能（单点） | 两个接口各自可被伪造，但同时改才不矛盾 | MNT-008 |
| `statx` 的 `stx_dev` 与 mountinfo 登记的 dev | Mount | 能（单点） | 同上；覆盖式挂载本来就会产生真实差异，需区分信号与误报 | MNT-009 |
| **`btime` / `/proc/uptime` / `CLOCK_BOOTTIME` 三者一致** | Kernel | **很难** | 三者来自 RTC 基准、tick 累加与时钟源三本账，同步伪造会波及全系统的时间观 | KRN-006 |
| **syscall 返回码与 errno 的语义正确性** | Kernel | **很难** | 伪造层必须对「不存在路径 / 空路径 / 正常文件」三类语义同时正确，任一处改写就与另一处矛盾 | KRN-007 |
| **可执行映射的来源路径** | Inject | **很难** | 注入代码必须落在真实文件或匿名/memfd 段：路径要么可追溯、要么就暴露匿名段 | INJ-005、AHK-005 |
| **函数指针的段权限与模块归属** | 反 Hook | **很难** | 跳板会让指针指向匿名可执行页（`dladdr` 失败）或 `rw-` 段（不可执行），二者必有一项对不上 | AHK-005 |
| **`openat2` 与 `openat` 两条 syscall 的读取结果** | 反 Hook | **很难** | 两条路径内核入口不同；只挂 libc 符号对直调 `SYS_openat2` 无效，两边都改要动两套分发 | AHK-006 |
| **目录枚举结果 vs 按名直接访问** | 文件系统视图（fops） | **很难**（只过滤一侧必暴露） | 只改 `getdents` 时按名字仍可达；两侧都改要动 VFS 的 `readdir` 与 `lookup`，波及所有进程 | FOPS-001 |
| 线程名（`comm`） | Zygisk | 能 | `prctl(PR_SET_NAME)` 可任意改，属纯用户态文本 | ZYS-007 |
| **Java 静态字段（启动快照）vs 属性区当前值** | Zygisk | **很难** | 快照早于运行期改写；要消除必须提前到 `Build` 类初始化之前，且与磁盘 `build.prop` 自洽 | ZYS-008、SEL-005 |

> 结论：把判据建立在表格上半部分（可擦除项）上的检测项，只能作为「发现低级隐藏」的快速信号；真正抗对抗的是表格下半部分的**物理一致性、多路径互证、时间分布、代码段自校验**。1.0.1-rc 新增的 10 项里只有 ZYS-007（线程名）落在上半部分，其余 9 项都落在下半部分：跨接口同义（MNT-008/009）、时间账本（KRN-006）、errno 语义（KRN-007）、映射来源（INJ-005）、指针归属（AHK-005）、双 syscall（AHK-006）、目录枚举（FOPS-001）、静态字段快照（ZYS-008）。

## 4. 二阶对抗

二阶对抗指：攻击者已经知道本 RASP 的存在，并针对**检测函数本身**下手（Hook、伪造输入、专项免杀）。此时不能指望单条证据，必须依赖「检测过程本身的可观测性」。

### 4.1 隐藏模块 Hook 检测函数

**攻击形态**：Hook `rasp_emit` / `rasp_score_compute` / `rasp_build_report_json`，或替换 JNI 表，让报告直接输出 `score=0`；或让检测函数读到伪造的 `/proc` 内容。

**兜底手段**：

1. **自校验快照**（AHK-003）：`JNI_OnLoad` 时对自身热代码取指纹，检测末尾重算。Hook 检测函数必然改写代码页 → 哈希变化。局限：加载前改文件可绕过（需签名校验，未实现）。
2. **入口形态校验**（AHK-001、INJ-003）：libc 与 libart 关键符号的入口指令必须是正常序言，跳板/断点/全零直接判可疑。
3. **双路径互证**（AHK-002）：同一事实（`/proc/self/status`、`/system/build.prop` 元信息、`getpid`）分别用直调 syscall 与 libc 读取，逐字节比较；1.0.1-rc 再加一条 `openat2` vs `openat`（AHK-006）：同一个文件走两条入口不同的 syscall，只挂 libc 符号必暴露。
4. **JNI 表校验**（AHK-004）：表指针 + 关键槽位必须指向可执行映射。
5. **子进程重放**（MNT-007、SBX-001）：检测逻辑在 `clone3` 出的子进程里重跑一次关键读操作。用户态 Hook 通常只覆盖主进程（要覆盖 fork 出的子进程需要 ptrace 或内核级注入，成本更高且会留下 INJ-002 痕迹）。
6. **元信号**（见 §4.3）：即使分数被篡改，报告的可用率、耗时、证据条数、结果矛盾仍会暴露。

**必须承认的局限**：如果攻击者在 APK 安装前就替换了 so 文件，上述所有自校验都以被污染的基线运行。本方案没有签名校验（`PackageManager` 签名摘要校验未实现），这是已知边界。

### 4.2 完全伪造 `/proc` 视图

**攻击形态**：内核模块让目标进程读到的 `mountinfo`、`status`、`maps`、`version`、`attr/current` 全部是精心构造的假数据，且互相自洽；甚至让 `statx` 返回与假视图匹配的 `mnt_id`。

**兜底手段**：

1. **父子双读哈希**（MNT-007）：父进程读一次、子进程读一次，两次结果的哈希必须完全相同。攻击者要伪造，必须保证两个进程在不同时刻读到逐字节相同的假数据——这要求伪造层是确定性的、且覆盖 fork 后的子进程。
2. **`mnt_id` 物理一致**（MNT-001）：假 `mountinfo` 里的 id 集合必须覆盖所有被探测路径的 `statx.mnt_id`。这是一组「文本 ↔ 返回值」的约束，单独伪造文本会让 `mnt_id` 找不到归属。
3. **跨进程比对**（MNT-002、MNT-003）：让 `init` 与 `system_server` 也返回与 app 自洽的假视图，攻击面从 1 个进程扩展到 3 个进程 + 所有被比对路径。
4. **双读取路径**（MNT-006）：直调 syscall 与 libc 各读一次。伪造必须同时覆盖两条路径，否则逐字节比较直接暴露。
5. **时序侧信道**（KRN-001、BPF-003）：伪造层要拦截每次读取并构造内容，会在耗时分布上留下尾巴；即使单次差异很小，统计量也会偏移。
6. **反向探针**（KRN-007 已实现 errno 语义探针；其余仍属可扩展）：读取不存在路径的 errno、空路径的返回值、正常文件能否打开——伪造层很难对所有边界情况都给出与真实内核一致的行为。尚未实现：读空文件的长度、`(deleted)` 标记、`fstat` 与 `stat` 的交叉比对。
7. **目录级一致性**（FOPS-001）：`getdents64` 的枚举结果必须与「按名字直接访问」一致。伪造挂载文本可以骗过 MNT 系列，但只要过滤做在目录层，按名字访问仍然成功，矛盾立刻暴露。

### 4.3 针对本 RASP 的专项免杀：元信号

当攻击者开始「只针对本 App 做免杀」时，报告本身的**形状**会先于内容暴露问题。以下信号不依赖任何单条检测项，建议在报告消费侧（UI / 导出 / 服务端）做二次判读：

| 元信号 | 正常基线 | 异常形态 | 判读 |
| --- | --- | --- | --- |
| 可用率 | `counts.available / counts.total` 接近 1（51/51） | 显著下降（如 < 0.8），或固定若干项恒为 `available=false` | 检测被系统性阻断；**「不可用」不等于「安全」** |
| 反 Hook 与自校验的矛盾 | `antiHook.hit=false` 且 AHK-001～006 全部 `available=true` | `antiHook.hit=false` 但 AHK 某项 `available=false`、或 `error` 非空 | 自校验被跳过或被提前短路 |
| 分数与命中数矛盾 | `hits=0` ↔ `score=0`；`hits≥3` ↔ `score>0` | 高 `hits` 却 `score=0`（v3 默认模板下几乎只能是异常豁免）、低 `hits` 却高分（权重被覆盖） | 白名单/权重配置异常，或报告被篡改 |
| 耗时骤降 | 完整模式数百毫秒级、各项耗时梯度合理 | `durationMs` 异常小（如 < 50ms）且 `available` 偏低 | 检测被短路（函数被 Hook 后直接返回） |
| 耗时骤升 | 完整模式数百毫秒级 | `durationMs` 接近或超过 5 s，且 `available` 并未下降 | 某模块反复重试/熔断，可能有人在探测或干扰 |
| 证据条数不完整 | 流式回调条数 ≈ `counts.total`（未开 disabled 时 51） | 回调条数明显少于 `counts.total` | 结果被截断或部分检测项静默失败 |
| 单项内部矛盾 | `MNT-001`：`mnt_ids_missing=0` 且 `paths_checked>0`；`MNT-007`：`hash_equal=true`；`KRN-006`：两个 delta 在 8 s / 5 s 内；`KRN-007`：`anomalies=0`；`FOPS-001`：`hidden_entries=0` | `MNT-001` checked>0 但 `mountinfo_entries` 远低于同机型基线；`MNT-007` 父子条目数不同却 `hash_equal=true`；`FOPS-001` 连续两次命中同一 fd 号 | 视图被裁剪、哈希被篡改，或目录层被过滤 |
| 置信度贴边 | `confidence` 在 0.3–0.9 之间 | 恰好等于 0.05 或 0.98（clamp 边界） | 权重/置信度被污染的可能性上升 |
| 证据分布突变 | 同类设备多次检测的命中项集合稳定 | 同一设备两次检测中某类**全部** miss 且 `raw` 为空字符串 | 采集被定向过滤 |
| 时间戳形态 | items 的 `ts_ms` 单调递增、有梯度 | 多个 item `ts_ms` 完全相同，或顺序倒置 | 报告被合成/重放 |

说明：当前报告**没有输出单项耗时**（`rasp_evidence_t.cost_ms` 字段存在但未参与序列化），元信号只能依赖模块级 `durationMs`、`counts`、`items[].ts_ms` 与流式回调节奏。若要在报告中加入单项耗时，属于代码变更（本文档不实施）。

**免杀对抗的底线思路**：不要试图「猜攻击者的下一个手法」，而是把判据收敛到 §3 下半部分的物理约束上，并让「检测没跑成」本身变成高风险信号。检测项被关闭（`disabled`）、不可用（`available=false`）、结果被截断（回调条数不足）——这三种情况都应在产品侧呈现为「无法判定」，而不是「安全」。

## 5. 检测边界（明确做不到的事）

| 做不到 | 原因 | 影响 |
| --- | --- | --- |
| 读取内核内存 / 内核数据结构 | 无 Root、无 `/dev/kmem`、无 bpf | KRN 系列只能是间接推断 |
| 调用 `bpf()` 或枚举系统级 bpf 程序 | 普通应用无权限 | 只能看自己进程的 fd |
| `setns` 进入 `init` / `system_server` 的 namespace | 需要 `CAP_SYS_ADMIN` | 跨视图只能靠 `pidfd` 读可读文本 |
| 阻止或反制注入 | 本方案只检测、不攻击 | 对抗环境里检测函数本身可能被 Hook，靠 §4 的兜底 |
| 校验 APK/so 签名 | 未实现 | 加载前被改文件可绕过 AHK-003 |
| 发现「内核态完全自洽的伪造」 | 物理上无法从用户态区分 | 只能靠时间侧信道与元信号，置信度有限 |
| 在同一时刻伪造「目录枚举 + 路径解析 + 双 syscall + 时间账本」 | 需要改 VFS 的 `readdir`/`lookup`、两条 syscall 分发与内核时间记账，且要与所有进程的访问行为自洽 | 属 L4 能力；用户态只能靠这类跨接口矛盾抬高成本，无法反制 |
| 覆盖非 KSU 的其它 root 方案 | 特征库未覆盖 | 本方案定位为 KSU/隐藏套件专项 |

## 6. 结论与合规声明

1. **没有「不可检测」的隐藏，也没有「不可绕过」的检测。** 本方案的价值在于：把隐藏套件的成本从「改一个 `/proc` 文件」抬高到「同时伪造多个进程的多条观测面，抹掉时间与内存布局痕迹，并让目录枚举、syscall 语义与属性快照互相自洽」（1.0.1-rc 把这类观测面扩到 51 项）。
2. **判据的优先级**：物理一致性（mnt_id/ino/dev/cred）> 跨接口同义（`statfs`↔mountinfo、`statx` dev↔mountinfo、`openat2`↔`openat`、目录枚举↔按名访问）> 多路径互证（raw/libc、父子进程、Java 静态字段↔属性区）> 时间账本与 errno 语义 > 时间分布 > 文本特征（进程名、线程名、路径、属性值）。文本特征只能作为快速信号，不能作为唯一判据。
3. **「不可用」必须被视为风险信号**，而不是「没发现问题」。产品侧对 `available` 偏低、回调不完整、耗时异常的报告，应提示「无法判定」。
4. **本文档仅用于检测取证与防护加固**：不提供任何 Hook、注入、隐藏、免杀、绕过 KernelSU 或其检测的实现；不包含任何需要 Root 才能运行的逻辑；全部检测在设备本地完成，不做 SafetyNet / Play Integrity 等远程校验。
5. 若后续要落地本文档中的「可扩展方向」（签名校验、ArtMethod 互证、单项耗时上报等），属于代码变更，需要单独评审并同步更新 02 / 04 文档。
