# 02 误报规避与白名单机制

> 对应《生成要求》④「误报规避策略」。
> 适用版本：aegis-rasp/1.0.1（versionCode 3；native，API 35）· 51 个检测项（8 大类 + 沙箱独立性 + 文件系统视图一致性）· 打分模型见 [rasp_score.c](../rasp-detect-native/src/main/cpp/rasp_score.c)。
>
> 本文档描述的是**已经实现的行为**，不是设计愿景。凡是「现状」「实测推算」「建议」三种措辞，分别代表：代码当前行为、按源码静态推算的数值、尚未落地的改进方向。文中不虚构任何源码中不存在的接口。
>
> **本轮同步说明**：白名单已做第三版收敛——片段与检测项 ID 完全相等可显式豁免；非 ID 片段要求 ≥ 10 字节、不以 `/` 开头、且不在通用进程名黑名单中；强证据额外要求片段 ≥ 14 字节且含 `=`、`.` 或 ` on `；native 内部片段分隔符由空格改为分号，多词锚点得以完整保留。`whitelist_default.json` 升到 version 3。原先「MNT-002/KSU-003/KRN-002 被整条豁免」「mounts 数组空转」的结论均不再成立。
>
> **1.0.1-rc 同步说明**：检测项 41 → 51，新增 10 项（MNT-008、MNT-009、KRN-006、KRN-007、INJ-005、AHK-005、AHK-006、FOPS-001、ZYS-007、ZYS-008），其中 FOPS-001 属于**新类别 `fops`**。本轮**没有改动白名单模板与匹配规则**（仍为 version 3）：新增项全部落在「不豁免」面内，原因见 §1.4；`fops` 只进入打分的分桶表（[rasp_score.c:19-24](../rasp-detect-native/src/main/cpp/rasp_score.c#L19-L24)），不参与豁免判定。权重（30/10/3）、同类 `0.7^n` 衰减、单强 25 下限、反 Hook 85 下限与阈值 20/50 均未变化。

## 0. 结论摘要

本方案的误报控制由三条互相独立的防线组成，任何一条都不能单独承担「干净设备判安全」的责任：

| 防线 | 实现位置 | 作用 | 局限 |
| --- | --- | --- | --- |
| 分级白名单（系统级 / 设备级 / 应用级） | `assets/whitelist_default.json` → `WhitelistLoader.loadForNative()` → `rasp_extract_array()` → `ctx.wl_*` → `evidence_whitelisted()` | 命中片段即豁免单条证据，不计入打分 | 片段必须「足够具体」；默认模板已无「无条件豁免任何检测项」的条目（见 §1.4） |
| 置信度 + 同类衰减 | `rasp_score_compute()`：`w = 权重 × confidence`，同类 `0.7^n` | 压制同类重复证据、压制低置信度线索 | 不能修正「证据本身判错」 |
| 消解规则 | 单强证据下限 25、单一弱线索 ×0.5、阈值 20/50、反 Hook 下限 85 | 避免「一条线索直接判死」和「噪声抬分」 | 需要真机基线校准，见 04 文档 §6 |

上线前必须知晓的五点（细节见 §1.3、§1.4、§2.10）：

1. **默认模板不再无条件豁免任何检测项**。只有 3 个 ID 存在「条件豁免」：MNT-004（示例恰为 `overlay on /system_ext`）、ZYS-005 / ZYS-006（差异列表里出现被收录的系统包名）。
2. **通用进程名被永久排除**：`system_server`、`zygote64`、`zygote`、`init`、`surfaceflinger`、`servicemanager` 六个词即使写进模板也不会生效，因此它们不会再把 MNT-002 / KSU-003 整条豁免。
3. **强证据有特异性门槛**：片段需 ≥ 14 字节且含 `=`、`.` 或 ` on `，否则不允许豁免强证据——避免「证据正文里恰好出现某个普通词」就把 30 分的强证据清零。
4. 报告 `counts.hits` 统计的是「原始命中数」，包含被白名单豁免的项；`score` 不含被豁免项。所以可能出现 `hits>0` 而 `score=0` 的报告，解读时必须区分。
5. **新增的 10 项在默认模板下同样不被豁免**：它们的 raw 里没有 ≥ 10 字节且具体的锚点；`fops` 只是新的打分分桶，不改变匹配语义（见 §1.4、§2.1、§2.3、§2.5、§2.6、§2.8、§2.9）。唯一理论边缘是 ZYS-008 的 raw 含机型与指纹原值（见 §2.5）。

## 1. 分级白名单机制

### 1.1 三级白名单的覆盖对象与本实现落点

白名单 JSON 有 6 个数组字段（`mountPaths` / `mounts` / `processes` / `properties` / `kernel` / `oem`），其中 `mountPaths` 只作文档说明、**不参与匹配**（native 只解析 5 个数组，见 §1.2）。三级白名单是通过**字段选择 + 条目内容**表达的，不存在单独的「级别」字段：

| 级别 | 需求覆盖对象 | 本实现使用的字段 | 默认模板示例（v3 实际条目） | 豁免生效方式 |
| --- | --- | --- | --- | --- |
| 系统级 | CloreOS 原厂固件特征、官方系统 overlay、厂商内置调试模块、系统核心进程 | `oem[]`、`processes[]`、`mounts[]`、`kernel[]` | `ro.build.display.id=CloreOS`、`ro.cloreos.`、`com.android.systemui`、`CONFIG_KSU=n`、`overlay on /system_ext`、`tmpfs on /apex` | 片段在证据 raw 中出现，且满足长度/特异性/非通用名要求 |
| 设备级 | 正常 userdebug 固件、官方模拟器、通用虚拟机容器指纹 | `properties[]`、`kernel[]`、`mountPaths[]`（仅文档） | `ro.build.tags=release-keys`、`ro.build.type=user`、`ro.boot.verifiedbootstate=green`、`ro.boot.veritymode=enforcing`、`ro.kernel.version=` | 同上 |
| 应用级 | 业务自身的特殊配置、合法调试工具 | 运行时通过 `WhitelistLoader.loadForNative(context, extraJson)` 的 `extraJson` 参数叠加；也可直接放检测项 ID（如 `MNT-004`）做显式豁免 | `com.example.debugtool`、`MNT-004` | 合并去重后下发；ID 片段命中即豁免该检测项 |

要点：

- **默认模板只收录合法系统 / OEM / 调试环境特征**，仓库不预置任何具体业务包名。
- `schema`、`version`、`note`、`mountPaths` 只用于人工维护，native 侧**不解析**；native 只读取 5 个数组（见 [rasp_jni.c:164-172](../rasp-detect-native/src/main/cpp/rasp_jni.c#L164-L172)）。
- 白名单的「级别」只影响条目放在哪个数组里；由于评分时 5 个池会合并查找（见 §1.3），**数组归属不改变匹配语义**（只有长度/特异性/通用名规则会改变结果）。

### 1.2 native 侧数据通路（从 assets 到豁免判定）

```
assets/whitelist_default.json（version 3）
   │  WhitelistLoader.loadDefault()            （Kotlin，读 assets；只解析 5 个数组）
   │  WhitelistData.merge(extra)               （去重合并；extra 由调用方传入）
   │  WhitelistData.toJson().toString()        （重新序列化：只输出 5 个数组 + schema=1 + version=1）
   ▼
RaspNative.runDetect(configJson, whitelistJson, weightSpec, sink)
   │  jni_run_detect()                          rasp_jni.c
   │  rasp_extract_array(wl, "mounts",     ctx.wl_mount , 768)   ← 条目之间用 ';' 拼接
   │  rasp_extract_array(wl, "processes",  ctx.wl_proc  , 768)
   │  rasp_extract_array(wl, "properties", ctx.wl_prop  , 1024)
   │  rasp_extract_array(wl, "kernel",     ctx.wl_kernel, 768)
   │  rasp_extract_array(wl, "oem",        ctx.wl_oem   , 768)
   ▼
rasp_score_compute() → evidence_whitelisted()
   │  5 个池合并，按 ';' 切分条目（多词锚点保持完整）
   │  ① 条目 == 检测项 ID            → 豁免
   │  ② 条目 >= 10 字节、非 '/' 开头、非通用进程名
   │  ③ 强证据还需条目 >= 14 字节且含 '='、'.' 或 ' on '
   │  ④ 在 e->raw 上做子串查找，命中则豁免
   └─ 豁免 → continue（该条证据不进入分值，但仍留在报告 items 中）
```

两个容易被忽略的链路事实：

1. **`mountPaths` 到不了 native**：`WhitelistData` 只声明 5 个列表，`toJson()` 也不输出 `mountPaths`；Asset 里的 `mountPaths` 只服务于人工阅读与后续实现。
2. **`version` 会被重写**：`WhitelistData.toJson()` 固定写 `"schema":1,"version":1`，所以运行时下发给 native 的 JSON 与 asset 里的 `version: 3` 不一致；排查问题时以 native 收到的字符串为准。

关键常量（`rasp_core.h`）：

| 字段 | 容量 | 说明 |
| --- | --- | --- |
| `wl_mount[768]` | 768 字节 | 分号分隔的片段表，超出容量后 `append_token()` 静默丢弃后续片段 |
| `wl_proc[768]` | 768 字节 | 同上 |
| `wl_prop[1024]` | 1024 字节 | 属性能容纳更多条目，仍可能被截断 |
| `wl_kernel[768]` | 768 字节 | 同上 |
| `wl_oem[768]` | 768 字节 | 同上 |

`rasp_extract_array()` 的实现语义（[rasp_util.c:429-472](../rasp-detect-native/src/main/cpp/rasp_util.c#L429-L472)）：

1. 在 JSON 文本中找第一个 `"key"`，再找其后的 `[`；
2. 只提取双引号内的字符串（支持 `\"` 转义跳过），`0 < len < 160` 的条目才收录；
3. 条目之间用**一个分号 `;`** 拼接进目标缓冲（第三版改动，此前是空格）；
4. 容量不足时丢弃该条目，不报错、不告警。

> 同一分隔符也用于 `disabled` 列表：`rasp_emit()` 现在同样按 `;` 切分，设置页关闭某项仍然有效。

### 1.3 匹配算法与六条硬约束

`evidence_whitelisted()`（[rasp_score.c:105-131](../rasp-detect-native/src/main/cpp/rasp_score.c#L105-L131)）的实际逻辑：

```c
for each pool in {mounts, processes, properties, kernel, oem}:
    for each token in pool:                 /* 以 ';' 分割，多词锚点完整保留 */
        if (token_len == strlen(e->id) && strncmp(token, e->id, token_len) == 0)
            return 1;                       /* ① ID 完全相等：显式豁免，不受等级/长度限制 */
        if (token_len >= 10 && token[0] != '/' && !is_generic(token)) {
            if (e->grade != GRADE_STRONG || (token_len >= 14 && is_specific(token))) {
                if (substr_any_offset(e->raw, token)) return 1;   /* ④ raw 子串命中 */
            }
        }
```

其中：

- `is_generic()`：与 `system_server`、`zygote64`、`zygote`、`init`、`surfaceflinger`、`servicemanager` **精确相等**则视为通用进程名，不参与片段豁免；
- `is_specific()`：片段中任意位置含 `=` 或 `.`，或含子串 `" on "`。

由此得到六条必须遵守的约束：

1. **ID 分支优先且不受长度限制**：片段与 `e->id` 完全相等即豁免，7 字符的 `MNT-004` 也有效。默认模板未放任何 ID，需要时应通过 `extraJson` 显式加入。
2. **非 ID 片段至少 10 字节**：`init`(4)、`zygote`(6)、`overlay`(7)、`tmpfs`(5)、`/data`(5) 全部失效；`system_server`(13) 虽够长但被规则 3 排除。
3. **以 `/` 开头的片段一律忽略**：`mountPaths` 里的裸路径、`/dev/__properties__` 形态的条目都不参与匹配。
4. **通用进程名永久排除**：`system_server` 不会再因为出现在 MNT-002 的 `detail` 里而豁免该强证据；`zygote64` 同理。
5. **强证据要求片段「足够具体」**：≥ 14 字节且含 `=`、`.` 或 ` on `；否则即使 raw 命中也不豁免（例如 `proc on /proc`(13) 可豁免间接/弱线索，但不能豁免强证据）。
6. **匹配对象是整条证据 raw JSON，不是单一观测字段**；命中即整条豁免，且**不影响 `hit` / `available`**——豁免是「不计分」，不是「当没发生过」；报告仍保留命中状态与原文。

补充：`rasp_core.h` 里另有一个更朴素的辅助函数 `rasp_whitelisted()`（[rasp_util.c:474](../rasp-detect-native/src/main/cpp/rasp_util.c#L474)），当前**没有任何检测项调用它**，实际豁免完全由 `rasp_score.c` 内的 `evidence_whitelisted()` 完成；阅读代码时不要把它当成生效路径。

### 1.4 默认模板对 51 项的实际豁免面（静态分析，第三版）

按 §1.3 的算法对 `whitelist_default.json`（version 3）逐项推演：

| 状态 | 检测项 ID | 触发条件 / 片段 |
| --- | --- | --- |
| 显式 ID 豁免（默认模板未使用，扩展点） | 任意 ID（如 `MNT-004`） | 模板中出现与 ID 完全相等的片段即豁免该检测项；适合「业务已知误报」，需通过 `extraJson` 加入并留痕 |
| 条件豁免（3 项） | **MNT-004**、**ZYS-005**、**ZYS-006** | MNT-004：`example` 恰好等于 mounts 锚点——当前实际可达的只有 `overlay on /system_ext`（MNT-004 只检查 `/system`、`/vendor`、`/product`、`/system_ext`、`/odm`，故 `tmpfs on /apex`、`proc on /proc`、`sysfs on /sys`、`tmpfs on /dev/__properties__` 目前不会命中它）；ZYS-005 / ZYS-006：`hiddenFromInstalled` / `onlyBinder` 等差异列表中出现 `com.android.systemui`、`com.android.phone`、`com.android.settings`、`com.android.permissioncontroller`、`com.android.providers.media` 时整条豁免（隐藏的通常是第三方包，故很少发生） |
| 不豁免（正常参与打分，共 48 项） | MNT-001、MNT-002、MNT-003、MNT-005、MNT-006、MNT-007、MNT-008、MNT-009、KSU-001～005、KRN-001～007、BPF-001～004、ZYS-001～004、ZYS-007、ZYS-008、INJ-001～005、SEL-001～005、AHK-001～006、FOPS-001、SBX-001 | 无片段同时满足：≥ 10 字节、非 `/` 开头、非通用进程名；强证据还须 ≥ 14 字节且含 `=`/`.`/` on ` |

与第二版相比的关键变化：

- **MNT-002、KSU-003、KRN-002 不再被整条豁免**：`system_server`/`zygote64` 被通用名黑名单排除，`Linux version 5.10/5.15/6.1` 已从模板删除；
- **`mounts` 不再空转**：分号分隔让 `overlay on /system_ext` 这类多词锚点完整保留；但当前可命中证据的只有 `/system_ext` overlay 这一条，其余 4 条锚点是「保留以备扩展」；
- **ID 豁免从不可达变为可用**：7 字符 ID 现在可以直接作为片段；
- **1.0.1-rc 的 10 项全部落在「不豁免」面内**：新项 raw 的结构是「计数 + 路径/设备号/errno/布尔值」，没有任何片段能同时满足长度、非 `/` 开头与特异性要求；`fops` 类别只新增一个打分桶，不新增匹配语义。唯一例外是 ZYS-008 的 raw 里带 `model` / `fingerprint` 原值，若机型名恰好与 `processes[]` 中某个包名相同（或含 `android.hardware.`）才会触发 raw 子串豁免，见 §2.5；
- 默认模板下**没有任何条目无条件豁免某个检测项**，因此「干净设备因白名单泛匹配而低分/高分」的结构性偏差已消除。

使用建议：

- 若确认某个环境存在**合法但会误报**的项（例如企业设备给应用附加 capability 触发 KRN-004），优先用 ID 片段（`KRN-004`）显式豁免，并在变更记录里写明原因；
- 不要把「证据 raw 正文里本来就有的词」当作片段（例如 `tcph`、`release-keys`、模块路径片段），否则等于给该证据开后门；
- `mounts` 锚点只对「示例文本恰好等于该锚点」的 MNT-004 生效；若发现某个合法 OEM overlay 仍被误报，应新增对应锚点（例如 `overlay on /odm`），而不是关闭 MNT-004。

## 2. 逐检测项误报场景表（51 项全覆盖）

列说明：
- **基础贡献** = 等级权重（强 30 / 间接 10 / 弱 3）× 该分支置信度；实际得分还要乘同类衰减 `0.7^n`（n = 同 category + 同 grade 的前序命中数，最大按 3 计）。
- **默认模板** 列的结论来自 §1.4 的静态推演。

### 2.1 Mount Namespace 与文件视图（9 项）

| ID | 等级 | 正常场景（误报来源） | 过滤规则（实现） | 基础贡献 | 默认模板 |
| --- | --- | --- | --- | --- | --- |
| MNT-001 | 强 | 内核 < 5.8 不返回 `stx_mnt_id`；挂载条目超过 768 条（`MI_MAX_IDS`）或 1024 行（`MI_MAX_LINES`）时被截断，后段挂载点会「查不到 id」；个别路径 statx 失败 | `checked == 0` → 置 `available=0` 不参与判定；仅 `mnt_ids_missing > 0` 才 hit，并把缺失路径写进 raw | 0.90 → 27.0 | 不豁免（路径片段以 `/` 开头） |
| MNT-002 | 强 | SELinux 拒绝读取 init / system_server 的 mountinfo（`compared == 0`）；正常 OEM overlay 造成的标志差异 | 行数比容差 90%–115%；只有 overlay/tmpfs 标志翻转或行数越界才计；无可用比对时 `available=0` 并带 error | 0.85 → 25.5 | 不豁免（`system_server` 属通用名） |
| MNT-003 | 强 | 32 位机型或路径变体没有 `/system/bin/app_process64`（`compared=0`）；跨进程 statx 被 EACCES | 无任何可读视图时置 `available=0`；只有 ino/size/dev 不一致才 hit | 0.85 → 25.5 | 不豁免 |
| MNT-004 | 强 | OEM 把 tmpfs 挂到系统分区；userdebug `adb remount`；加固 ROM 自带 overlay | 只在 `/system`、`/vendor`、`/product`、`/system_ext`、`/odm` 上判；`/data/adb` 单独加分 | 0.50 overlay + 0.30 tmpfs + 0.40 `/data/adb` + 0.50 KSU/worker + 0.30 重复挂载点，cap 0.95 → ≤28.5 | 条件（示例为 `overlay on /system_ext` 时） |
| MNT-005 | 间接 | `/storage`、`/mnt` 的正常 shared propagation | 必须 `shared_prop > 0` **且** 同时存在 `rw_system` / `tmpfs_on_system` / `overlay_on_system` 之一 | 0.50 → 5.0 | 不豁免（示例不以锚点开头） |

### 2.9 文件系统视图一致性（fops，1 项）

1.0.1-rc 新增的类别 `fops`（[rasp_score.c:19-24](../rasp-detect-native/src/main/cpp/rasp_score.c#L19-L24) 的 `kCategories`）。**它只进入打分分桶表，不改白名单匹配**：`evidence_whitelisted()` 从不读 `e->category`，所以「新增类别会不会改变豁免」的答案是**不会**。它影响的是同类衰减——FOPS-001 的强证据与 mount / antihook 的强证据**不共享** `dup[cat][grade]` 桶，既不会被其它强证据的 `0.7^n` 压掉，也不会去压它们。

干净设备上的预期值是 `hidden_entries=0`。若偶发 1 条，先看 `detail` 指向的 fd 目标（`socket:[…]`、`anon_inode:…`、`/data/…`）：目标若是在枚举之后才新建的（socket、eventfd、数据库临时文件），应判为**竞态**；同一台设备连续两次命中同一个 fd 号，才按真实目录过滤归档。

### 2.10 ART 固有映射：已从判据中排除（修复记录与残留）

修复前后对照（`rasp_maps_stats`，[rasp_memory.c:81-113](../rasp-detect-native/src/main/cpp/rasp_memory.c#L81-L113)）：

| 观测 | 修复后处理 | 对干净设备的影响 |
| --- | --- | --- |
| `memfd:jit-cache`、`jit-zygote-cache` 等 ART JIT 映射 | `is_jit` 判定（路径含 `jit` / `dalvik` / `boot.art` / `boot.oat`）后，不再计入 `rwx` / `memfd_exec` / `deleted_exec` | 不再产生 ZYS-001 的 `memfd_exec` 证据 |
| `libart.so` 的 rw 数据段（ELF `.data`，天然可写） | `art_writable` 改为只统计 **`w && x`** 的 libart 段 | 不再产生 ZYS-002 / ZYS-004 的 `libart_code_writable` 证据 |
| 单段 rwx（部分 ROM 的常规映射） | ZYS-001 / ZYS-004 / INJ-001 的阈值都改为 `rwx > 1` | 单段 rwx 不再命中，需 ≥ 2 段 |
| 匿名可执行段 | 阈值从 `> 2` 提到 `> 3`（ZYS-001 / INJ-001） | 少量 ART/图形匿名页不再命中 |
| 大块匿名 rw（> 64 MB） | INJ-001 阈值从 `> 6` 提到 `> 12` | 正常图形/相机大缓冲不再命中 |

结论：干净设备上 ZYS-001 / ZYS-002 / ZYS-004 / INJ-001 不再有「ART 基线分」，04 文档中干净场景的预期分数已相应校准到 0–24 区间（典型 0–3）。

残留误报源（均已显著低于单条强证据下限，不会单独把分数推进「可疑」）：

| 残留来源 | 命中项 | 分值 |
| --- | --- | --- |
| Intel 翻译层设备的 `native.bridge` 非 0（libhoudini / libndk_translation） | ZYS-002（conf 0.40） | 间接 10 × 0.40 = 4.0 |
| 厂商加固 / 热修使用非 JIT 的 `memfd:` 加载 so | ZYS-001（conf 0.50） | 5.0 |
| 应用自更新后残留的 `(deleted)` vdex/odex | INJ-004（conf 0.50）、ZYS-001（`deleted_exec` 0.45） | 5.0 / 4.5 |
| 个别 ROM 同时存在 ≥ 2 段非 JIT rwx | ZYS-004（0.45，强证据）、ZYS-001（0.55）、INJ-001（0.50） | 13.5 / 5.5 / 5.0 |
| 模拟器 / 调试环境从 `/data/local/tmp` 加载 so | INJ-005（conf 0.70） | 10 × 0.70 = 7.0 |
| NTP 校时，或厂商内核的 `/proc/uptime` 不含 suspend（深度休眠后） | KRN-006（conf 0.45 / 0.90） | 4.5 / 9.0 |

> 1.0.1-rc 新增项里有**两处不能只按「残留低分」处理**的误报，必须先复测再定性：**AHK-006** 在两次读取之间发生挂载/卸载时给 0.92 并置 `anti_hook_hit=1`，直接触发 85 下限；**FOPS-001** 的枚举竞态给 0.85 的强证据（单条 26 分，落「可疑」）。排查顺序是：同一构建复测一次 → 看 raw（AHK-006 比两个长度差多少；FOPS-001 看 `detail` 的 fd 目标是否为枚举后新建）→ 最后才考虑用 `extraJson` 加 ID 豁免并留痕。**不要为这两处噪声改判据或降权重。**

## 3. 误报消解规则（与打分模型的耦合）

### 3.1 四条规则与实现

| 规则 | 需求原文 | 实现 | 精确效果 |
| --- | --- | --- | --- |
| 单一弱线索不升级 | 单一弱线索不触发风险升级 | `if (total_hits == 1 && weak_hits == 1) score *= 0.5;` | 该条弱线索得分减半；由于弱线索本身只有 3 分，通常落到 0–2 分 |
| 白名单豁免 | 系统白名单内特征自动豁免，不计入打分 | `evidence_whitelisted()` 命中即 `continue` | 该条 0 分，但报告仍保留 `hit=true` 与 raw |
| 多证据加权 | 冲突时加权而非直接判定 | 强 30 / 间接 10 / 弱 3，各自乘 confidence，同类 `0.7^n` | 不同维度叠加才可能进入高风险，见 §3.3 |
| 首次未知特征只标可疑 | 首次未知特征标记可疑 | 单条强证据把下限抬到 25（>20 → suspicious），不直接进 high | 25–50 之间保持「可疑」，由 UI 引导人工确认 |

### 3.2 衰减公式

对第 i 条命中证据（未被豁免）：

```
w_i    = weight(grade_i) × confidence_i            # 强 30 / 间接 10 / 弱 3
n_i    = 该 (category, grade) 组此前的命中条数，取值 0,1,2,3（封顶）
score += w_i × 0.7^(n_i)
```

`dup[cat][grade]` 只在 `hit` 且未被豁免时递增，且**封顶 3**：即同类第 4 条及以后都按 `0.7³ ≈ 0.343` 计入。这让「同类堆 10 条间接证据」最多贡献约 `10×(1+0.7+0.49+0.343×7) ≈ 45.9`，而不是 100。

最终修正：

```
if (strong_hits > 0 && score < 25)      score = 25     # 单强证据下限
if (anti_hook_hit && score < 85)        score = 85     # 反 Hook 直接高风险
if (total_hits == 1 && weak_hits == 1)  score *= 0.5   # 单一弱线索减半
score = clamp(score, 0, 100)
level = score > 50 ? "high" : (score > 20 ? "suspicious" : "safe")   # 用未四舍五入的 score 判级
report.score = (int)(score + 0.5)
```

### 3.3 边界示例（可直接用于验收对账）

| 场景 | 命中 | 计算 | 结果 |
| --- | --- | --- | --- |
| 只有一条 KRN-005（`kptr_restrict=0`） | 1 条弱线索，conf 0.25 | 3×0.25 = 0.75 → 单弱 ×0.5 = 0.375 | `score=0`、`level=safe`；但 items 里 KRN-005 的 `hit=true` |
| 只有一条 SEL-003（模拟器 boot 状态 orange） | 1 条弱线索，conf 0.55 | 3×0.55 = 1.65 → ×0.5 = 0.825 → 四舍五入 | `score=1`、`safe` |
| 只有一条 ZYS-002（Intel 翻译层 native.bridge） | 1 条间接证据，conf 0.40 | 10×0.40 = 4.0 | `score=4`、`safe`（间接证据不会触发下限） |
| 只有一条 KSU-001（ksud 可见） | 1 条强证据，conf 0.92 | 30×0.92 = 27.6 > 25（下限不触发） | `score=28`、`suspicious`——单条强证据**不会**直接判高风险 |
| 只有一条 FOPS-001（目录项被隐藏） | 1 条强证据，conf 0.85 | 30×0.85 = 25.5 > 25（下限不触发） | `score=26`、`suspicious`；与 KSU-001 同样是「单强不判死」 |
| 只有一条 AHK-006（`openat2`/`openat` 不一致） | 1 条强证据，conf 0.92，且把 `anti_hook_hit` 置位 | 30×0.92 = 27.6 → 反 Hook 下限 85 生效 | `score=85`、`high`——新增 10 项里只有 AHK-005 / AHK-006 会走这条下限路径 |
| 50 分边界 | 计算值 49.5 | 判级用 49.5（`>50` 不成立） | `score=50`、`level=suspicious`；阈值是严格大于，50 分仍为可疑 |

### 3.4 报告字段的解读约定

| 字段 | 含义 | 误读风险 |
| --- | --- | --- |
| `score` / `level` | 归一化后的风险分与等级 | 被白名单豁免的命中不体现在分数里 |
| `counts.hits` | 原始命中条目数（含被豁免项） | `hits>0` 且 `score=0` 是合法结果（全部被豁免） |
| `counts.available` | 本次真正执行成功的检测项数 | 权限受限项会让 `available < total`；快速模式还会让部分项**根本不出现**在 items 里（见 04 文档 §4.4） |
| `confidence` | 有命中时 = `Σ(权重×conf²) / Σ(权重×conf)`（因 w 已含 conf，代码里累加的是 `w·conf`；截断到 0.05–0.98）；无命中时 = `available/total × 0.9` | 不是「判定正确的概率」，只是证据置信度的加权均值 |
| `items[].raw` | 原始证据 JSON | 白名单匹配就是在这段文本上做的，排查豁免问题时直接看它 |

## 4. 标准 JSON 白名单模板

### 4.1 完整模板（与 `assets/whitelist_default.json` 一致，version 3）

```json

  ],
```

> 注意：Kotlin 侧 `WhitelistData.toJson()` 会重新序列化为 `schema=1, version=1` 且**不输出 `mountPaths`**，所以 native 实际收到的 JSON 与本模板不同；对账时以 `RaspNative.runDetect` 的入参为准。

### 4.2 字段说明

| 字段 | 类型 | native 是否解析 | 语义 | 维护建议 |
| --- | --- | --- | --- | --- |
| `schema` | int | 否 | 模板结构版本 | 结构变化时递增 |
| `version` | int | 否 | 内容版本（运行时会被 Kotlin 重写为 1） | 每次改条目 +1 |
| `note` | string | 否 | 匹配规则说明 | 随规则变化同步更新 |
| `mountPaths` | string[] | **否** | 正常挂载点清单，仅作文档说明 | 不会被 `WhitelistData` 解析，也不下发 native；不要指望它参与匹配 |
| `mounts` | string[] | 是 → `wl_mount` | 多词挂载锚点（`overlay on /system_ext` 等） | 分号分隔让多词锚点完整保留；目前只有 MNT-004 的 `/system_ext` 示例能命中 |
| `processes` | string[] | 是 → `wl_proc` | 系统应用包名（`com.android.*`、`android.hardware.`） | 只放 ≥ 10 字节的包名；通用进程名（`system_server` 等）已进黑名单，写了也不生效 |
| `properties` | string[] | 是 → `wl_prop` | `键=值` 全串 | 只有证据 raw 出现该全串才生效；对强证据还要求 ≥ 14 字节（这些条目都满足） |
| `kernel` | string[] | 是 → `wl_kernel` | 内核配置标记 / 版本属性前缀 | 已删除 `Linux version` 系列，避免 KRN-002 整条豁免；新增条目要注意不要与证据正文撞车 |
| `oem` | string[] | 是 → `wl_oem` | CloreOS 原厂属性键 / 前缀 | 证据 raw 里通常是属性**值**，键前缀基本不命中；保留作声明与后续扩展 |

### 4.3 条目编写规则（避免「越写越免检」）

1. **多词锚点可以直接写**：native 用 `;` 分隔，`overlay on /system_ext` 会保持完整（第三版改动）。
2. **非 ID 片段至少 10 字节，且不能以 `/` 开头**：`init`、`zygote`、`overlay`、`/system`、`/data` 都不会生效。
3. **六个通用进程名永不生效**：`system_server`、`zygote64`、`zygote`、`init`、`surfaceflinger`、`servicemanager`——不要用它们做豁免。
4. **要豁免强证据，片段必须 ≥ 14 字节且含 `=`、`.` 或 ` on `**：例如 `ro.build.display.id=CloreOS`、`overlay on /system_ext`；`proc on /proc`（13 字节）只能豁免间接/弱线索。
5. **按检测项豁免请直接写 ID**（如 `MNT-004`，7 字符有效）：建议只用于业务已知误报，并在变更记录里写明原因；不要用它掩盖真实问题。
6. **不要写「证据 raw 正文里本来就有」的通用词**：即使能通过长度与特异性检查，也等于给该类证据开后门。
7. **控制总量**：`wl_mount`/`wl_proc`/`wl_kernel`/`wl_oem` 各 768 字节、`wl_prop` 1024 字节；分号也占字节，超出后静默丢弃。
8. **改模板必须跑对照测试**：同一台设备、同一次构建，白名单开/关各跑一遍，逐项对比 `score` 与 `hits`（记录模板见 04 文档 §7）。

## 5. 运行时加载与验收自检

### 5.1 加载时序

1. `RaspEngine.detect()` 在 `Dispatchers.Default` 上先执行 Java 探针（ZYS-005 / ZYS-006 / ZYS-008），再读取白名单；
2. `WhitelistLoader.loadDefault()` 从 assets 读取并解析（只取 5 个数组）；解析失败 → 返回空 `WhitelistData`（不抛异常、不阻断检测）；
3. `loadForNative()` 合并额外条目并序列化（`mountPaths` 丢失、`version` 被重写）；
4. JNI 侧逐字段 `rasp_extract_array()` 灌入 `ctx`（条目用 `;` 拼接），随后检测开始；
5. 每条证据在 `rasp_emit()` 时已经定稿，白名单只在打分阶段生效——**不存在「先豁免后采集」**。
